# Собственная прошивка U7005

Приложение для NUC1261NE4AE на плате MPG 341CQPX. Код приложения, startup,
протокол MSI, транспорт расширения и MSC написаны на C11. Код или патч исходного
APROM MSI в образ не включаются. Драйверы периферии и CMSIS — открытый NUC1261BSP.
Штатный LDROM остаётся отдельным загрузчиком; собственной реализации LDROM здесь нет.

**Сборка, USB-установка и базовая аппаратная проверка прошли 2026-09-14:**
локальные команды, UART к скалеру и чтение 512 байт через 4A с независимой сверкой.
Побайтово проверены USB-дескрипторы и 10 653 HID-ответа реального обновления MSI,
с ответами скалера, подставленными на границе HAL. Это не доказательство физической
совместимости всех команд, таймингов, сна и пробуждения. Границы проверки и новые
результаты разбора: [docs/u7005-source-firmware.md](../../docs/u7005-source-firmware.md).

## Сборка

Из корня репозитория, после [установки инструментов](../../docs/u7005-development.md):

```sh
make -C firmware/u7005 verify
```

`make all` собирает без исходного дампа; `test` запускает проверки C на хосте;
`verify` дополнительно сверяет ELF, HEX, дескрипторы, оригинальные таблицы и захват.
Python используется только из корневой `.venv`. Для host-тестов нужен системный `cc`
с ASan/UBSan (на этом Mac — Apple Clang). Необходимые зависимости уже установлены.
Эталоны MSI лежат в [`tests/data/`](tests/data/README.md): нужные проверкам 404 байта
APROM, обмен с LDROM и штатное обновление FW.034. Обновление восстанавливается из
эталона и файла FW.034 с сайта MSI (путь — `U7005_FW034`, по умолчанию корень
репозитория) и сверяется с SHA-256 исходного захвата. Полный APROM можно задать
через `U7005_REFERENCE`. Отсутствие эталона — ошибка интеграционной проверки, а не
пропуск теста.
Путь сборки переопределяется `BUILD=/absolute/path`.

В `out/u7005/` создаются:

| Файл | Назначение |
|---|---|
| `u7005.elf`, `u7005.map` | Символы, адреса, отладка |
| `u7005-code.bin` | Только код и начальные данные приложения с адреса 0 |
| `u7005.hex` | Разреженный образ: приложение, виртуальный диск, длина и сумма для LDROM |
| `u7005-disk.bin` | Собственный FAT12-том, 44 сектора по 512 байт |
| `u7005-manifest.json` | Адреса, размеры, SHA-256, checksum и отметка `hardware_tested: false` |

BIN с кодом сам по себе **не является полным установочным образом**. В HEX намеренно
нет страницы режима USB, DataFlash, CONFIG, LDROM и SPROM. Программатор должен
сохранять отсутствующие диапазоны; стирание всего APROM этого свойства не имеет.
Существующий ISP-загрузчик при обновлении стирает весь APROM до DFBA, поэтому
обычная загрузка BIN его командой A0 не эквивалентна применению этого HEX.
Автоматической установки/стирания в сборке нет. Первый аппаратный запуск
описан в [исследовании](../../docs/u7005-source-firmware.md#первый-usb-запуск-и-ошибка-systick).

USB ISP подходит и для первой установки. Дополнительный USB BIN создаётся из
сборки и резервного APROM командой ниже. Перед включением USB приложение проверяет
полученный образ и заменяет метаданные суммой только кода: последующее изменение
диска и USB mode не нарушит загрузочную проверку. Ошибка возвращает мост в LDROM.
SWD полезен для независимого чтения и восстановления при неработающем USB нового
приложения; использовать его именно для записи необязательно.
Подробности: [проверка USB-установки](../../docs/u7005-ldrom.md#первая-установка-собственного-приложения-через-usb).

## Установка через USB

Сначала собрать и проверить прошивку, затем подготовить комплект из резервной копии
**своего** моста. Команды из корня репозитория; `prepare` и `check` не открывают USB:

```sh
make -C firmware/u7005 verify
.venv/bin/python tools/u7005_usb_update.py prepare --build out/u7005 --backup flash/u7005_aprom.bin --config flash/u7005_config.bin -o out/u7005/u7005-usb.bin
.venv/bin/python tools/u7005_usb_update.py check out/u7005/u7005-usb.bin
```

`prepare` создаёт `u7005-usb.bin` и обязательный `u7005-usb.json` с SHA-256,
параметрами микроконтроллера, суммами кода/передачи и происхождением сохранённых
областей. Существующие файлы не перезаписываются: для новой сборки задайте новый
путь результата. Обычный `make` собирает приложение без дампа экземпляра.

Запись, если мост уже в USB ISP (`0416:3F00`):

```sh
.venv/bin/python tools/u7005_usb_update.py flash out/u7005/u7005-usb.bin --already-isp --out captures/u7005-usb-install-NEW
```

Если мост работает как приложение `1462:3FA4`, уберите `--already-isp`: утилита
проверит B0/B2/B4 и USB mode, затем сама переведёт **мост** в LDROM локальной A0.
Входить в ISP скалера через `isp_read.py` для этого не требуется.
В уже открытом LDROM board ID до записи недоступен: проверяются PDID, версия,
CONFIG0/1 и источник загрузки; board ID сверяется после запуска приложения.

Запись действительно стирает APROM `[0,1F800)`. BIN восстанавливает код, диск и
хвост APROM до `1F7F8` из выбранного комплекта; текущий DataFlash не стирается и
не заменяется дампом. CONFIG/LDROM/SPROM и флеши скалера не записываются.
Комплект, подготовленный 2026-09-14, использует APROM от 2026-08-16 и режим 0;
это не свежий снимок всех текущих областей. При изменившемся mode обычный вход
прерывается до стирания — нужен комплект из актуального APROM.

После каждого блока сверяются сумма ACK и номер пакета, после последнего — сумма
всей передачи. Затем AF проверяет загрузочные метаданные и запускает приложение.
Хост ожидает USB, проверяет U7EX, board ID, mode и B0 с новой суммой только кода.
Все исходные пакеты, точный записываемый образ и `result.json` сохраняются в новом
каталоге `--out`. При ошибке блоки не повторяются, AB/AF не отправляются как cleanup.
Неудача проверки уже запущенного приложения означает `complete=false`, но не откат.

Для независимого read-back через SWD добавьте к `flash` флаг `--stay-in-isp`.
Тогда после проверенной передачи мост остаётся в LDROM, `transfer_verified=true`,
`complete=false`. До первого запуска длина/сумма в `1F7F8/1F7FC` относятся ко всему
USB BIN. После чтения запустить приложение можно отдельно:

```sh
.venv/bin/python tools/u7005_usb_update.py run out/u7005/u7005-usb.bin --out captures/u7005-usb-run-NEW
```

`run` не передаёт APROM заново; первый запуск приложения сам обновляет страницу
метаданных. Суммы ISP — 16-битные, полного побайтового read-back через этот USB
протокол нет. **Первая запись состоялась, приложение запустилось, но обнаружена
ошибка SysTick**: ответ оставался в очереди до следующего USB-прерывания.
Исправленная сборка с суммой `8118` установлена и проверена без обхода;
[захваты и границы проверки](../../docs/u7005-source-firmware.md#аппаратная-проверка-исправленной-сборки).
Формат комплекта и нормализации: [u7005-usb-v1.md](../protocols/u7005-usb-v1.md).

### Обновление первой сборки с ошибкой SysTick

В первой сборке (`code sum=624D`) `USBD_Start()` выключал SysTick. В исправленной
`usb_init()` восстанавливает период 1 мс после каждого запуска USB, включая смену
режима. Комплект исправления: `out/u7005-usb-tick-fix/u7005-usb.bin` и соседний JSON;
сумма кода `8118`, сумма USB BIN `C62B`. Старый комплект `out/u7005/` сохранён.

```sh
.venv/bin/python tools/u7005_usb_update.py flash out/u7005-usb-tick-fix/u7005-usb.bin --wake-stalled-app --out captures/u7005-usb-install-02
```

`--wake-stalled-app` после пустого чтения однократно посылает HID GET_REPORT:
его USB-прерывание будит главный цикл. Кешированный контрольный ответ игнорируется;
утилита ждёт обычный interrupt IN. Команда не повторяется. Обход применяется только
при проверке старого приложения перед входом в ISP; новая прошивка после AF должна
ответить без обхода. Этот переход и полная установка подтверждены в сеансе
`captures/u7005-usb-install-02`.

Отдельная проверка уже установленной первой сборки, без сброса и записи:

```sh
.venv/bin/python tools/u7005_usb_update.py verify out/u7005/u7005-usb.bin --wake-stalled-app --out captures/u7005-usb-verify-NEW
```

Для исправленной сборки указать её BIN и убрать `--wake-stalled-app`.
Успех `verify` подтверждает ответы приложения и сумму из метаданных, а не полный
побайтовый read-back. `complete=true` с обходом не доказывает исправность таймера.

## Команды

| Транспорт | Реализация |
|---|---|
| Report 1 | ASCII passthrough, настройки `5b00130`/`5800130`, macro/aux события; A0, B0/B2/B4/B6, C0, D0/D2, E0 |
| Report 2 | Все A0…C3, UART1 и три семейства длинных передач |
| Report 3 | A0/A1: запись, B0/B1: чтение регистров через I2C1 |
| Report 4 | Все A0…C3, таблицы длин MSI, STOP между записью и чтением, особый вход A0/A1 |
| Report 1 E2 | Обнаружение расширения `U7EX` |
| Report 4 4A | Чтение страницы U4002 и получение фрагментов из её буфера |
| MSC, если D0 включает составной режим | SCSI 00,03,12,15,1A,1B,1E,23,25,28,2A,2F,55,5A,9E,A8,AA; дополнительно 35 |

Сохраняются VID/PID `1462:3FA4`, дескрипторы, размеры пакетов и номера endpoints.
Версия B0 остаётся `54` как версия совместимого ABI; отличать эту реализацию нужно
по E2. Сумма приложения B0 соответствует новой сборке. Настройки, USB mode и ID
читаются из сохранённых областей конкретного моста. Аппаратная конфигурация задана
для исследованной платы с UART1/I2C0 на PE12/13 и I2C1 на PF3/4, revision=1.

## Чтение flash

**2026-09-15:** `isp_read.py` и read-back `isp_write.py` автоматически обнаруживают
4A; `--flash-read-method legacy` сохраняет старый способ без E2, `4a` требует
расширение. По 512 байт обоих банков сверены двумя способами; через 4A проверена
запись загрузчика. В мост установлен также таймаут всей I²C-транзакции 1000 мс:
прежние 250 мс не позволяли передать 4098 байт при 100 кГц.
[Протокол опыта и ограничения](../../docs/u7005-source-firmware.md#isp-tools-4a).

Формат расширения задан в [firmware/protocols/u7005-flash-v1.md](../protocols/u7005-flash-v1.md).
Хост сначала посылает безопасный E2; без его ответа Report 4/4A не отправляется.
После установки и отдельной аппаратной проверки прошивки:

```sh
.venv/bin/python tools/u7005_flash_read.py --info
.venv/bin/python tools/u7005_flash_read.py --read 0x0 0x200 -o out/page.bin --enter
```

`--enter` использует полный вход в ISP из `isp_read.py`, останавливающий обычную
работу скалера. После него для возврата монитора требуется передёрнуть питание.
`--reuse` предназначен для уже подготовленного полного ISP; `--bootloader` — для
входа из bootloader-libre. Утилита не восстанавливает обычный режим автоматически.
Разрешён диапазон 32 МиБ U4002; хост поддерживает некратные 512 адрес и длину,
обрезая краевые страницы. Существующий выходной файл не перезаписывается.
При ошибке частичный BIN остаётся без итогового JSON и не считается завершённым дампом.

## Как расширять

`src/bridge.c` не зависит от регистров ARM или USB SDK: принимает ровно 64 байта,
вызывает функции из `bridge_io` и формирует ответ. Новую команду добавлять отдельным
обработчиком перед legacy-dispatch; формат фиксировать в `firmware/protocols/`,
возможность объявлять через discovery, а тесты гонять через тот же C и mock HAL.
Не менять таблицы A0…C3 ради расширений — существующие утилиты используют их длины.

`board.c` реализует выводы, UART/I2C, часы и FMC. `usb.c` владеет endpoints и очередями;
длительные операции исполняются в главном цикле. `msc.c` ограничен виртуальным диском.
Для нового аппаратного примитива добавлять явную функцию HAL, а не доступ к MMIO из
обработчика команды. SRAM не выделяется динамически; linker резервирует минимум
2 КиБ стека. Два буфера длинных посылок по 4160 байт не смешивают UART и I2C.

## Flash и ограничения

Код ограничен `00000…0FFFF`, виртуальный диск — `10000…157FF`; `1E800…1EFFF` —
сохранённый USB mode, `1F7F8/1F7FC` — длина/сумма, `1F800…1FFFF` — DataFlash.
FMC допускает запись только этих страниц диска, mode и DataFlash, с проверкой DFBA;
для метаданных отдельно разрешены ровно 8 байт по `1F7F8` с сохранением страницы.
FMC-примитив находится в SRAM, прерывания на время операции выключены, запись
проверяется чтением. При зависшем FMC исполнение остаётся в SRAM.

Изменение страницы не защищено от пропадания питания между erase и program;
сохранённые дампы по-прежнему нужны. Перезапись B6 и настроек сохраняет остальные
байты DataFlash, тогда как MSI их стирает. Неопределённые запросы с выходом за
таблицы/буферы MSI не воспроизводятся. Виртуальный FAT12 создан заново и содержит
ссылку на поддержку MSI; исходные файлы диска не копируются. MODE SENSE(6) сообщает
write-protect, как MSI; сырой WRITE остаётся реализован. Автовыбор старой разводки
UART2, недоказанные эффекты PWM и ветка глубокого сна MCU из MSI не переносились.
Фактическое включение этой ветки MSI на мониторе не подтверждено; её разрешающий
флаг исходно нулевой. [Условия сна и отличие нашей реализации](../../docs/u7005-source-firmware.md#что-именно-не-перенесено-из-энергосбережения-msi).
Эти границы нельзя описывать как полную аппаратную взаимозаменяемость.
