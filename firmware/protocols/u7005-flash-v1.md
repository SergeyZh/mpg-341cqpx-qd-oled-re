# U7005: расширение чтения flash, версия 1

Этот документ определяет собственный USB-протокол. Он не является описанием
штатного формата MSI или vendor-запросов VIA/ASUS. Все HID-пакеты имеют 64 байта,
включая Report ID; неописанные байты запроса нулевые. Многобайтные числа — LE,
кроме отдельно описанного I²C-запроса скалеру.

## Обнаружение

Запрос: `01 E2`, остальные 62 байта нулевые. В MSI v54 локальный E2 не обработан.
Хост обязан получить этот ответ **до первого** Report 4 с подкомандой 4A:

| Смещение | Размер | Значение |
|---|---|---|
| 0 | 1 | Report ID = 1 |
| 1 | 1 | `5A` |
| 2 | 4 | ASCII `U7EX` |
| 6 | 1 | Версия = 1 |
| 7 | 1 | Подкоманда = `4A` |
| 8 | 1 | Возможности = 1 (чтение страниц) |
| 9 | 2 | Размер страницы = 512, LE |
| 11 | 1 | Максимум данных в HID-ответе = 52 |

Таймаут discovery не означает разрешение продолжать: штатная прошивка индексирует
таблицу Report 4 через `subcommand−A0`, без проверки нижней границы.

## Запрос 4A

| Смещение | Размер | Значение |
|---|---|---|
| 0 | 1 | Report ID = 4 |
| 1 | 1 | Подкоманда = `4A` |
| 2 | 1 | Версия = 1 |
| 3 | 1 | 1 = READ, 2 = FETCH |
| 4 | 2 | Token хоста, LE |
| 6 | 2 | Смещение внутри страницы, LE |
| 8 | 4 | Байтовый адрес flash, LE (используется только READ) |

READ принимает адрес `00000000…01FFFE00`, кратный 512, и смещение 0. Нужен ранее
подготовленный полный ISP скалера и режим I2C у моста (`01 E0 01`). READ очищает
незавершённый legacy I2C-stream и предыдущую страницу, выбирает банк, читает новую
страницу и возвращает первые 52 байта. Сам READ не вводит скалер в ISP.

FETCH принимает смещение 0…511 и token последнего успешного READ. Адрес в FETCH
игнорируется. Он читает только SRAM, без I²C; повторный FETCH идемпотентен. Буфер
сбрасывается новым READ, USB reset, переключением E0/USB mode и любой legacy-командой
Report 4. Следует держать один последовательный сеанс хоста: token не является
межпроцессной блокировкой, и после повторного READ тот же token использовать нельзя.

## Ответ

| Смещение | Размер | Значение |
|---|---|---|
| 0…2 | 3 | `04 4A 01` |
| 3 | 1 | Статус |
| 4 | 2 | Token из запроса |
| 6 | 2 | Смещение из запроса |
| 8 | 1 | Число данных `min(52,512−offset)`, при ошибке 0 |
| 9 | 1 | 1, если в странице остались данные; иначе 0 |
| 10 | 2 | Полный размер страницы = 512, LE |
| 12 | 0…52 | Данные flash, затем нулевое заполнение до 64 |

Статусы: 0 — успех; 1 — неверные версия/операция/адрес/смещение;
2 — мост не в I2C; 3 — ошибка I2C или таймаут; 4 — неверный ответ скалера;
5 — страницы нет; 6 — token не совпадает. При ошибке данные не выдаются.
HID не передаёт отдельную контрольную сумму: USB защищает передачу своим CRC,
а мост проверяет XOR полного I²C-ответа до выдачи любой части страницы.

## I²C, используемый READ

1. Запись `6E 02 0F bank XOR`, где `bank=address>>24`; STOP, задержка 20 мс.
2. Чтение на SLA+R `6F` четырёх байтов: `02 F0 bank XOR`; STOP.
3. Запись `6E 04 4A a23 a15 a7 XOR`; STOP, задержка 20 мс.
4. Одна транзакция чтения 515 байтов: `len B5`, 512 байтов данных, XOR; STOP.

SLA не входит в принятые данные. Для проверки XOR адрес `6F` добавляется логически.
XOR записи включает `6E`, длину и все аргументы; XOR ответа вместе с `6F` должен
равняться нулю. Для страницы проверяются B5 и XOR, но не первый байт длины:
его точное значение не установлено. Внутри 515-байтной транзакции мастер ACK-ает
первые 514 байтов и NACK-ает последний.

Handshake `00` в утилите ASUS — ответ USB-моста о завершении записи; это не
дополнительный байт I²C, и здесь его заменяет успешное завершение `i2c_write`.
Основание: разбор ASUS (не опубликовано).
Физическая поддержка этого обмена NT68503 требует отдельного опыта.
