# U7005: LDROM 1.5, USB ISP и протокол обновления

Разбор 2026-09-13, шаг 38. Объект — собственная прошивка NUC1261NE4AE из
`flash/u7005_aprom.bin`, а не FW.034/FW.037 скалера.

**USB-вход в ISP и возврат проверены на мониторе.** Отчёт приложения `01 A0`
выбирает `BS=1`, делает CPU reset и приводит к перечислению `0416:3F00`.
Загрузчик отвечает версией `15`, PDID и CONFIG; команда ISP `AB` возвращает
приложение `1462:3FA4`. **Команды стирания и записи не посылались.**

Настоящий LDROM прочитан через FMC дважды и сохранён как
`flash/u7005_ldrom_fmc.bin`. Прежний `flash/u7005_ldrom.bin` сохранён для истории:
это зеркало APROM, полученное по AHB. Вывод о невозможности USB-ISP был ошибочным.

Первичные свидетельства:

- два дампа FMC, контрольные чтения AHB/APROM, CONFIG и журнал (не опубликовано);
- исходные USB-отчёты входа, опроса и выхода (не опубликовано),
  сопоставление сведений до и после (не опубликовано).

## Что установлено по коду команды A0

Адреса ниже — адреса исполнения APROM/SRAM. Проверены листинги Ghidra, включая
вызываемые RAM-функции; одной декомпиляции диспетчера недостаточно.

| Адрес | Действие |
|---|---|
| `2256…227A` | Меняет приоритет IRQ 23 через `3D68`; обнуляет `PWM0.CMPDAT[0…5]` (`40040050…64`) и `PWM1.CMPDAT[3…5]` (`4014005C…64`) |
| `227E…2288` | `USBD.INTEN` (`40060000`) &= `~0x110`: выключает SOF interrupt и wake-up enable |
| `228A` | `53F8`: разблокирует защищённые регистры SYS |
| `228E…2296` | `WDT.CTL` (`40004000`) = 0, ждёт сброса бита 30 |
| `2298` | Через thunk `2A0` вызывает `20002814`: `FMC.ISPCTL.ISPEN=1` |
| **`229C…229E`** | **`r0=1`; thunk `2D0` → `2000286C`: устанавливает `FMC.ISPCTL.BS=1`** |
| `22A2…22A8` | `NVIC.ICPR` (`E000E280`) = `FFFFFFFF` |
| `22AA…22BC` | FMC-команда `2E`, адрес `00100000`, trigger = 1, ожидание завершения |
| **`22BE`** | **thunk `2DC` → `20002E98`: `SYS.IPRST0` (`50000008`) |= 2, CPU reset** |

В старом описании были три ошибки: PWM назван UART, запись в `USBD.INTEN` названа
отцеплением USB, а `BS` и CPU reset пропущены. Запись `INTEN` сама по себе не
отключает USB PHY или pull-up: `USBD.ATTR` расположен по `40060010`.
Повторное перечисление обеспечивается последующим кодом LDROM и проверено живьём.

Семантика проверена по официальному
[NUC1261.h](https://github.com/OpenNuvoton/NUC1261BSP/blob/94bfd7c4cf92f08b7e7c6ab155f2991848a9ba4c/Library/Device/Nuvoton/NUC1261/Include/NUC1261.h):
карта PWM/UART, поля `USBD.INTEN`, `SYS.IPRST0.CPURST`, `FMC.ISPCTL.BS`.
Та же последовательность выбора источника и последующего reset описана в
[FMC_SetBootSource](https://github.com/OpenNuvoton/NUC1261BSP/blob/94bfd7c4cf92f08b7e7c6ab155f2991848a9ba4c/Library/StdDriver/src/fmc.c).

## CBS=01: почему значение VECMAP не объясняет загрузку

Сохранённые `CONFIG0=FFFFFB7E` и `ISPSTS=00100002` дают `CBS=01`.
В примечании к `FMC_SetVectorPageAddr` и `FMC_GetVECMAP` официальный
[fmc.h](https://github.com/OpenNuvoton/NUC1261BSP/blob/94bfd7c4cf92f08b7e7c6ab155f2991848a9ba4c/Library/StdDriver/inc/fmc.h)
ограничивает действие VECMAP режимами `CBS=00/10` — с IAP. Поэтому на нашем
экземпляре значение `00100000` в ISPSTS **не доказывает**, что векторы APROM
замещены векторами LDROM. Существенный механизм перехода — `BS` плюс reset.

При холодном сбросе BS загружается инверсией CONFIG0[7], то есть единицей.
CPU reset его сохраняет. В прежнем сеансе работающего приложения читался BS=0.
Это согласуется с отдельным загрузчиком, переключающимся на приложение.
Его решающее условие установлено по настоящему LDROM ниже.

## Что действительно лежит в старом файле LDROM

SHA-256 `flash/u7005_ldrom.bin` и первых 4096 байт `flash/u7005_aprom.bin`:

```text
921e5d3cab297b7d0ba59bba9e7d4916cd2bcbe83167085eab6b61773cd21e9e
```

Совпадение файлов проверено целиком, а путь исполнения — в Ghidra как на базе 0
(APROM), так и после отдельного импорта файла LDROM по `00100000`:

| Смещение в файле | Содержимое и следствие |
|---|---|
| `0000` | Начальный SP = `20004868`, стек приложения |
| `0004` | Reset vector = `00000101`, адрес Thumb `0100`, **не** `00100101` |
| `0100…0116` | Разблокировка SYS, запись `5AA5` по `50000024`, блокировка SYS |
| `0118…011A` | Абсолютный вызов `00005561` (Thumb); за пределами файла 4 КиБ |
| `011C…011E` | Абсолютный переход на startup `000000CD` |
| `00CC…00D0` | Установка MSP и переход в scatter-loader `0220` |
| `0220…0238` | Таблица инициализации `6F5C…6F74`; код и исходные данные вне 4 КиБ |
| `00D4` | Переход на `200030C5`, главный цикл приложения в SRAM |
| `0FF4…0FFF` | `2000006E`, `20000068`, `20000038`: SRAM-указатели внутри кода приложения |

При физическом импорте по `00100000` PC-relative ссылки перемещаются вместе с
файлом, но абсолютные константы `5561`, `CD`, `6F5C`, `200030C5` остаются прежними.
Автоматически прибавлять мегабайт к reset vector нельзя. Простое ребазирование
не превращает фрагмент приложения в самостоятельный загрузчик.

Воспроизводимый импорт старого AHB-чтения:

```bash
./tools/ghidra_import.sh u7005-ldrom-ahb
```

База задаётся **до** анализа, чтобы Ghidra не переносила уже найденные абсолютные
ссылки. Затравки — смещения `CC,100,220`; прежняя затравка APROM `A4` удалена из
скрипта импорта, поскольку это слово таблицы векторов, не начало функции.
Проверенные имена функций приложения и RAM-хелперов сохранены в
`names/u7005_boot.csv`.

**Подтверждено новым опытом:** при `CBS=01, BS=0` оба AHB-окна `0…FFF` и
`100000…100FFF` возвращают префикс APROM. Все четыре чтения равны старому файлу
LDROM и двум чтениям префикса APROM через FMC. Но FMC READ(`100000…100FFC`)
возвращает другой, самостоятельный загрузчик. Ошибка старого дампа воспроизведена;
правило зеркалирования других адресов и режимов этим опытом не устанавливается.

Сумма приложения `4F0F` для длины `DC00` подтверждает согласованность **APROM**
с его метаданными. Она не проверяет физический LDROM и не является криптографическим
доказательством происхождения образа MSI.

## Независимый контроль через B0

Обработчик `22C4` читает данные **командой FMC READ**, через `1A80`:

| Смещение в полезной нагрузке ответа, без Report ID | Источник |
|---|---|
| `0` | `5A` |
| `1` | версия приложения, константа `54` |
| `3` | младший байт FMC READ(`100FF4`), версия LDROM |
| `4…7` | FMC READ(`100FFC`), big-endian |
| `8…11` | FMC READ(`01F7FC`), big-endian; в старом APROM `00004F0F` |

Старый файл предсказывал версию `6E` и поле суммы `20000038`. Живой ответ B0
вместо этого дал `15` и `0000D926`, в точности как настоящий дамп FMC:

```text
01 5a 54 00 15 00 00 d9 26 00 00 4f 0f 01 00 ...
```

После входа и выхода ответ совпал побайтово. B2 дал PDID `01205206`, B4 —
идентификатор `1C33D802`; они также не изменились. B0 читает **сохранённые** суммы,
а не пересчитывает всю прошивку; полную побайтовую неизменность флеша этот ответ
сам по себе не доказывает. Отсутствие команд записи проверено отдельно по USB-трассе.

## Физическое чтение: выполнено

`tools/u7005_ldrom_read.py` использует FMC READ (`ISPCMD=00`), независимо от AHB-
отображения. Сохраняет по два чтения LDROM, префикса APROM, CONFIG и метаданных
APROM, а также два снимка AHB `0`/`100000`. SHA-256, исходные FMC-регистры и
состояние восстановления записываются в `manifest.json`. Кэши pyOCD выключены.

```bash
# Проверка на модели FMC, без железа:
.venv/bin/python tools/verify_u7005_ldrom_read.py

# На обесточенном мониторе, с внешними 3,3 В на CN7003.1 и CMSIS-DAP:
.venv/bin/python tools/u7005_ldrom_read.py --out captures/u7005-ldrom-NEW
```

Каталог должен быть новым. Старые `flash/` не перезаписываются. Скрипт не меняет
BS, VECMAP или CONFIG, не сбрасывает MCU; разрешения обновления `*UEN` снимаются
на время чтения, допустима только команда READ. Перед вмешательством ядро
останавливается. После завершения исходные регистры возвращаются и проверяются;
ранее работавшее ядро возобновляется. Если FMC занят или восстановление не удалось,
ядро остаётся остановленным. Не подавать внешние 3,3 В одновременно со штатным
питанием монитора — порядок подключения описан в [U7005](mcu-u7005.md#подключение-по-swd).

На модели проверены два физических чтения, сохранение BS и прежней остановки ядра,
восстановление после ISPFF, отказ при занятом FMC и timeout без возобновления ядра.
На железе считыватель отработал успешно: `complete=true`,
`registers_restored=true`, ранее работавшее ядро возобновлено. Исходные
`ISPCTL=0`, `ISPSTS=00100002`, `DFBA=1F800`, PC=`20003408`.

Два физических дампа LDROM имеют SHA-256:

```text
adf83bc017642eb676b40d746a5de30fb3206be70d3d162e7f6e7dfa55e1e330
```

По смещениям `FF4/FF8/FFC` лежат слова LE `15/FEC/D926`.
Сумма байт `[0,FEC)` по модулю 65536 равна `D926`. Это третья проверка после
двойного чтения и независимого B0. CONFIG и метаданные APROM совпали с прежними
сохранёнными файлами.

## Исполнение настоящего LDROM

LDROM физически расположен по `100000`, но при нашем `CBS=01` исполняется
с нулевой базы. Начальный SP=`20000D28`, reset vector=`000000D5`.
Импортировать как `ARM:LE:32:Cortex` с **базой 0**:

```bash
./tools/ghidra_import.sh u7005-ldrom
```

Имена — `names/u7005_ldrom_v15.csv`. Startup `C0` через scatter-loader `120`
обрабатывает таблицу `F28…F48`: копирует `A4` байта из `F48` в `20000000`,
обнуляет `C84` байта с `200000A4`, затем переходит в `D18`.
`AddCortexMem.java` переносит инициализируемые данные до анализа. Единственный
периферийный вектор с рабочим обработчиком — USBD IRQ (`848`); остальные заглушены.

Главный код `D18` настраивает тактирование, открывает FMC, определяет объём APROM
по PDID (`284`, для нашего чипа `20000`) и Data Flash по CONFIG0/1 (`2BC`).
Затем в `D5A…D98` выбирает ISP или приложение:

1. Если `SYS.RSTSTS.CPURF` (бит 7) установлен, очищает наблюдавшиеся reset flags
   записью обратно и **остаётся в ISP**. Так работает вход из приложения по `A0`.
2. Иначе FMC READ(`DFBA−8`) даёт длину приложения. Если длина больше APROM size,
   остаётся в ISP.
3. FMC READ(`DFBA−4`) даёт сохранённую сумму. Функция `144` читает приложение через
   FMC блоками по `800` байт и суммирует ровно указанную длину, modulo 65536.
4. При совпадении суммы: `RSTSTS=3`, сброс `ISPEN/BS`,
   `SCB.AIRCR=05FA0004` (system reset) — запуск APROM. При несовпадении — ISP.

В этом пути **нет проверки GPIO DetectPin, кнопок или тайм-аута ожидания хоста**.
Выбор по reset cause и сумме отличается от примера `ISP_HID` в публичном BSP.
На обычном старте существующее приложение проходит проверку `DC00/4F0F`.
Поведение при специально повреждённом APROM не испытывалось.

## USB и кадры ISP

Дескриптор устройства начинается по `E93`: VID/PID=`0416:3F00`.
Конфигурация `EA5`: один HID-интерфейс, interrupt IN `81` и OUT `02`,
оба по 64 байта, интервал 1 мс. HID report descriptor по `E78` не содержит
Report ID. Поэтому в `hidapi.write` перед 64 байтами протокола добавляется нулевой
байт Report ID; входной отчёт содержит ровно 64 байта без него. Это проверено живьём.

| Байты кадра протокола | Запрос | Ответ |
|---|---|---|
| `0…3` | команда, uint32 LE | в `0…1` — сумма 64 байт обработанного запроса, uint16 LE; `2…3` незначимы |
| `4…7` | номер пакета, uint32 LE | следующий номер, uint32 LE |
| `8…63` | аргументы/данные | результат |

`390` — весь диспетчер. Он **не проверяет** входной номер пакета и не принимает
контрольную сумму в запросе. Его счётчик начинается с 1; ответ получает 2,
следующий запрос хоста использует 3 и т. д. `AE` сбрасывает счётчик к 1;
`A4` задаёт его словом `[8…11]`. В проверке `A4(101)` вернул 102, следующий
`A2` — 104. Проверять сумму и порядок обязан хост.

До разбора команды загрузчик читает CONFIG0/1 в ответ `[8…15]`. Поэтому
`A2` работает как чтение CONFIG через общую ветку, без отдельного сравнения
опкода. Это подтверждено и кодом, и USB-ответом.

## Команды реального загрузчика 0x15

| Код uint32 LE | Поведение | Проверка |
|---|---|---|
| `AE` | Connect, счётчик = 1; в ответе CONFIG0/1 | USB |
| `A4` | Счётчик из `[8…11]` | USB |
| `A6` | Версия `15` в `[8]` | USB |
| `B1` | PDID в `[8…11]`, у нас `01205206` | USB |
| `A2` | CONFIG0/1 в `[8…15]` | USB |
| `CA` | Источник загрузки: 2 при BS=1, иначе 1 | USB: 2 |
| `AB` | Снять ISPEN/BS и выполнить system reset в APROM, без проверки его суммы | USB: приложение вернулось |
| `AF` | Проверить длину/сумму приложения и при успехе перейти в APROM | Ghidra, `450…494`; при отказе не формирует новый достоверный ответ |
| `AC` | BS=1, ISPEN=0, system reset | Ghidra; это не CPU reset, CPURF не задаётся этой командой |
| `AD` | Снять ISPEN, сохранить BS, system reset | Ghidra |
| **`A0`** | **Сразу стереть APROM `[0,DFBA)`, затем начать запись с адреса 0** | Ghidra; **не посылалась** |
| `00` | Продолжить начатую передачу A0/C3 | Ghidra; не посылалась |
| `C3` | Стереть Data Flash и начать запись с DFBA | Ghidra; не посылалась |
| `A1` | Стереть CONFIG и записать CONFIG0/1 из `[8…15]`; CONFIG2 не восстанавливает | Ghidra; не посылалась |
| `A3` | Стереть APROM и Data Flash, снять LOCK через обновление CONFIG0/1 | Ghidra; не посылалась |
| `FF` | Откатить последний блок с частичным сохранением страницы и стиранием для повторной передачи | Ghidra; не посылалась |

У A1 есть условие: CONFIG0.LOCK=1 либо в сеансе уже была A0/A3.
У A0 такой защитной проверки перед стиранием нет. Общего чтения произвольного
APROM и команды обновления самого LDROM в этом диспетчере нет.

## Можно ли штатно прочитать собственную прошивку по USB

Проверка 2026-09-14 по APROM MSI 54 и физическому LDROM 15: **штатной команды
для полного дампа APROM U7005 не найдено**. Проверены прикладные HID-диспетчеры,
контрольные запросы USB, чтение виртуального MSC-диска и весь диспетчер LDROM.
Это вывод по коду сохранённых образов; перебор неизвестных команд на устройстве
не выполнялся. Он не утверждает невозможность эксплуатации ошибок протокола.

| Путь | Что можно получить | Почему это не полный дамп U7005 |
|---|---|---|
| Report 1 B0 | Версия и фиксированные слова метаданных LDROM/APROM | Адрес чтения не задаётся запросом, возвращаются сохранённые суммы |
| Report 1 B2/B4, `5800130` | PDID, board ID и фиксированный набор настроек | Нет параметра адреса/длины чтения собственной памяти |
| Reports 2/3/4 | Данные UART и внешнего I2C | Адреса относятся к внешним устройствам, не к APROM ARM |
| MSC READ(10)/READ(12), `28/A8` | Выделенное окно внутренней flash для виртуального диска | Допустимые обычные запросы ограничены 44 секторами, `[7000,C800)` |
| LDROM A2/AE, A6, B1, CA | CONFIG0/1, версия, PDID, источник загрузки | Диспетчер не выбирает произвольный адрес APROM из запроса |
| LDROM A0/00 | Суммы записанных и прочитанных обратно данных | Сначала выполняется стирание/запись, сами прочитанные байты хосту не возвращаются |

### Доказательства в приложении MSI

HID-вход `171C` направляет Reports 1/2/3/4 в `1D38/5430/51E0/2568`.
Ghidra подтверждает четыре вызова обёртки FMC READ `1A80`: `1FEE` проверяет
DataFlash+4 в обработчике настроек, а `22DC/22E6/2302` читают фиксированные
`100FF4/100FFC/1F7FC` для B0. Прочие прямые вызовы RAM READ `20002824` относятся
к загрузке настроек и режиму USB при старте. Они не принимают адрес чтения из HID.

В MSC-диспетчере `2E4C`, ветка `3080…30C6`, READ(10)/READ(12) переводит LBA в
байтовое смещение сдвигом на 9 и проверяет начало/конец относительно `5800`.
Затем `32F0 → 1208` добавляет базу `7000` и читает FMC либо буфер страницы
незавершённой записи. Таким образом, обычное чтение всего виртуального диска даёт
22 КиБ `[7000,C800)`, а не первые 128 КиБ APROM. Большие LBA, переполнения длины
и некорректные CBW не считаются штатной командой чтения и на железе не испытывались.
Включать MSC через D0 специально для этой проверки не стали: D0 меняет flash.

Контрольные запросы проходят через `603C`. Для vendor-типа код берёт callback
из `200036B4`; его начальное значение в `DBB4` равно нулю (startup копирует
`DAB8…DBFF` в `200035B8…200036FF`). Ghidra показывает для этого адреса только
чтение в `607A`; зарегистрированного vendor-обработчика чтения памяти не найдено.
Class-обработчик `1C2C` реализует управление HID/MSC, не выдачу адресного диапазона
APROM. Это проверка текущего бинарника, не свойство любого Nuvoton USB SDK.

### Доказательства в LDROM и практический вывод

В `390…614` разобраны все ветки команды. До выбора опкода `3B0` читает только
CONFIG0/1. В процессе A0/00 ветка `5AE` сначала пишет данные, `5C6` читает их
обратно в буфер **запроса**, а `602…60E` формирует сумму и номер ответа.
Байты APROM не копируются в полезную нагрузку ответа. AF проверяет длину/сумму
для запуска; отдельного режима чтения APROM у него нет.

Для свежего полного резервного дампа до замены приложения остаётся проверенный
путь SWD/FMC. USB-установщик может проверить передачу суммами, но штатный LDROM
не позволяет добавить к нему независимый побайтовый read-back всего APROM.
Прямое чтение собственной flash можно реализовать отдельной командой нашего
приложения; существующая новая 4A читает U4002 скалера и такого интерфейса не даёт.
Прошивка и установочный BIN в ходе этой проверки не изменялись.

## Порядок обновления: разбор кода и первая запись

Первый аппаратный сеанс A0/00/AF выполнен 2026-09-14; приложение запустилось,
но проверка USB выявила ошибку SysTick в собственном коде.
[Захват и границы результата](u7005-source-firmware.md#первый-usb-запуск-и-ошибка-systick).

**Локальная `01 A0` приложения и команда ISP `A0 00 00 00` имеют разный смысл.**
Первая только переводит MCU в загрузчик. Вторая уже стирает APROM.

Для будущего хоста обновления установлены следующие требования:

1. До входа сохранить актуальный полный APROM, Data Flash и CONFIG0/1/2.
   При нашем DFBA=`1F800` команда A0 стирает 63 страницы по `800` байт,
   включая байт режима USB `1E800` и метаданные `1F7F8/1F7FC`.
   Стирание не зависит от объявленной длины нового образа.
2. После `AE` проверить `A6=15`, `B1=01205206`, `A2=FFFFFB7E/0001F800`, `CA=2`.
   Для сохранения Data Flash и CONFIG не использовать A1/A3/C3.
3. Первый пакет A0: `[8…11]` — поле стартового адреса, **загрузчик его игнорирует**;
   `[12…15]` — полная длина, `[16…63]` — первые 48 байт образа.
   Последующие пакеты с командой 0 несут по 56 байт в `[8…63]`.
4. Последний пакет ограничивается оставшейся длиной. Но функции чтения/записи
   работают словами по 4 байта; безопасный хост должен требовать кратности длины 4
   и `0 < length <= DFBA−8`. Загрузчик сам эту верхнюю границу перед записью
   не проверяет. Передача до `1F7F8` с сохранённой областью режима USB позволяет
   восстановить её после общего стирания; послать только старые `DC00` байт —
   значит оставить `1E800` стёртым.
5. После каждого блока код очищает переданную область RAM и читает записанное
   обратно из флеша. Сумма ответа считается по запросу **с прочитанными обратно
   данными**, поэтому хост сверяет её с исходным пакетом. Это 16-битная сумма,
   не побайтовая криптографическая проверка.
6. В конце функция `144` вычисляет сумму всего образа; `[8…9]` ответа — uint16 LE.
   Код записывает длину в `DFBA−8`, сумму — в `DFBA−4`. Остальные байты поля
   результата могут содержать остатки CONFIG, трактовать `[8…11]` как чистый uint32
   суммы нельзя. Результаты отдельных FMC write/erase не оформлены как явный статус.
7. До запуска приложения проверить записанное независимым чтением через FMC/SWD.
   `AF` дополнительно проверяет сохранённые длину/сумму, в отличие от безусловной AB.

Автоматический повтор при ошибке небезопасен: `FF` в `54C…596` использует маску
`000FFE00` (граница 512 байт), хотя стирание/буфер рассчитаны на страницы 2048 байт.
Это ставит под сомнение сохранение начала страницы при откате внутри неё;
результат стирания по невыровненному адресу на железе не проверялся.
Поэтому нельзя считать retry безопасным и просто перенести его из типового NuvoISP.
Это статически найденное несоответствие, разрушительный опыт не проводился.

## Выполненная USB-проверка без записи

```bash
.venv/bin/python tools/u7005_isp.py probe --out captures/u7005-ldrom-usb-probe-NEW
```

Инструмент имеет только `info` и `probe`. В ISP разрешены AE/A6/B1/A2/CA/A4/AB;
опкоды обновления и продолжения передачи отвергаются до обращения к HID.
В приложении разрешены B0/B2/B4 и переход A0. Трасса содержит все отправленные
и полученные 64-байтовые отчёты протокола; начальный ноль hidapi для ISP в ней
не включён в поле `packet`.

В выполненном опыте приложение до и после сообщило: версия `54`, LDROM `15`,
суммы `D926/4F0F`, PDID `01205206`, board ID `1C33D802`. Все ответы ISP прошли
проверки суммы и номера пакета. Последовательность ISP была ровно
`AE,A6,B1,A2,CA,A4,A2,AB`. Команды A0/A1/A3/C3/FF/00 в ISP не отправлялись.

## Что это означает для обновления моста

Утилита MSI ожидает после локального `01 A0` устройство `0416:3F00` и использует
NuvoISP — это установлено по её коду, разбор DLL (не опубликовано).
Официальный BSP NUC1261 действительно содержит
[USB HID ISP](https://github.com/OpenNuvoton/NUC1261BSP/tree/94bfd7c4cf92f08b7e7c6ab155f2991848a9ba4c/SampleCode/ISP/ISP_HID).
Семейство протокола совпало, но наш загрузчик имеет собственные условия старта,
метаданные и дополнительные команды. Источник истины — физический дамп и его код.

**Шаг 38 закрыт разбором и проверкой транспорта.** На момент его закрытия реальная
запись APROM и работа новой прошивки не испытывались. Первый опыт записи позднее
описан [отдельно](u7005-source-firmware.md#первый-usb-запуск-и-ошибка-systick);
recovery после прерванной записи остаётся непроверенным.
Готового проверенного прошивальщика этот результат пока не означает: инструмент
данного шага намеренно не содержит команд стирания и записи.
Статус плана (не опубликовано).

## Первая установка собственного приложения через USB

Повторная проверка 2026-09-14: **SWD не обязателен как транспорт записи**.
Штатный USB ISP подходит и для первой установки собственного приложения.
Основание — физический дамп LDROM и его Ghidra-листинг: A0 вызывает стирание
`[0,DFBA)` в `49C → 1EC`, запись блоков — в `59C…5D0`, запись длины и суммы —
в `5D8…5FA`. При ограничении длины `DFBA−8` и использовании только A0/00
DataFlash, CONFIG, LDROM и SPROM не затрагиваются. Сохранение этих диапазонов —
вывод по коду; первый физический опыт подтвердил ответы приложения и прежний
board ID, но полного независимого read-back после записи не было.

### Резервные копии

Повторно проверены размеры, суммы и совпадения с сохранёнными захватами:

| Область | Резервная копия | Граница подтверждения |
|---|---|---|
| APROM, включая DataFlash | `flash/u7005_aprom.bin`, 128 КиБ | Полный дамп 2026-08-16; префикс 4 КиБ и метаданные совпали с двумя FMC-чтениями 2026-09-13 |
| CONFIG0/1/2 | `flash/u7005_config.bin`, 12 байт | Совпадает с обоими FMC-чтениями 2026-09-13 |
| Физический LDROM | `flash/u7005_ldrom_fmc.bin`, 4 КиБ | Два совпавших FMC-чтения 2026-09-13, собственная сумма `D926` верна |
| SPROM | `flash/u7005_sprom.bin`, 2 КиБ | Сохранённый дамп, все байты `FF` |

Полный APROM и DataFlash после 16 августа повторно не сверялись: совпадение
префикса, метаданных и board ID не доказывает неизменность остальных настроек.
Перед установкой предпочтителен свежий снимок. Старый `flash/u7005_ldrom.bin`
содержит AHB-зеркало APROM и **не является резервной копией физического LDROM**.
Проверка manifest захвата FMC и файлов реализована в
[tools/verify_u7005_usb_install.py](../tools/verify_u7005_usb_install.py).

### Требования к упаковке A0 и нормализация метаданных

У текущей [собственной прошивки](u7005-source-firmware.md) HEX содержит код,
виртуальный диск и метаданные, сумма которых покрывает только код.
Прямо передать `u7005-code.bin` недостаточно: A0 также сотрёт диск и USB mode,
хотя контрольная сумма переданного кода будет правильной.

Сплошной образ до `1F7F8`, содержащий код, диск и сохранённую страницу режима,
устраняет потерю этих данных при стирании. Однако LDROM самостоятельно запишет
длину **всего переданного образа** и его сумму. Тогда изменение mode командой D0
или данных диска через MSC может нарушить сумму, проверяемую при следующем
холодном запуске. Включение желаемых метаданных внутрь BIN этого не исправляет:
загрузчик перезаписывает их в конце передачи.

В собственной прошивке реализована адаптация: перед включением USB проверить
полную сумму, затем один раз заменить метаданные на длину/сумму только кода,
сохранив остальные байты страницы `1F000…1F7FF`. Нормализация исполняется до
изменения mode/диска. При ошибке чтения, проверки или записи приложение возвращает
мост в LDROM. Повторные успешные старты не перезаписывают метаданные.
При обрыве питания операция страницы не атомарна; физический опыт не проводился.

USB BIN и парный JSON создаёт `tools/u7005_usb_update.py prepare`; команды
`flash`/`run` записывают APROM и запускают приложение с проверкой ответов.
`u7005_isp.py` по-прежнему содержит только info/probe, его публичный whitelist
не расширен командами записи. [Инструкция установки](../firmware/u7005/README.md#установка-через-usb),
[формат комплекта и контракт нормализации](../firmware/protocols/u7005-usb-v1.md).

Проверка на сохранённых данных и модели алгоритма LDROM:

```sh
.venv/bin/python tools/verify_u7005_usb_install.py --out out/u7005-usb-install-audit.json
```

Для первой сборки до исправления SysTick код занимает `3730` байт, сумма `624D`. Полный
образ имеет длину `1F7F8`, сумму `E720` и 2304 пакета A0/00. Модель подтверждает
сохранение DataFlash, потерю ресурсов при передаче одного кода и нарушение суммы
полного образа при однобитовом изменении mode/диска. Нормализация
метаданных исключает эти области из проверки, оставляя код под суммой.
Это Python-модель по листингу, **не эмуляция ARM и не аппаратный опыт**.
Аудит не создаёт BIN; готовый файл создаёт отдельный упаковщик. Политика первого
запуска дополнительно исполняется как настоящий C в host-тестах, в том числе
в составе модели полного USB-сеанса. Разрушительные операции LDROM моделируются,
а читающая часть хоста сверяется с исходной физической трассой 2026-09-13.

### Для чего остаётся нужен SWD

При текущем CONFIG холодный старт проходит через LDROM. В `D5A…D98` он проверяет
причину сброса, длину и сумму приложения. При стёртых метаданных или несовпадении
суммы остаётся в ISP. Поэтому после незавершённой записи ожидается доступность
USB-загрузчика; восстановление после реального обрыва питания не испытывалось.

**Правильная сумма не означает работоспособный USB приложения.** Если сумма верна,
LDROM запускает APROM без окна ожидания USB-команд. Повторное включение питания
не вернёт в ISP приложение, которое зависает или не поднимает USB, но проходит
проверку суммы. Наличие дампов этот доступ не восстанавливает.

SWD нужен как независимый путь чтения и восстановления: например, выбрать BS=1
и выполнить CPU reset для входа в сохранённый LDROM либо восстановить APROM.
Ветка CPU reset остаётся в ISP (`D5A…D68`); принудительная последовательность
через SWD в таком аварийном состоянии ещё не испытывалась. Это причина держать
SWD доступным при первом запуске, но не причина обязательно записывать им образ.

Во время этой проверки устройства `1462:3FA4` и `0416:3F00` через hidapi на Mac
не обнаружены. Команды устройству не отправлялись, flash не записывался.

### Обновление LDROM

Возможно ли перепрошить LDROM U7005 — см. [ldrom-update-possibility.md](ldrom-update-possibility.md).
Краткий вывод: LDROM — это Flash-память, а не mask-ROM. Бит `LDUEN` в регистре
`FMC_ISPCTL` разрешает программирование LDROM. На нашем мониторе `LDUEN=0`,
загрузчик MSI не устанавливает этот бит и не содержит команду самообновления.
Обновить LDROM можно только через SWD (pyOCD/CMSIS-DAP).
