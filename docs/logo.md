# Загрузочный логотип: чем занят слот 3 и как логотип нарисован

Разбор по следу из `docs/input-switching.md`: в таблице слотов таймерного массива слот 3
был подписан «`0x00021D10` (показ логотипа)» без разбора. Здесь он разобран до конца,
а логотип извлечён из образа.

Все адреса — Leon2 Main, база 0; файловое смещение = адрес + `0x108000`.

## При каком условии логотип рисуется

Предикат целиком — `0x00021C74`, и две его копии внутри `APPSTATE_PWR_ON`
(`0x00021DD8` и ветка `case 2`):

```asm
ld    [%o1+0x174], %o0    ; 0xA802BD74
sethi 0x14, %o4           ; маска 0x5000
and   %o0, %o4, %o5
sethi 4, %g1              ; 0x1000
cmp   %o5, %g1
bne   -> мимо             ; бит 12 сброшен ИЛИ бит 14 установлен
lduh  [%i0+0x16e], %o3    ; 0xA802BD6E
cmp   %o3, 0x55AA
be    -> мимо
```

Условия три, и они независимы:

| Условие | Что это | Где разобрано |
|---|---|---|
| бит 12 `0xA802BD74` установлен | выключатель заставки | здесь |
| бит 14 `0xA802BD74` сброшен | **не** заводской режим | `docs/buttons.md` |
| `0xA802BD6E != 0x55AA` | **не** режим `PRODUCT` | `docs/burn-in-mode.md` |

### Бит 12 — выделенный выключатель заставки

По всем 67 обращениям к слову `0xA802BD74` маска `0x1000` встречается ровно в четырёх
местах: два чтения — это и есть предикат логотипа, и две пары чтение-запись внутри
`FUN_0006E9C0`. Больше этот бит ни на что не влияет. Оговорка к методу: перебирались
маски, собранные через `sethi`, и сдвиги; собранную иначе маску сканер бы не увидел.

Меняется бит **только по DDC/CI**, вендорским опкодом `0xE1`. Нотация как в
`docs/burn-in-mode.md`: опкод в `param[4]`, нагрузка в `param[5..7]`.

| Команда | Действие |
|---|---|
| `0xE1`, подкоманда `0xA7`, `param[6]=6`, `param[7]=1` | установить бит 12 — заставка включена (`0x0006FC04`) |
| `0xE1`, подкоманда `0xA7`, `param[6]=6`, `param[7]≠1` | сбросить бит 12 — заставки нет (`0x0006FA88`) |

Пункта меню для него нет — ни пользовательского, ни сервисного: других записей этого
бита в образе просто не существует.

Сама команда в FE2P ничего не пишет: обработчик уходит на общий выход `0x0006FE10`
(`ret; restore`), без вызова `FUN_000E7050`. Но блок длиной `0x1F8` байт, начинающийся
с `0xA802BD74`, целиком сбрасывается в FE2P по смещению 0 в ветке `dc off`
(`0x000224EC`) — то есть настройка переживает штатное выключение вместе со всеми
остальными пользовательскими.

**Осторожно с соседями по опкоду.** У подкоманды `0xA7` есть ещё ветки `param[6]=3`
(контур ACE) и `param[6]=0x13` (середина кривой яркости, пишет FE2P немедленно и затирает
поля, которые не восстанавливает даже сброс настроек), а подкоманда `0xA2` с `param[6]=0`
включает заводской прогон. Ошибка в байте попадает в них — карта команд в
`docs/ddcci.md`.

### Ускоряет ли отсутствие логотипа включение

Да, и не косвенно. В диспетчере состояний питания стоит:

```c
if ((DAT_a8029aa1 & 1) != 0) {     // логотип сейчас на экране
    if (FUN_000264e4(3) == 0) {    // слот 3 истёк
        FUN_0002e430();            // снять логотип
        DAT_a8029aa1 &= 0xfe;
    }
    goto LAB_00025624;             // безусловно в общий хвост
}
```

Бит 0 слова `0xA8029AA1` ставится ровно там же, где рисуется логотип, и снимается только
по истечении слота 3. Пока он стоит, **весь остальной диспетчер пропускается
безусловно** — и опрос источника, и включение панели. То есть 3000 мс это не «пока
монитор и так грузится», а жёсткий пол: раньше картинки не будет.

Плюс сама отрисовка: 18 765 байт тайлов и 5 904 байта ячеек — около 24 700 однобайтовых
записей в порт OSD, каждая с холостым циклом на ~160 итераций. В секунды без частоты
ядра это не переводится, но заметно меньше трёх секунд.

Чего по коду сказать нельзя — сколько занимает остальной старт: обучение линка,
определение режима. Если он и так длиннее 3 с, выигрыш окажется меньше номинала.
Меряется секундомером.

### Три способа не показывать логотип

1. **Сбросить бит 12 по DDC/CI** — `0xE1` / `0xA7` / `6` / `0`. Перепрошивки не требует
   вообще: это штатный путь, который вендор просто не вывел в меню.
2. **Заводской режим** (бит 14) — удержание нажатия джойстика при холодном старте
   (`docs/buttons.md`). Заставку убирает, но меняет и остальное поведение, включая
   префикс «F» в заголовке OSD.
3. **Режим `PRODUCT`** (`0xA802BD6E = 0x55AA`) — заставку убирает, но включает заводской
   прогон с заливкой экрана цветом (`docs/burn-in-mode.md`). Как способ ускорить
   включение бессмыслен.

Правкой образа можно вместо этого укоротить саму выдержку — две константы `mov 0xbb8`,
файловые смещения `0x0012A430` и `0x0012A588`. Это дороже: требует шагов 9, 20 и 21 плана.

## Слот 3 — выдержка показа логотипа

`0x00021D10` — это `APPSTATE_PWR_ON` (имя от автоименования по отладочным строкам,
`docs/firmware-map.md`). Логотип он не рисует, а запускает: рисованием занята
`ShowLogo` — `0x0002E028`, тоже именованная по строке.

В двух ветках `APPSTATE_PWR_ON` (`case 0`, ветка `dc on`, и `case 2`) стоит один и тот же
блок, под условием `(0xA802BD74 & 0x5000) == 0x1000 && 0xA802BD6E != 0x55AA`:

```c
FUN_0007bd68(s_show_logo__d, 1);   // отладочный printf
ShowLogo();                        // 0x0002E028
FUN_0002df4c(0xff, 1);
FUN_0002df4c(0x40, 0);
DAT_a8029aa1 |= 1;
thunk_FUN_000d9254();
FUN_00026458(3, 3000);             // взвод слота 3
```

Читается слот в диспетчере состояний питания `0x00025480`, по адресу `0x000256DC`, тем же
шаблоном, что и слот 11 (`docs/input-switching.md`): пока остаток не ноль — управление
уходит в общий хвост `0x25624` и ветка не выполняется. По истечении:

```asm
000256dc  call 0x264e4
000256e0  mov  3, %o0          ; остаток слота 3
000256e4  sll  %o0, 0x10, %l3
000256e8  cmp  %l3, 0
000256ec  bne  0x25624         ; не истёк -> ветка пропускается
000256f4  call 0x2e430         ; истёк -> снять логотип
000256fc  mov  0xff, %o0
00025700  call 0x2df4c
00025704  mov  0, %o1          ; FUN_0002df4c(0xFF, 0) — обратное взводу
```

`0x0002E430` — снятие логотипа, зеркало вызовов из `ShowLogo`: гасит панель,
вызывает `FUN_000E202C(0,0,0,0,**0**)` там, где `ShowLogo` вызывала её же с `1`, и сбрасывает
бит `0x1000` в `0xA802BAE0`, который взводится в `APPSTATE_PWR_ON` перед показом.

Итого **слот 3 — это время, которое логотип висит на экране: 3000 мс.** Константа
закодирована как `mov 0xbb8, %o1` и лежит в образе в двух местах:

| Взвод | Файловое смещение константы |
|---|---|
| `0x0002242C` (`case 0`, `dc on`) | `0x0012A430` |
| `0x00022584` (`case 2`) | `0x0012A588` |

Слот 3 больше нигде не взводится и нигде больше не читается, так что правка этих двух слов
меняет только длительность заставки. Как и во всём таймерном массиве, «миллисекунда» —
вывод из сравнений вида `1000 <`, а не проверенный факт.

## Логотип — не картинка в флеше, а экран OSD

Искать в образе готовый растр бесполезно: его там нет. `ShowLogo` открывает **два окна
OSD**, заливает в память OSD собственный набор тайлов и заполняет окна номерами тайлов.

| Окно | Сетка | Позиция (`FUN_000E2558`) | Что на нём |
|---|---|---|---|
| 0 | 93 × 18 тайлов = 1116 × 324 px | `0xB4`, `0x95` | `msi`, `MPG`, `MSI PERFORMANCE GAMING` |
| 1 | 42 × 7 тайлов = 504 × 126 px | `0xCC`, `0x4A0` | HDMI (и затёртый AMD FreeSync) |

Тайл — **12 × 18 пикселей**. Единицы позиции не установлены: по горизонтали `0xB4` = 180
для окна шириной 1116 px на панели 3440 px — это явно не пиксели.

### Значок AMD FreeSync есть в тайлах, но на экран не выводится

Заполнив окно 1, `ShowLogo` проходит по нему **второй раз** и записывает тайл 0 в
столбцы `0…0x10` всех семи строк — константа `mov 0, %o4` на `0x0002E378`. Это ровно та
часть окна, где лежит значок `AMD FreeSync Premium Pro`, так что на экране остаётся один
`HDMI`. Тайлы значка при этом никуда не деваются и извлекаются:

Фотография заставки это подтверждает: слева от `HDMI` пусто даже при поднятой яркости
снимка. Почему значок оставили в данных и гасят при отрисовке — не установлено.

Коды тайлов в картах идут почти подряд (0, 1, 2, 3 …) с редкими повторами: набор тайлов
собран под конкретный логотип и дедуплицирован, отсюда и экономия. Это не шрифт OSD —
меню пользуется другим набором.

### Как это выглядит в коде

```c
FUN_000e21e8(R+0x70, 0);        // палитра окна 0 (без сжатия)
FUN_00053a70(0x5d, 0x12, 0);    // открыть окно 0, 93 x 18
FUN_000e23ac(0, 93*18+1,        0);   // база банка 0xA0 в памяти OSD
FUN_000e23ac(1, 93*18+1+0x678,  0);   // база банка 0xB0
FUN_000e221c(1, R+0xCC, 0);     // залить банк 0xA0 — 1 bpp, RLE
FUN_000e221c(1, R+0xC0, 0);     // залить банк 0xB0 — 2 bpp, RLE
for (i = 0; i < 0x68a; i++)     // 1674 = 93 * 18 ячеек
    FUN_000e24a8(1, code[i], (attr[i] << 8) | (i <= 0x3a2 ? 8 : 0), 0);
```

`FUN_000E24A8` пишет в порт OSD **три байта на ячейку**: код тайла, управляющий байт
и байт атрибута. Смещение `0x678` = 1656 = 184 × 9: адрес памяти OSD считается
трёхбайтовыми словами, 27 байт тайла = 9 слов.

### Где что лежит

Адреса массивов и дескрипторов заливки в двух образах разные, поэтому здесь — FW.037:

| Что | Адрес (FW.037) | Размер |
|---|---|---|
| карта тайлов окна 0 | `0x000FF098` | 1674 × u16 |
| массив атрибутов окна 0 | `0x00100B98` | 1674 × u8 |
| банк 1 bpp окна 0 | `0x00108548` | 3623 B RLE → 4968 B = 184 тайла |
| банк 2 bpp окна 0 | `0x00107940` | 3074 B RLE → 9612 B = 178 тайлов |
| палитра окна 0 | `0x000FD8B8` | 30 B |
| карта тайлов окна 1 | `0x000FC25C` | 294 × u16 |
| банк 1 bpp окна 1 | `0x000FCE38` | 2687 B RLE → 4185 B = 155 тайлов |
| палитра окна 1 | `0x000FC258` | 4 B |

Дескрипторы заливки лежат не в коде, а в блоке инициализированных данных, который
копируется в RAM: FW.037 — файл `0x000EC000` → `0xA8024000`, FW.034 — файл `0x000EBFF4`
→ `0xA8023FF4`. **Базовый адрес в RAM у разных образов разный**, на это стоило потратить
время: сначала он был принят за константу.

## Формат тайлов

Два банка, оба заливаются одним и тем же RLE:

- **1 bpp**, 27 байт на тайл;
- **2 bpp**, 54 байта на тайл — это **два плана по 27 байт**, а не чередование по 2 бита
  на пиксель. Упакованный вариант даёт мусор, планарный — чистую картинку.

### Память OSD 24-битная и little-endian

Тайл 12 × 18 — это 216 бит, то есть **девять 24-битных слов по две строки в каждом**.
Что единица адресации именно 24 бита, видно из кода независимо: разрыв `0x678` между
базами двух банков (`0x0002E0F4`) — это 1656 = 184 тайла × 9, а 27 байт тайла = 9 единиц.

Слово собирается из трёх байт потока **младшим байтом вперёд**, а **верхняя строка лежит
в младших двенадцати битах**:

```c
w = b0 | b1 << 8 | b2 << 16;
верхняя строка = w & 0xFFF;      // слева направо, старший бит — левый пиксель
нижняя строка  = w >> 12;
```

Обе половины этого правила легко переврать, и каждая даёт свой характерный дефект:

| Ошибка | Как выглядит |
|---|---|
| порядок байт в слове | каждая вторая строка съезжает на полбайта — грубая «гребёнка», глиф на грани узнаваемости |
| порядок строк в слове | строки переставлены попарно — на диагоналях мелкие зубцы, всё остальное выглядит правильно |

Заметить это по одним данным трудно: суммарный объём сходится, число тайлов совпадает с
числом различных кодов, логотип узнаётся. Оба раза ошибку находил владелец, сравнивая PNG
с экраном; второй дефект — тот, который «почти не видно», — ловится численно: у чистой
диагонали левая граница по строкам монотонна, и достаточно посчитать, сколько раз она
идёт назад. При верной раскладке — ноль, при переставленных строках — заметная величина.

Проверка сходится точно: 4968 / 27 = 184 тайла при 184 различных кодах в ячейках
с `attr = 3`; 9612 / 54 = 178 при 178 различных кодах в ячейках с `attr = 0`;
4185 / 27 = 155 при 155 кодах в окне 1.

**Второй банк — не 2 bpp, а два независимых однобитных слоя.** Индекс 3 (оба плана
установлены) не встречается ни разу на 38 448 пикселей. Первый план (байты 0…26) несёт
`msi` и даёт индекс 1, второй (байты 27…53) несёт `MPG` и даёт индекс 2; разделены они
ровно затем, чтобы получить разный цвет. Никакого сглаживания в логотипе нет, все края
жёсткие.

Логотип `MPG` при этом разрезан между банками по строке 10 сетки: верх — в двухслойном
банке, низ — в однобитном. Обе половины выходят одного цвета, но не потому, что
однобитный банк белый, а потому что у него другой атрибут — см. ниже про палитру.

### RLE

`FUN_000B8C54`, ветка сжатия. Кодируются только серии байтов `0x00` и `0xFF`:

```
v = src[p]
if v == 0x00 or v == 0xFF:  повторить v столько раз, сколько в src[p+1]
                            (0 означает 256);  p += 2
else:                       выдать v один раз; p += 1
```

Та же функция умеет и без сжатия (`param_1 == 0`), но `ShowLogo` пользуется только сжатой
веткой. Палитры заливаются другой функцией — `FUN_000B7C18`, всегда без сжатия.

## Палитра

Байты палитр в образе:

```
окно 0 (0x000FD8B8, 30 B):
  00 00 ff ff 0f e9 00 00 0f e9   00 00 ff ff e0 ff 00 00 e0 ff   00 00 ff ff 94 ee 00 00 94 ee
окно 1 (0x000FC258,  4 B):
  00 00 ff ff
```

Записи **двухбайтные**: у окна 1 однобитный банк и ровно четыре байта палитры, а его
значки на экране белые — значит `0x0000` фон, `0xFFFF` белый.

**Индекс в палитру — это байт атрибута плюс номер цвета пикселя.** Атрибут, стало быть,
не цвет сам по себе, а база в таблице. Отсюда всё сходится:

| Что | attr | пиксель | запись | цвет |
|---|---|---|---|---|
| фон окна 0 | 0 | 0 | 0 = `0x0000` | чёрный |
| `msi` | 0 | 1 | 1 = `0xFFFF` | **белый** |
| `MPG`, верх | 0 | 2 | 2 = `0x0FE9` | **малиновый** |
| фон, строки 10…17 | 3 | 0 | 3 = `0x0000` | чёрный |
| `MPG` низ и подпись | 3 | 1 | 4 = `0x0FE9` | **малиновый** |
| значки окна 1 | 0 | 1 | 1 = `0xFFFF` | белый |

Записи 0 и 3 обе нулевые — потому фон и остаётся чёрным при обоих атрибутах. Тридцать
байт делятся на **три группы по пять записей** одинакового строения
`(0x0000, 0xFFFF, C, 0x0000, C)`, различающиеся акцентным цветом `C`: `0x0FE9`, `0xE0FF`,
`0x94EE`. Заставка пользуется первой группой; две другие — видимо, темы для других
моделей.

### Кодировка: обычный RGB565, читаемый little-endian

Записи читаются **младшим байтом вперёд** — той же конвенцией, по которой собираются
24-битные слова тайлов. Значит байты `0f e9` в образе это значение `0xE90F`, и дальше
это простой RGB565:

```
0xE90F = 11101 001000 01111  ->  R=29/31, G=8/63, B=15/31  ->  #EE207B
```

Ярко-малиновый — то, что и видно на экране. Заодно осмысленными становятся и два других
акцентных цвета, чего не было ни при одном прочтении big-endian:

| Запись в файле | Значение | Цвет |
|---|---|---|
| `0f e9` | `0xE90F` | `#EE207B` малиновый — им нарисован `MPG` |
| `e0 ff` | `0xFFE0` | `#FFFF00` жёлтый |
| `94 ee` | `0xEE94` | `#EED2A4` песочный |

`0x0000` даёт чёрный, `0xFFFF` — белый при любом порядке байт, так что фон и `msi`
проверку порядка не проходят — различает его только акцентный цвет.

### Почему PNG всё равно не будет выглядеть точно как экран

`0xE90F` — это **аппаратное значение** для панели, а не цвет в sRGB. Скалер отдаёт его
матрице как есть, а матрица здесь QD-OLED с охватом заметно шире sRGB, так что живой
малиновый насыщеннее, чем `#EE207B` в sRGB вообще может быть. Никакой sRGB-файл этого не
повторит — расхождение не в разборе, а в разнице охватов.

Чтобы хотя бы убрать неоднозначность, `tools/logo.py` помечает файлы чанком `sRGB`
(плюс `gAMA` и `cHRM` для декодеров, которые про него не знают). Без пометки одни
просмотрщики считают данные sRGB, другие отдают их на панель напрямую как есть — и на
широкоохватном мониторе эти два прочтения выглядят по-разному.

Сами пиксели в файле — ровно три цвета: `#000000`, `#EE207B`, `#FFFFFF`, без полутонов
и без сглаживания.

**Фотография вопрос о цвете решить не может, и попытка это сделать была ошибкой метода.**
Внутри глифа на снимке пересвечены все три канала: при выбитом в 255 красном зелёный
измеряется как 206, синий как 235. Единственные непересвеченные пиксели лежат в ореоле, а
ореол у светящейся малиновой надписи заметно краснее самой надписи, потому что тянется в
основном по самому сильному каналу. Измерения по ореолу дали `B/R` 0.26…0.33 и увели
разбор в раскладку, дающую `#FF084A`, — заметно более красный цвет, чем на самом деле.
Снимок надёжно свидетельствует о форме и о том, какой элемент белый, а какой цветной; о
точном значении цвета — нет.

## Извлечение

```bash
.venv/bin/python tools/logo.py FW.bin -o out/logo
```

Скрипт ничего не берёт из этого документа: блок дескрипторов он находит по форме
(два 12-байтных дескриптора заливки на `+0xC0`/`+0xCC` и так далее), а `ShowLogo` — по
тому, что она единственная обращается к пяти дескрипторам этого блока подряд; адреса карт
и массива атрибутов вынимает из её собственного кода, прослеживая регистры через
`sethi`/`or`. Захардкожена только геометрия окон.

Результат — `logo_msi.png` (1116 × 324), `logo_badges.png` (504 × 126, как рисуется) и
`logo_badges_hidden.png` (то же окно без затирания, со значком AMD FreeSync).

## Проверки

- **Сверено с фотографией заставки живого монитора** (`photo/start_logo.jpeg`) и с самим
  монитором. Совпало: форма всех трёх элементов окна 0, белый `msi`, малиновые `MPG` и
  подпись, белый `HDMI`, отсутствие значка AMD FreeSync, отсутствие зубцов на диагоналях.
  Точное значение цвета снимком не проверяется — он пересвечен, см. раздел про палитру.
- **Мелкий текст читается.** Под значком `HDMI` в тайлах лежит строка
  `HIGH-DEFINITION MULTIMEDIA INTERFACE` высотой в несколько пикселей. Пока раскладка бит
  была неверна, она оставалась нечитаемым пятном. Это самая чувствительная проверка
  правильности разбора тайлов из имеющихся.
- **Левая граница диагоналей монотонна.** У `msi` наклонные штрихи идут ровной лесенкой;
  счётчик «сколько раз левый край уходит назад» даёт ноль при верной раскладке слова и
  ненулевую величину при переставленных строках. Это ловит тот дефект, который глазом на
  PNG почти не виден.
- **Оба образа дают побайтово одинаковые PNG**, хотя в FW.034 и FW.037 различаются все
  адреса без исключения: блок дескрипторов, карты, массив атрибутов, банки тайлов.
  Это независимая проверка и разбора, и скрипта.
- Число тайлов в каждом банке точно совпадает с числом различных кодов, которые на него
  ссылаются (184 / 178 / 155) — то есть и длина RLE, и размер тайла разобраны верно.
- Индекс 3 не встречается ни разу, что согласуется с палитрой, где четвёртая запись — ноль.

## Поправка: порядок планов был выведен неверно

В первой редакции этого разбора порядок планов в двухслойном банке был **перевёрнут**, и
рассуждение стоит записать, потому что ошибка была тонкая. Довод был такой: `MPG` разрезан
между банками, обе половины обязаны быть одного цвета, однобитный банк — это индекс 1,
значит `MPG` тоже индекс 1, а `msi` — индекс 2.

Первая посылка верна, вторая — нет. Однобитный банк идёт с атрибутом 3, а атрибут
сдвигает базу в палитре, поэтому его индекс 1 попадает не в запись 1 (белую), а в запись
4 — тот же малиновый, что и у `MPG` сверху. Обе половины `MPG` одного цвета, но не
белого. Фотография показала обратное распределение: `msi` белый, `MPG` малиновый.

Тот случай, когда вывод из наблюдаемой непрерывности выглядел железным, а на деле опирался
на непроверенное «однобитный банк = белый».

## Что не доказано

- **Чем именно выбирается банк** — байтом атрибута (`0` или `3`) или битом 3 управляющего
  байта. Они расходятся ровно на одной ячейке из 1674 (индекс 930), и код тайла в ней — 0,
  то есть пустой, так что различить их по картинке нельзя. Скрипт использует атрибут.
  К палитре это отношения не имеет: индекс в неё даёт именно атрибут.
- **Единицы координат окна** в `FUN_000E2558`.
- **Зачем в тайлах оставлен значок AMD FreeSync**, который отрисовка гасит.

## Побочная находка: неиспользуемые данные рядом

Между разобранными массивами лежат ещё два, на которые в Leon2 Main **нет ни одной ссылки**
(проверено `RefsTo.java` в Ghidra, не только своим сканером):

| Адрес | Размер | Что похоже |
|---|---|---|
| `0x000FD8D6` … `0x000FF098` | 6082 B | карта u16 с последовательными кодами, 201 различный код |
| `0x000FFDAC` … `0x00100B98` | 3564 B | байтовый массив, значения 0, 1, 2, 4, 5, 8, 10, 13 |

Похоже на остаток от сборки ассетов вендором — ещё один экран заставки, который в этой
прошивке не вызывается. Не разбиралось.
