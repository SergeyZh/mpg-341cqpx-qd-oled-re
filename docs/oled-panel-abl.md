# Команды панели OLED и контур ABL

## 1. Протокол «скалер → T-CON панели» (Leon2 Main)

Панель `SDC QMC340CA01_D01` управляется по I2C из Leon2 Main. Каждая настройка — своя
функция; все они построены по одному шаблону. Адреса функций и DRAM в этом разделе
по умолчанию относятся к **FW.037**, как и остальные reference-адреса репозитория.
Отдельный точный контракт и адреса FW.034 для собственной базовой яркости приведены
в leon2-main-panel-luminance.md (не опубликовано).

```c
buf[0] = value >> 8;                            // big-endian16
buf[1] = value;
I2C_Write(0x60, 2, REG, 5, 0, buf, 2, 1);       // запись
delay(0x32);                                     // 51 countdown events
I2C_Read (0x60, 2, REG, 5, 0, rbuf, 2);         // чтение обратно
// сверка двух bytes; retries ограничены общим счётчиком
```

- `0x60` — write byte на проводе; семибитный адрес панели равен `0x30`, read byte —
  `0x61`;
- `2` — ширина адреса регистра в байтах (регистры бывают >0xFF, см. таблицу);
- `REG` — регистр команды;
- `5` — timing/half-period field, а channel/select равен `0`; panel calls используют
  bus 0;
- полезная нагрузка — 2 байта big-endian; старший byte не обязан быть нулём
  (`gain=0x03FF` — допустимый пример).

Обёртки: запись `0x000E3BC0`, чтение `0x000E3C08`, задержка `0xA002CFA4`
(FW.037). Последняя находится в retained runtime **Leon2 Main**, не Leon2 Sub.
Аргумент `0x32` означает 51 внешний countdown event; физическая единица времени
из этого вызова не следует.

**Существенная деталь:** запись всегда верифицируется обратным чтением и повторяется
при расхождении, пока общий счётчик допускает retry. В FW.037 этот счётчик находится
по `0xA802B4E0`; соответствующий адрес FW.034 — `0xA802B4D0`. Initial attempt плюс
десять retries получается только при исходном значении счётчика `0`; при ненулевом
значении остаётся меньше попыток. Прошивка предусматривает несовпадение readback, но
одно несовпадение само по себе не доказывает, что именно панель отвергла команду.

### Таблица команд

| REG | Команда | Функция Main FW.037 |
|---|---|---|
| 0x008 | Temp Sensing (только чтение) | 0x000C2D4C |
| 0x01E | **Luminance mode** | 0x000C283C |
| 0x05E | **Lum Gain** — 16-битная яркость панели | 0x000C2660 |
| 0x060 | Screen Saver Range | 0x000C30CC |
| 0x070 | Pixel Shift On/Off | 0x000C2DE4 |
| 0x072 | Pixel Shift Speed | 0x000C2F58 |
| 0x0B2 | Frame Rate Control | 0x000C2A04 |
| 0x0C0 | **OFF Sensing** | 0x000C2BCC |
| 0x0C2 | **EL Sensing** | 0x000C2C38 |
| 0x1B2 | MultiLogo | 0x000C35B4 |
| 0x1B4 | Pillar Box | 0x000C32CC |
| 0x1B6 | Task Bar | 0x000C3440 |
| 0x1C6 | Inspection Mode | 0x000C3728 |
| 0x1C8 | Inspection Pattern | 0x000C389C |

Буферы FW.037 в DRAM: запись `0xA802C370` (2 байта), чтение `0xA802C368`
(2 байта).

**Регистр `0x05E` (Lum Gain) в прежней таблице отсутствовал**, а он ключевой: именно
через него скалер задаёт яркость панели. Отладочная строка — `OLED set Lum Gain %d,(%02x,%02x)`
(`0x15DB78`). Входной byte-процент `p`, уже рассчитанный предыдущей кривой,
переводится в gain функцией `SetBrightness` (`0x000E80FC`) линейно:

```
значение = (яркость * 0x381 + 50) / 100 + 0x7E      // основной режим
значение = (яркость * 0x25F + 50) / 100 + 0x7E      // второй режим
значение = (яркость * (поле_0xA802CCF6 - 0x7E) + 50) / 100 + 0x7E
```

То есть шкала панели идёт от `0x7E` (нижняя граница) до `0x3FF` в основном режиме.

**Подтверждено живым железом 2026-08-15** (`docs/boot-sequence.md`): Leon2 Main печатает
`SetBrightness 234` в рабочем режиме и `SetBrightness 1023` на время показа логотипа.
`1023 = 0x3FF` — верхняя граница normal arithmetic, а `234` лежит внутри её диапазона.
Эти строки не устанавливают исходный пользовательский byte и не доказывают реакцию
ABL в этот момент. Путь заставки отдельно описан в `docs/logo.md`.
Подробнее о том, кто ещё пишет в этот регистр, — в `docs/panel-protect.md`.

`0x01E` — режим яркости панели, ближайший аналог «ABL-профиля» на стороне T-CON.
`0x0C0`/`0x0C2` — циклы компенсации (OFF-sensing при выключении, EL-sensing).
Регистры 0x008, 0x0C0, 0x0C2 участвуют в последовательности выключения питания
(функция `0x000C3CE4`), где температура выше 45 °C переводит панель в DC off.

### Контроллер панели: своя прошивка есть, из скалера она не обновляется

У панели есть собственный контроллер (T-CON, в отладочных строках — FRC), и это не
просто набор регистров. Свидетельства, все из образа:

- **Он загружается по стадиям.** Строки `OLED_FRC_DVDD_ON` → `OLED_FRC_FRC_READY` →
  `OLED_FRC_IIC_READY` (`0x2665C9`–`0x266609`): сначала питание, потом готовность
  контроллера, и только потом доступен его I2C. Регистровому файлу такая
  последовательность не нужна.
  **Снято на живом железе 2026-08-15** (`docs/boot-sequence.md`), с таймингами: между
  `OLED_FRC_DVDD_ON` и `OLED_FRC_FRC_READY` проходит **0,5 с**, дальше
  `OLED_FRC_Handler 1`, `OLED set Frame rate control 1`,
  `OLED Get Frame rate control 0 1` и через 56 мс `OLED_FRC_IIC_READY`. Полсекунды на
  готовность контроллера — это уже не похоже на регистровый файл окончательно.
- **Он исполняет длинные автономные процедуры.** Циклы компенсации по командам `0x0C0`
  и `0x0C2` идут минутами и завершаются сигналом на отдельной линии
  (см. `docs/panel-protect.md`).
- **Он ведёт детекцию содержимого сам** — логотип, панель задач, границы, статика.
- **Прошивка предусматривает несовпавший readback**: каждая запись сверяется
  обратным чтением и при доступном общем budget повторяется. Причина конкретного
  несовпадения из одного readback не определяется.

**Пути обновления этого контроллера в образе нет.** Проверено: все 28 обращений на
запись к панели — это двухбайтовые записи в регистр из замкнутого набора обёрток
`0x000C26xx`–`0x000C39xx` и автомата `0x000C3CE4`; буфер записи один и тот же, на два
байта (`0xA802C370`). Ни объёмной передачи, ни цикла загрузки, ни блока данных для
панели. Строк вида download/upgrade/update применительно к панели тоже нет, и среди
девяти разделов флеша (`docs/firmware-map.md`) нет раздела с прошивкой панели.

Различать надо аккуратно: установлено, что **скалер не умеет обновлять контроллер
панели**. Из этого не следует, что тот неперепрошиваем в принципе — у него может быть
заводской путь по своей шине, или его код может быть в масочном ПЗУ. Из образа скалера
этот вопрос не решается.

Практическое следствие: обновление прошивки монитора инструментом MSI меняет только
скалер. Всё, что живёт в панели — алгоритм компенсации, детекторы, реакция на статику —
обновлением не затрагивается.

Побочно: «ревизия панели», которую показывает сервисное меню, приходит **не от панели**.
`0x000774E4` читает её с канала 6 АЦП (`0x0007A6A8`), то есть это резисторная кодировка
на разъёме. Версии прошивки контроллера панели в интерфейсе нет нигде.

## 2. Контур ABL/LDC — образ Tensilica

**Исправление к прежней документации:** раздел id=0x03 (файл 0x30000–0x3D900) — это
**не 8051**, а прошивка **Tensilica Xtensa, little-endian**. Проверено импортом:
`Xtensa:LE` декодирует 13 885 инструкций, `Xtensa:BE` — 103. Плотность 8051-опкодов
здесь в 20 раз ниже, чем в настоящих 8051-разделах.

Раскладка раздела: код 0x30000–0x3ACF8, дальше и до конца раздела (0x3D8DC) — образы
секций данных, которые старт копирует в DRAM. База образа — **0x40000000**, данные
адресуются уже по DRAM; разбор в `docs/tensilica.md`.

У образа своя отладочная консоль, независимая от 8051 и Leon2:
`NT68500 Tensilica S/W`, `Welcome to User's Command Line Debug`, команды
`mem`, `wmem`, `mdw`, `proc`, `gpio`.

### Параметры ABL

Функция дампа печатает параметры в этом порядке — он же отражает структуру блока:

```
LDC_Mode              ZonePeakingPercent
usUserPDIM            UserGlobalGain
usUserADIM            ApplyGlobalGain
ADIM_Max              GainFilterMode
ADIM_Min              Input Duty:
ADIM_BrighPercent     Merged Segment:
PercentADIM           LED ADIM:
LimitUpperBound       LED PDIM:
```

Какие из этих параметров вообще имеет смысл трогать, а какие нет — разобрано
в `docs/external-research.md`: `LimitUpperBound` и связка `ADIM` относятся к ABL,
то есть к бюджету мощности панели, и не поддаются отключению в принципе; а вот
`Screen Saver Range`, `MultiLogo`, `Pillar Box` и `Task Bar` — это семейство
ASBL/GSR, которое настраивается штатно.

Смысл в терминах OLED (на LCD те же поля управляли бы подсветкой):

- **ADIM** — «автоматическое» затемнение, вычисляемое из содержимого кадра.
  `ADIM_Max`/`ADIM_Min` задают коридор, `ADIM_BrighPercent` и `PercentADIM` — доли.
- **PDIM** — «панельное»/пользовательское затемнение, `usUserPDIM` — заданное с OSD.
- **LimitUpperBound** — верхняя граница, куда упирается результат. Ключевой параметр
  ограничения яркости.
- **ZonePeakingPercent** — насколько ярче среднего разрешено светить локальной зоне
  (эффект peak brightness на малой площади).
- **UserGlobalGain / ApplyGlobalGain** — заданное и фактически применённое усиление.
  Расхождение между ними и есть работа ограничителя.
- **GainFilterMode** — сглаживание по времени; вероятный источник мерцания при резких
  переходах.
- Режимы слияния сегментов: `Maximum`, `Average`, `Average exclude black`, `Blend`.
- `Current Stress Staus = %d (Peaking ON/OFF)` — состояние «нагрузки» панели,
  переключающее peaking.
- `LDC_GainTable_ANV1..3` — три таблицы коэффициентов усиления.

### Адреса параметров

База установлена, и параметры нашлись. Все они лежат одной структурой в `.data`,
базовый адрес — **`0x3FFE2390`** (файл 0x3D088). Найдено по функции дампа
`0x40003190`, которая печатает каждое поле рядом с его именем; смещения взяты прямо
из её кода. Значения ниже — те, что лежат **в образе**, то есть значения по
умолчанию до того, как их перезапишет конфигурация панели.

| Адрес | Смещ. | Параметр | Значение в образе |
|---|---|---|---|
| `0x3FFE2390` | +0x00 | число сегментов (`LED_row × LED_col`) | 32 |
| `0x3FFE2394` | +0x04 | `GainFilterMode` | 6 |
| `0x3FFE2398` | +0x08 | `ADIM_Min` | 0x0040 (64) |
| `0x3FFE239C` | +0x0C | `ADIM_Max` | 0x03FF (1023) |
| `0x3FFE23A0` | +0x10 | `usUserPDIM` | 0x0FFF (4095) |
| `0x3FFE23A4` | +0x14 | `PercentADIM` | 0x0200 (512) |
| `0x3FFE23A8` | +0x18 | `usUserADIM` | 0x0200 (512) |
| `0x3FFE23AC` | +0x1C | `ADIM_BrighPercent` | 0x03FF (1023) |
| `0x3FFE23B0` | +0x20 | `UserGlobalGain` | 0x0400 (1024) |
| `0x3FFE23CC` | +0x3C | флаг стресса (ставится в 1 при Peaking OFF) | 1 |
| `0x3FFE23D0` | +0x40 | **`LimitUpperBound`** | 0x00FF (255) |
| `0x3FFE23D4` | +0x44 | `ZonePeakingPercent` | 0x0078 (120) |
| `0x3FFE23D8` | +0x48 | `ApplyGlobalGain` | 0x0400 (1024) |

Поля панели (`Resolution`, `DriverDuty`, `LEDRowCol`, `DriverType`, `LED_Mode` на +0x140,
`LDC_Mode` на +0x144) лежат во второй структуре с базой `0x3FFE2BF0` — она в `.bss`,
в образе её содержимого нет, заполняется на старте из регистров.

### Значения сняты с живого монитора и совпали с образом

**2026-08-15, командой `msg1` в консоли Tensilica** (`docs/console-commands.md`,
`captures/tensilica-msg1-ldc-dump.log`). Она включает **периодический дамп этого самого
блока** — тот, что печатает функция `0x40003190`. Монитор был без сигнала, панель не
светилась.

| Печатает консоль | Значение | Соответствует полю |
|---|---|---|
| `LED ADIM:` ×16 | `0200` | `usUserADIM` / `PercentADIM` = 0x0200 |
| `LED PDIM:` ×16 | `0FFF` | `usUserPDIM` = 0x0FFF |
| `ApplyGlobalGain:` | `0x0400` | `ApplyGlobalGain` = 0x0400 |
| `Input Duty:` | две строки по 16, все нули | число сегментов = 32 |
| `Pure Pattern:` | `0` | — |

**Совпадение полное.** Это первое подтверждение разбора ABL живым железом: до сих пор
значения были вычитаны из образа и считались «значениями по умолчанию до того, как их
перезапишет конфигурация панели» — теперь видно, что на работающем мониторе они те же.

Два наблюдения из дампа:

- **`Input Duty` печатается двумя строками по 16, то есть 32 значения** — согласуется с
  «число сегментов = 32» из таблицы выше и **расходится** с `LEDRowCol: 01 x 16 : 16`,
  который Tensilica печатает при старте (`docs/boot-sequence.md`). При этом `LED ADIM` и
  `LED PDIM` печатаются по 16. Что из этого геометрия зон, а что размер массива, не
  разобрано.
- **`Merged Segment` содержит указатели, а не яркости:** `4000A97C`, `40000824` (код
  Tensilica), `3FFEEFD0` (DRAM), маркер `11223344`, `FFFFFFFF`. Одно значение меняется
  между итерациями (`C000A307` → `C000A348`), пара `C000xxxx`/`4000xxxx` отличается
  старшим битом — похоже на адрес с флагом. Подпись строки и её содержимое, судя по
  всему, не соответствуют друг другу.

### Как этим измерить передаточную функцию

`Input Duty` — вход контура (заполнение по сегментам), `LED ADIM`/`LED PDIM` — то, что
контур выдаёт на драйвер. Сейчас вход нулевой, потому что нет сигнала. **Подать
картинку — и дамп начнёт показывать обе стороны контура одновременно**, а меняя APL
(белое поле, градации серого, оконный паттерн), можно снять зависимость прямо с живого
монитора.

Это и есть открытый вопрос №3 из `README.md` — «передаточная функция APL → яркость не
восстановлена», — и теперь к нему есть инструмент, не требующий ни колориметра, ни
записи в память.

### Таблицы усиления `LDC_GainTable_ANV1..3`

Каждая таблица — пять пар `(входная яркость 0…255, коэффициент)`, коэффициент в
формате с 1024 = ×1.0 (подтверждается плоской «выключенной» таблицей).

| Таблица | Адрес | Точки |
|---|---|---|
| `ANV1` | `0x3FFE23E0` | (0, ×2.000) (64, ×1.579) (128, ×1.199) (200, ×1.000) (255, ×1.000) |
| `ANV2` | `0x3FFE2420` | (0, ×1.800) (64, ×1.500) (128, ×1.199) (224, ×1.000) (255, ×1.000) |
| `ANV3` | `0x3FFE2450` | (0, ×2.195) (64, ×1.579) (128, ×1.318) (224, ×1.000) (255, ×1.000) |
| плоская | `0x3FFE2410` | (0, ×1.000) (255, ×1.000) — две точки, усиления нет |

Форма кривой — это и есть peaking: тёмному кадру разрешено усиление до ×2.2, к
яркому оно спадает ровно к единице. В железо таблицу загружает
`DRV_LDC_Intensity_Gain_Update(указатель, число точек)` на `0x40006904` — имя её
собственное, функция печатает его при входе.

Выбор таблицы делает `0x40001428` по `LDC_Mode`: режим 3 — `ANV1` и
`GainFilterMode = 4`; режимы 1 и 2 — плоская таблица и `GainFilterMode = 0`;
режим 4 — `ANV1` и `GainFilterMode = 0`. Отдельная функция `0x40001938` выбирает
`ANV1/ANV2/ANV3` по номеру 1/2/3 — похоже на сервисную. `0x4000165C` переключает
стресс: при `Current Stress Staus = 0 (Peaking OFF)` пишет `LED_Mode = 3`, при
`1 (Peaking ON)` — `LED_Mode = 6`.

### Имена функций

Прошивка Tensilica собрана с той же трассировкой, что и Leon2: функция печатает
своё имя при входе. Отсюда девять **достоверных** имён (`names/tensilica_ldc.csv`,
применяются при импорте):

`DRV_LDC_SetPanelResolution` 0x40006374, `DRV_LDC_UpdateSegmentBoundary` 0x40006434,
`DRV_LDC_SetLDCSegment` 0x4000660C, `DRV_LDC_SetDSRegisters` 0x400066D4,
`DRV_LDC_Intensity_Gain_Update` 0x40006904, `LED_AS3824_SetPwmPeriod` 0x400077A4,
`LED_AS3824_Unlock` 0x40007998, `LED_AS3824_Init` 0x400079B8, `LDC_LoadPanel` 0x40000FB4.

Ещё пять функций разобраны по содержимому, но **имён в прошивке не имеют** и в CSV не
вносились: дамп параметров 0x40003190, установка `LDC_Mode` 0x40001428, выбор таблицы
0x40001938, пересчёт слова состояния 0x400011E4, переключение стресса 0x4000165C.
Отладочный `printf` — 0x400099BC.

`LED_AS3824_*` — драйвер внешней микросхемы подсветки AS3824 (регистры PWM, ток,
DAC, HDR-режим). Задействован ли он на этой OLED-модели — **не установлено**: код в
образе есть, но подсветки у OLED нет, так что это может быть общий код платформы.

**Уточнено 2026-08-15 по UART-консоли Tensilica** (`docs/uart-console.md`): код **не
мёртв — он исполняется при каждом включении** и печатает `DRV_LDC_SetPanelResolution`,
`SetLDCSegment`, `UpdateSegmentBoundary`, `SetDSRegisters` и три регистра
`LED AS3824`. Что микросхема физически есть на шине, это не доказывает — прошивка может
писать в пустоту, — но версия «в этот код не заходят» снята. За платформенный код
говорят две детали: модуль стартует с разрешением `3840,2160` и лишь потом получает
`3440,1440` по почтовому ящику, а все значения нулевые (`Direct PWM: 0x0000`,
`Options: 0x0000`, `CURR CTRL: 0x0080`, `Peaking OFF`).

Расхождение, требующее проверки: консоль печатает `LEDRowCol: 01 x 16 : 16`, то есть
16 зон, а разбор `0x400011E4` ниже усредняет по **32 сегментам**.

### Что вычисляет прошивка, а что железо

Интерполяцию по таблице и само применение усиления делает аппаратура — прошивка
только загружает пять точек. Из вычислений на Tensilica восстановлена функция
`0x400011E4`, она вызывается после каждой смены режима и раз в 60 тактов:

1. складывает массивы `LED_PDIM[]` и `LED_ADIM[]` по всем 32 сегментам и делит на 32;
2. `ADIM% = (avgADIM − ADIM_Min) / (ADIM_Max − ADIM_Min)`, с округлением, в процентах;
   если среднее ниже `ADIM_Min` — ноль;
3. `PDIM% = avgPDIM / 0xFFF` в процентах;
4. произведение `ADIM% × PDIM% / 100`;
5. пакует всё в слово `[31:24] = ADIM%, [23:16] = PDIM%, [15:8] = произведение`,
   бит 0 — признак `LED_Mode ≥ 4`, и пишет его в регистр **`0xE009104C`**.

То есть наружу отдаётся уже посчитанная доля от максимума. Регистровое окно ядра —
`0xE009xxxx`: там же лежат `0xE0091080` (команда отладочной консоли) и `0xE0091084`.

### Чего пока нет

- **Передаточная функция APL → яркость в канделах не восстановлена.** Известны
  коэффициенты и их форма, но не то, во что они превращаются на панели: между
  таблицей и светом стоит аппаратный интерполятор, `LimitUpperBound` и бюджет
  мощности. Проверка колориметром (шаг 15) остаётся единственным способом.
- **Значения живьём не читались.** Адреса известны, но `mdw` требует поднятой
  UART-консоли (открытый вопрос №5), а она пока закрыта.
- Значения в образе — только умолчания. Что реально оказывается в `.data` после
  `LDC_LoadPanel`, зависит от конфигурации панели, которую ядро читает из регистров.
