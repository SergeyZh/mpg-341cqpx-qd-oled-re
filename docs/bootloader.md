# Загрузчик STBC (8051) — полный разбор

Регион `0x000000–0x0018EB` (6 379 байт кода), вектор сброса `LJMP 0x13F7`.
Собран Keil C51: 48 функций, 3 066 инструкций, восемь строк. Байт-в-байт одинаков
в обоих банках флеша и не менялся между FW.023, FW.034 и FW.037.

Воспроизвести:

```
tools/ghidra_import.sh stbc-8051
~/ghidra_12.0.2_PUBLIC/support/analyzeHeadless ghidra nt68503 \
    -process region_000000_001900.bin -noanalysis \
    -scriptPath tools/ghidra_scripts -postScript DumpAsm.java $PWD/out/boot.asm 0x0 0x1900
```

**Читать надо листинг, а не декомпиляцию.** На этом образе декомпилятор 8051 врёт
в самом важном месте: `FUN_CODE_18E8` он показывает пустой функцией `{ return; }`,
тогда как на самом деле это `MOV R7,#0x39; RET` — возврат константы 57 в регистре,
и это число задаёт длину перебора таблицы JEDEC. Приняв декомпиляцию за истину,
получаешь вывод «микросхема не опознаётся», прямо противоречащий живому логу.

## Что вокруг: кодовое пространство — окно во флеш

Загрузчик читает `MOVC` по адресам `0x4000` (таблица JEDEC), `0x6000`/`0x7000`
(таблицы разделов) и `0x7FFF` (маркер слота) — это файловые смещения во флеше.
Значит **CODE-пространство 8051 повторяет начало микросхемы**. На включении база
нулевая и расширенный адрес флеша нулевой, поэтому исполняется то, что лежит с самого
начала.

**Уточнено 2026-09-06: это не сквозное окно, а копия.** Захват шины показал, что
масочный ROM один раз вычитывает **64 КиБ с адреса 0** (`0x0B`, однобитно, 12 МГц) в
кодовую память на кристалле, а дальше, пока 8051 исполняется, **шина молчит**: за все
три промежутка работы ядра в захвате — ноль транзакций, включая тот, где загрузчик
читает `MOVC` таблицу разделов. `docs/spi-boot-trace.md`,
`docs/nt68503-hardware.md` §4.1.

Таблицы векторов прерываний у загрузчика нет: по `0x0003` сразу идёт обычный код,
а `main` первым делом гасит `EA`. Загрузчик не принимает ни одного прерывания.

## Алгоритм

### 1. `0x13F7` — стартап Keil `?C_START`

```
IDATA[0x7F..0x01] = 0
XDATA[0x3000..0x3FFF] = 0          ; сюда потом ляжет общий блок
SP = 0x5A
обработать таблицу инициализации CODE:0x185F
LJMP main (0x151C)
```

### Где находится стек STBC

Стек 8051 не имеет отношения к DDR и XDATA: инструкции `PUSH`, `LCALL`, `RET` и вход
в прерывание используют восьмибитный SFR `SP` и внутреннюю DATA/IDATA ядра. `SP`
указывает на последний занятый байт, поэтому первая запись идёт по `SP + 1`.

Все три исполняемых контекста STBC задают стек явно в Keil startup:

| Контекст | Reset/startup | Команда | Первый байт стека |
|---|---:|---|---:|
| bootloader | `CODE:13F7` | `CODE:140B: MOV SP,#0x5A` | `IDATA:5B` |
| основной `id=0x01` | `CODE:B686` | `CODE:B6A8: MOV SP,#0x6A` | `IDATA:6B` |
| AUX `id=0x02` | `CODE:D426` | `CODE:D42C: MOV SP,#0x61` | `IDATA:62` |

У NT68503 реализована и верхняя IDATA `0x80…0xFF`: startup основного образа и AUX
инициализирует через `MOV @R0,A` внутренние адреса от `0xCB` и `0xCF`. При косвенном
доступе и при работе стека диапазон `0x80…0xFF` означает RAM, тогда как прямые
обращения к тем же номерам означают SFR. Это разные пространства декодирования
одного 8-битного адреса.

Отдельного стека прерываний нет: основной `id=0x01` сохраняет адрес возврата и
регистры обработчиков в тот же стек. Начальные адреса установлены точно; верхняя
фактически допустимая граница для каждого образа пока не вычислена — для этого надо
свести максимальную глубину вызовов, вложенность прерываний и overlay-размещение Keil.
Аппаратный предел `SP` — `0xFF`, после чего он переполняется в `0x00`.

### 2. `0x151C` — `main`

```c
CLR bit0; CLR EA;
FUN_17E2();                       // → XDATA D929 = 4 при D511=20, иначе 6
F0E6 = FUN_18C9() * 4;            // режим шины SPI по варианту чипа
F00A = 0xAA;                      // назначение неизвестно; не доказанный watchdog
F0E0 = 0xAA;                      // выключить watchdog
FUN_1616();                       // UART 4800 8N1
F1A8 |= 2;  F1A8 &= ~1;
print("------STBC Boot Loader -----");
F1DF = 0x80;  FUN_18D6();         // импульс бита 0x40 в F0E5 — сброс FIFO SPI
F152 = 0x40;
FUN_1777();                       // JEDEC ID (0x9F) → F064/F065/F066
FUN_111F();                       // опознать микросхему, включить Quad/Dual
FUN_1899();                       // прочитать таблицу разделов, зарядить железо
if (CY) { print("Can't find valid partition table!!!"); for(;;) F00A=0x55; }
print("Re-booting STBC code...");
F00A = 0x55;
F1D0 = 0x87;                      // ← пуск команды F1D (но не передача управления,
                                  //   см. ниже поправку 2026-09-01)
for(;;) F00A = 0x55;              // штатный цикл ожидания; смысл записи неизвестен
```

**Назначение `F00A` неизвестно.** Прежний вывод «сторожевой таймер» опирался на
частые записи `0x55` и редкие `0xAA`, но измерениями в ISP не подтвердился.
Выключение watchdog — запись `F0E0 = 0xAA`, а не его взвод. Поэтому из одного
цикла `F00A = 0x55` нельзя выводить ни обслуживание watchdog, ни будущий reset.

> **Итог 2026-09-03: `F00A` — не сторож, а сторож это `F0E0`/`F0E2`.** Измерено
> (`captures/watchdog-2026-09-03/`): при `F00A = 0x55` сеанс ISP живёт 60 с, а при
> `F0E0 = 0x55` или `F0E2 = 0x55` монитор перезагружается через 6 секунд. Полярность
> обратная той, что предполагалась: `0x55` взводит и перезапускает отсчёт, `0xAA`
> выключает. **Уточнение 2026-09-13:** reset через шесть секунд ожидается лишь при
> запущенном и не обслуживаемом watchdog. Сам цикл после `F1D0 = 0x87` на
> `CODE:159B` этого не гарантирует: выше загрузчик выключает `F0E0`.
> Ниже сохранено историческое рассуждение до измерений, не текущая карта регистров.
>
> **Оговорка 2026-09-02: трактовка «сторожевой таймер» не доказана, и доводов против
> больше, чем за.** Довод выше — только статистика «`0xAA` редко, `0x55` часто», а она
> одинаково хорошо описывает регистр защиты, который редко отпирают и часто запирают.
> Против:
>
> - во всех трёх местах взвода в `id=0x01` (`CODE:2959`, `CODE:4EED`, `CODE:5156`)
>   значение `0xAA` кладётся в аккумулятор **один раз** и пишется подряд в `F00A`,
>   затем `F0E0`, затем (дважды) `F0E2`, без перезагрузки `A`. В главном цикле то же с
>   `0x55`: `CODE:4F80` пишет `F00A`, `CODE:4F86` — `F0E0`. Это выглядит как семейство
>   регистров защиты, которые правят вместе, а не как сторож рядом с чужим замком SPI;
> - `F0E0`/`F0E2` подписаны как защита SPI-контроллера с тем же магическим `0xAA` на
>   снятие — правда, и эта подпись заимствована из чужого инструмента и опытом
>   2026-09-02 не подтвердилась: с `0x55` чтение флеша работает
>   (`docs/nt68503-i2c-service-protocol.md`). То есть родство трёх регистров по способу
>   употребления остаётся, а вот что они делают — неизвестно ни про один из них;
> - все три читаются **одинаково нулём** на работающем мониторе, который пишет в них
>   `0x55` десятки раз в секунду (`F00A = 00`, `F0E0 = 00`, `F0E2 = 00`, замер
>   2026-09-02). Обратного отсчёта не видно ни у одного — поведение регистра только на
>   запись;
> - в полном ISP первое ядро не исполняется **минутами**, и монитор при этом не
>   сбрасывается. Взведённый и кормимый из цикла сторож за это время сработал бы.
>
> Последний довод не решающий сам по себе: сторож, тактируемый вместе с ядром, тоже
> молчал бы. Но вместе с первыми тремя трактовка «сторож» повисает, а вопрос «что такое
> `F00A`» остаётся открытым.

Вариант чипа читается один раз, в `FUN_18BB`: `XDATA 0xD511 == 0x20`. От этого
зависят делитель UART и значение `F0E6`. Это **единственный внешний вход
загрузчика, кроме содержимого флеша**.

На живом экземпляре 2026-08-22 несколько чтений в одной ISP-сессии дали
`D511=0x17`, поэтому выполняется ветка `!=0x20`: `FUN_18C9()` возвращает `1`,
начальное `F0E6=0x04`, а после выбора bank 1 командой `C5` конечное
`F0E6=(0x04&0x0C)|0x41=0x45`. Значение `0x41` относилось бы только к варианту
`D511=0x20`.

### 3. `FUN_111F` — опознание микросхемы флеша

```c
R7 = FUN_18E8();                  // 57 — число записей таблицы JEDEC
for (i = 0; i < 57; i++) {        // CODE:0x4000, записи по 6 байт
    // [0]=индекс [1]=mfg [2]=type [3]=capacity [4]=код размера [5]=флаги
    if (rec[1]==F064 && rec[2]==F065 && rec[3]==F066) {
        IDATA[0x30] = rec[0];                       // индекс
        IDATA[0x32]/[0x33] = rec[4];                // код размера
        IDATA[0x2F] = rec[5] & 1;                   // умеет Quad
        break;
    }
    if (rec[1] == F064) IDATA[0x30] = (rec[0] & 0xF0) | 0x0F;   // хотя бы производитель
}
IDATA[0x31] = (F064 == 0x7F) ? 0xD7 : 0x20;         // опкод стирания сектора
```

Для нашего чипа совпадает запись `87 c8 40 19 05 01` (GigaDevice `C8 40 19` =
GD25Q256): индекс `0x87`, код размера `5`, Quad разрешён.

**Ветка 32 МБ.** При коде размера 5 загрузчик посылает флешу команду **`0xC8`
(Read Extended Address Register)**, и если та вернула не ноль:

```
FUN_180D(0);          // 0xC5 Write Extended Address Register = 0
F00A = 0x55;         // одна запись CODE:121E..1223
for(;;) {}           // CODE:1224: SJMP 0x1224
```

Смысл прозрачен: убедиться, что 32-мегабайтная микросхема стоит в нижнем банке,
и если нет — принудительно вернуть её туда. Автоматического перезапуска в этой
ветке нет; `F0E0` ранее выключен в `main`. При обычном включении питания EAR
нулевой, поэтому остановка не требуется.

**Повторно проверено по листингу 2026-09-15:** `CODE:1210` читает EAR через
`FUN_18E2` (`R7=C8`), `CODE:1213..1217` пропускает остановку только при нуле,
`CODE:1219..121B` вызывает WREAR(0), затем следует указанный бесконечный переход.
Проверка в libre воспроизводит эту штатную политику; диагностическое сообщение
`power cycle required` добавлено нами. Если исправная верхняя копия MSI дойдёт до
этой ветки и успешно выставит EAR=0, следующий аппаратный reset должен позволить
ROM прочитать нижний банк без обесточивания. Это следствие алгоритма при сохранении
EAR=0 до следующего старта, а не проведённый аппаратный опыт.

### 4. `FUN_0C83` — режим шины флеша

Вызывается хвостом из `FUN_111F` (`CODE:1237`) с двумя аргументами: `R7` — флаг «чип
умеет Quad» (`IDATA 0x2F`), `R5` — индекс чипа в таблице JEDEC (`IDATA 0x30`).
Возвращает в `R7` рабочий опкод чтения — `0x6B` или `0x3B`; `main` этот результат
**не использует**, режим остаётся в регистрах контроллера.

Если флаг Quad снят — сразу к попытке Dual. Иначе первым делом **читается текущее
состояние QE**, и где он лежит, зависит от группы производителя (`индекс & 0xF0`):

| Группа | Опкод чтения | Бит QE | Где в коде |
|---|---|---|---|
| `0x30` | `0x05` (SR-1) | `0x40` | `CODE:0C95` |
| `0x40`, `0x80` | `0x35` (SR-2) | `0x02` | `CODE:0CAE` |
| `0x50` | — | считается взведённым всегда | `CODE:0CBD` |

**Если бит уже стоит, вся ветка записи пропускается** (`CODE:0CC0` → `0x0E4F`).
Наш чип — индекс `0x87`, то есть группа `0x80`, и на живом мониторе `0x35` возвращает
`0x02`: QE в `GD25Q256` энергонезависимый и взведён с завода. Поэтому в захвате
2026-09-06 нет ни одного `WREN`+`WRSR` — загрузчик его только проверил
(`docs/spi-boot-trace.md`). Иначе выполняется запись `0x01`/`0x31` с ожиданием по
биту `WIP`, и лишь потом — общая часть.

Дальше правятся биты `F134`, `F11D`, `F050`, и делается **проверка чтением**.

**`F050` — это защёлка режима, и в ней весь смысл процедуры.** Бит 2 означает «quad
подтверждён», бит 5 — «dual подтверждён», ни одного — однобитный режим; биты
взаимоисключающие. Загрузчик ставит их **только после успешной проверки**:
`F050 = (F050 & ~0x20) | 0x04` для quad (`CODE:0E61`), при неудаче `F050 &= ~0x04`
(`CODE:0EC5`) и `F050 = (F050 & ~0x24) | 0x20` для dual (`CODE:0ECC`), при неудаче и
там — `F050 &= ~0x20` (`CODE:0F2C`).

Опкод загрузчик возвращает в `R7`, но `main` его не использует и никуда не сохраняет:
**единственный канал между загрузчиком и основным образом здесь — сам регистр `F050`**,
который тёплый сброс не трогает. Основной код `id=0x01` перечитывает его и по нему
выбирает опкод чтения — `docs/nt68503-hardware.md` §6.8, «Режим шины хранится в `F050`».

#### Проверка чтением — и откуда на шине берутся 512 байт

Разобрано 2026-09-06, поводом был захват шины: сразу после опознания чипа флеш
отдаёт ровно **512 байт с адреса 0** одной четырёхбитной транзакцией
(`docs/spi-boot-trace.md`), хотя сравнивается всего десять.

`CODE:0E7D` заполняет блок параметров в прямо адресуемой внутренней памяти и зовёт
`FUN_1491(R7 = 0x6B)`:

| Ячейка | Значение | Что |
|---|---|---|
| `0x48…0x4B` | `00 00 00 00` | адрес во флеше, 32 бита, старший байт первым |
| `0x4C` | `0x0A` | сколько байт забрать из FIFO |
| `0x4D` | `0x00` | тип обобщённого указателя Keil: внутренняя память |
| `0x4E`, `0x4F` | `0x00`, `0x3D` | адрес приёмника |

То есть **прочитанное ложится в `IDATA 0x3D…0x46`** — десять байт во внутренней
памяти 8051, ни в XDATA, ни в DRAM.

`FUN_1491` — потоковое чтение через FIFO (§6.8 `docs/nt68503-hardware.md`), и длина
транзакции в нём **зашита константой**:

```
F0EA = R7 (опкод)      F0F4 = 0x0B          ; потоковое чтение
F0E6 = (F0E6 & 0x0C) | 1
F0EB = 0x00, F0EC = 0x02, F0ED = 0x00       ; длина = 0x000200 = 512 байт
F0F0, F0F1, F0F2 ← адрес из 0x48…0x4B
F1C0 = 0x81 ; F0E5 = 2 ; ждать (F0E5 & 2) == 0
F1C0 = 0x82 ; далее по байту из F1C0, пока не кончится счётчик 0x4C
```

Отсюда и 512 на проводах: **сколько бы байт ни просил вызывающий, контроллер всегда
вычитывает из флеша 512**, а код забирает из FIFO только нужные. Захват это
подтверждает независимо: окно `CS#` длится 43,56 мкс, а при четырёх тактах на байт на
48 МГц 512 байт плюс 40 тактов головы дают ровно 43,5 мкс.

Сама проверка (`CODE:0E8D…0EB4`) сравнивает эти десять байт с `CODE:0000…0009`,
прочитанными обычным `MOVC`. Смысл прямой: **эталон — копия, которую масочный ROM
положил в кодовую память однобитным чтением на 12 МГц; проверяется, даёт ли то же
самое четырёхбитное чтение на 48 МГц.** Что `MOVC` идёт не во флеш, а в эту копию,
видно по тому же захвату: между самопроверкой и загрузкой `id=0x01` (2,5026…2,6127 с)
на шине **нет ни одной транзакции**, хотя загрузчик за это время успевает пройти
`MOVC`-ом таблицу разделов на `0x6000`. Совпало — `Set Flash to Quad mode!!` и
возврат `0x6B`. Не совпало — `F050` возвращается назад и всё повторяется для Dual
(`0x3B`, тот же адрес, те же десять байт, тот же приёмник `0x3D`): совпало —
`Set Flash to Dual mode!!` и возврат `0x3B`, иначе `System can not support Dual mode!!`.
На живом мониторе — Quad.

**Латентная ошибка в `FUN_1491`.** Адрес разбирается сдвигами на 24 и 16 бит
(`CODE:14C0`, `CODE:14D2`), а младший байт берётся из `0x4B` напрямую — то есть в
`F0F0`/`F0F1`/`F0F2` уезжают биты 31:24, 23:16 и 7:0, а биты 15:8 не попадают никуда.
При старшем-первым порядке регистров (§4.3 `docs/nt68503-hardware.md`) правильными
были бы сдвиги 16 и 8. Обе точки вызова передают адрес 0, поэтому ошибка ничего не
ломает и на шине не видна.

### 5. `FUN_0003` — таблица разделов (через `FUN_1899`)

Одна большая линейная процедура `0x0003–0x0926`.

```c
SETB bit2;                                  // «таблица годная»
slot = (CODE[0x7FFF] == 0xAA) ? 0x1000 : 0; // выбор слота
base = 0x6000 + slot;

F1D3 = CODE[base+3];  F1D4 = CODE[base+2];  F1D5 = CODE[base+1];   // адрес id=0x01

if (slot != 0 && memcmp(CODE[0x6FF0+slot], "DUALFW", 6) == 0) {
    p = CODE[0x6FF6+slot .. +7];             // восемь байт параметров
    XDATA[p0:p1] &= p2;   print("[0x%04X] = %02BX", ...);
    XDATA[p0:p3] |= p4;   print(...);
    XDATA[p0:p5] = p7 ? (… & p6) : (… | p6);  print(...);
    FUN_111F();                              // заново опознать флеш
}

if (CODE[base+0] != 0) FUN_180D(CODE[base+0]);   // 0xC5 — номер банка
F1D1 = F1D2 = 0;
F1D6 = CODE[base+7];  F1D7 = CODE[base+6];  F1D8 = CODE[base+5];   // размер id=0x01

FUN_1346(&IDATA[0x25], 2, 0);                     // → XDATA 0x3000
скопировать записи 1..8 из CODE в XDATA 0xA000.., оттуда — в общий блок
CY = bit2;  return;                                // всегда 1
```

Три вещи в этой процедуре важнее прочего.

**`DUALFW` — это патч трёх регистров, а не «две прошивки».** Сигнатура проверяется
**только на альтернативной ветке** (при `slot == 0` до неё вообще не доходит), и
за ней лежат восемь байт: старший байт адреса, общий для всех трёх операций, и
три пары «младший байт адреса + маска» с операциями AND, OR и AND/OR-по-флагу.
Каждая операция печатается как `[0x%04X] = %02BX`. Механизм позволяет тронуть три
регистра чипа **до** опознания флеша — например, переключить выбор микросхемы, —
после чего опознание повторяется. В обоих банках дампа сигнатуры нет.

**Байт `[0]` пропускается, если он нулевой.** Отсюда и живое подтверждение того,
что это номер банка: в логе холодного старта строки `SetExtendedAddr=` нет вовсе,
потому что у слота 0 этот байт равен нулю (`docs/flash-u4002.md`).

**Проверки таблицы нет никакой.** Бит `bit2` ставится один раз в самом начале и
**не сбрасывается нигде в образе** — проверено сплошным поиском по байтам
(`C2 02` не встречается ни разу, `D2 02` — один раз на `0x0006`, `A2 02` — один
раз на `0x0924`). Значит `FUN_0003` всегда возвращает «годна», `FUN_1899` всегда
возвращает `CY = 0`, а ветка `Can't find valid partition table!!!` в этой сборке
**недостижима**. Ни контрольной суммы, ни проверки диапазонов, ни сигнатуры —
загрузчик берёт то, что лежит на `0x6000`, и отдаёт железу как есть.

### 6. `FUN_1346` — сборка общего блока на `0x3000`

`FUN_1346(src, len, kind)` — memcpy в `XDATA 0x3000 + off[kind]`, где
`off = {0, 2, 0x0E, 0x32, 0x5A, 0x66, 0x6A, 0x76, 0x82, 0x8E}`. Вызовов десять:
версию структуры (константа `00 01`), восемь дескрипторов разделов и — `kind = 5` из `FUN_111F` — четыре байта
про флеш (индекс, опкод стирания, класс размера). Именно отсюда `stbc-main` берёт
тип флеша, который `docs/flash-driver.md` находит в `XDATA 0x3066`.

Это тот самый «Share Structure», версию которого печатает id=0x01.

Полная раскладка общего блока (слот 0, база `0x6000`; запись №0 таблицы — сам
`id=0x01` — в блок не попадает, она уходит в регистры `F1D3..F1D8`):

| XDATA | Длина | kind | Источник | Что |
|---|---:|---|---|---|
| `0x3000` | 2 | 0 | IDATA `0x25..0x26` | версия структуры `0x0001` (байты `00 01`), константа — не зависит от слота |
| `0x3002` | 12 | 1 | запись 1 → `0xA000` | дескриптор `id=0x02` (AUX) |
| `0x300E` | 36 | 2 | записи 2,3,4 → `0xA00C` | `id=0x0D`, `0x0E`, `0x10` |
| `0x3032` | 40 | 3 | записи 5,6,8 → `0xA030` | `id=0x05`, `0x0A`, `0x0B` + константа |
| `0x305A` | 12 | 4 | запись 7 → `0xA058` | `id=0x03` (Tensilica) |
| `0x3066` | 4 | 5 | IDATA `0x30..0x33` | флеш: индекс, опкод стирания, класс размера |
| `0x306A` | 12 | 6 | запись 9 → `0xA064` | пусто (нули) |
| `0x3076` | 12 | 7 | запись 10 → `0xA070` | пусто |

**Полный дамп (FW.037, слот 0).** `??` — байты, которые загрузчик не инициализирует

**Формат записи** — 8 байт: `[bank][id][addr_hi][addr_lo][0x00][size_hi][size_mid][size_lo]`,
где `size` — 24-битный (`[5]<<16 | [6]<<8 | [7]`), байт `[4]` всегда `0`. В общем блоке у
двух записей (`id=0x0E`, `id=0x0A`) загрузчик вставляет между адресом и размером 4-байтную
базу AHB, а у `id=0x10` — зануляет базу и размер.

базы). У `id=0x10` из записи берутся только первые 4 байта (`00 10 80 00`),
следующие два слова нулевые. **Уточнение 2026-09-17:** это значения core-регистров
Main `+200/+204`, не база и размер. Восемь байт после HDR Sub — аналогичная пара
для Sub. Потребитель, именованные поля и проверка (не опубликовано).
База `id=0x0D` в дескриптор не входит — она константа в коде
(`docs/nt68503-hardware.md`).

**Флеш-блок `0x3066`:**

```
87 20 05 00
```

- `0x87` — индекс в таблице JEDEC (`C8 40 19` = GD25Q256, 32 МБ);
- `0x20` — опкод стирания сектора (mfg `0xC8` ≠ `0x7F`);
- `05 00` — класс размера 5 (после байт-свопа в `FUN_111F`: при `rec[4] < 0x0F` байт
  переставляется из `0x33` в `0x32`).

**FW.034 отличается только размерами** — семь байт, все в полях `size` (таблица разделов
менялась между версиями):

| XDATA | FW.037 | FW.034 | Чей размер |
|---|---|---|---|
| `0x3014`/`0x3015` | `80 C8` | `7B 3C` | id=0x0D |
| `0x3021` | `A0` | `90` | id=0x0E |
| `0x3039` | `40` | `30` | id=0x05 |
| `0x304C`/`0x304D` | `F4 C0` | `F3 B0` | id=0x0B |
| `0x3060` | `D8` | `D7` | id=0x03 |

**Четыре хвостовых байта каждого 12-байтового дескриптора загрузчик не пишет.**
Заполняются только 8 байт записи, а `FUN_1346` копирует 12 — последние 4 берутся из
scratch-буфера `XDATA 0xA0xx` (`0xA008..0xA00B`, `0xA02C..0xA02F`, …), который стартап-код
не обнуляет (нулится только `0x3000..0x3FFF`). Их значение кодом не задаётся и определяется
состоянием RAM при старте; в ISP-воспроизведении (`docs/usb-isp-protocol.md`) блок
`0x3000..0x3069` сошёлся побайтно, то есть хвосты читались как `0x00`.

Полный размер структуры — `0x3000..0x3099` (154 байта), а не `0x3069`: последние четыре
дескриптора (`kind 6..9`, записи 9–12) в текущем образе пустые — таблица разделов
кончается на записи №8, дальше нули.

**Именованные форматы в свободном загрузчике (2026-09-13).**
[`boot_abi.h`](../firmware/platform/nt68503/boot_abi.h) задаёт таблицу и общий блок через
байтовые C-структуры; `bootloader.c` обращается к полям через `offsetof`, сохраняя
разделение CODE/XDATA и порядок байтов. В `make verify` добавлено исполнение самого
C-кода сборки на хосте, не только Python-модели: все 154 байта сверяются на реальных
и синтетических таблицах. Размер, порядок F1D-записей и прежние нули сохранены;
на том этапе назначение хвостовой константы `07 FF` не переинтерпретировалось;
её потребитель установлен позднее при реализации STBC (§16 её спецификации).
[Контракт, проверки и границы доказательства](../firmware/bootloader-libre/README.md#boot-abi-layout).

**2026-09-17:** заголовок без изменения содержимого перенесён в `firmware/platform/`
для второго потребителя `firmware/stbc`. Результат настоящего C-производителя
теперь дополнительно проверяется C-потребителем и SDCC-кодом STBC в симуляторе;

Сборка `2523ee7` затем записана в банк 0, `0x0000..0x1FFF`; контрольное чтение

владелец подтвердил успешную загрузку; присланный UART показывает Quad self-test,
таблицу `0x6000`, запуск STBC и обоих Leon2. Затем reset с удержанием вправо дал

побайтно совпавшие с контрольным снимком после прошивки. Затем из recovery
проверены program и erase сектора банка 0 `0x2000`: рисунок совпал при чтении,
сектор возвращён к `FF`, все первые 16 КиБ восстановлены побайтно. При этом
`3066..3069` оставались нулевыми, но хостовый SETUP/arm выставлял `F067=20`,
а SETUP также `F068=9F`. Работа без хостовой подготовки этим не доказана.

UART владельца подтвердил повторный запуск libre, STBC и обоих Leon2, затем
штатный `CMD_SYS_POWEROFF`. U7005 не вернулся, поскольку восстановился Power Off,
а не потому, что сброс не загрузил систему. `--recover --reuse` теперь поддерживает
этот путь с отдельными проверками и отличает отсутствие USB-подтверждения от
отказа до сброса; подробнее — в журнале опыта ниже.

## Откуда железо узнаёт адрес прошивки

Ответ не «одно из двух», а **оба механизма сразу, и они делят один адрес пополам**.

32-битный адрес раздела разрезан по биту 24:

| Часть адреса | Куда уходит | Как |
|---|---|---|
| биты 0–23 | в **скалер** | регистры `F1D3`/`F1D4`/`F1D5`, порядок от младшего |
| биты 24–31 | в **саму микросхему флеша** | команда `0xC5` (Write Extended Address Register) |

Причина разреза — в железе: контроллер SPI у скалера 24-битный, а микросхема на
32 МБ. Недостающий старший байт хранится **внутри флеша**, и тот сам прибавляет
его к каждому пришедшему адресу. Разбор команды `0xC5` по даташиту GD25Q256E —
в `docs/flash-driver.md`; там же про то, чем она опасна.

Дескриптор целиком выглядит так (все три поля — от младшего байта к старшему):

| Регистры | Что | Откуда берётся |
|---|---|---|
| `F1D1`, `F1D2` | обнуляются | — |
| `F1D3`, `F1D4`, `F1D5` | адрес раздела, 24 бита | байты `[3]`, `[2]`, `[1]` записи №0 |
| `F1D6`, `F1D7`, `F1D8` | размер раздела, 24 бита | байты `[7]`, `[6]`, `[5]` записи №0 |
| `F1D0 = 0x87` | пуск | — |

Байт `[4]` записи (старший байт 32-битного размера) не используется вовсе — длина
тоже 24-битная.

**Живое уточнение для service/ISP (2026-08-22).** После записи именно такого
предзапускового дескриптора и первого `F1D0=87` регистры переходят в
`00 26 F0 00 00 01 26 F0 00`: `F1D1/F1D2` аппаратно становятся `26/F0`. В ISP
этого оказалось недостаточно для исполнения обычных STBC/Main — потребовался второй
`F1D0=87` уже без переписывания завершённого дескриптора. В коде самого загрузчика
второй записи нет; причина различия контекстов пока не доказана. Живой алгоритм — в
`docs/usb-isp-protocol.md`.

Попытка подставить source `0x300000` уточнила смысл слова «перезапускает». Первая фаза
успешно перешла к завершённому дескриптору
`00 26 F0 00 00 30 26 F0 00`, но после второй `F1D0=87` UART показал новый запуск
самого bootloader и затем штатный, неизменённый баннер `NT68500`. Проверенный перед
пуском образ по `bank 1:0x300000` содержал `NT6850X`. Значит, вторая фаза recovery
возвращает систему на обычный выбор раздела через таблицу слота, а не передаёт
управление непосредственно нестандартному source первой фазы. Полный опыт и границы
этого вывода записаны в `docs/usb-isp-protocol.md`.

Отдельный опыт пытался воспроизвести перед единственным `F1D0=87` уже не только
watchdog, но всё считавшееся тогда видимым конечным состоянием загрузчика:
`D929=01`, `F152=40`, Quad-настройки,
`F0E6=45`, `F1A8=02`, `F1DF=80`, FIFO pulse, `F00A=AA/55`, корректный EAR и точный
общий блок `XDATA:3000…3069`. Дескриптор при этом записывался строго как в
`FUN_0003`: `F1D3–5` → реальный `C5(01)` → `F1D1–2=0` → `F1D6–8`; после `F1D8`
до `F00A=55` и `F1D0=87` не выполнялось ни одного чтения регистра. Первая
F1D-команда завершилась и изменила `F1D1/F1D2`, однако UART остался пустым 60 секунд.
Точные значения и отрицательный результат приведены в `docs/usb-isp-protocol.md`.

**Поправка 2026-09-12: состояние не было полным.** Повторное чтение Keil startup
table на `CODE:185F` показало две шестибайтные последовательности: для ветки
`D511!=20` `0C 18 20 30 40 60`, для `D511==20` — `0C 18 20 30 3C 44`.
`FUN_17E2` ищет соответственно `60` и `30`, возвращает индекс, а `main` прибавляет
единицу. Поэтому штатное значение — **`D929=06` на этом экземпляре с `D511=17`**
и `04` при `D511=20`, не `01`. Это независимо подтверждает preflight из того же
опыта: до записи там читалось `06`. Следовательно, именно этот опыт не исключает
пропущенную видимую настройку; позднейшее опровержение ISP-hold в лёгком сеансе от
него не зависит.

После этого завершённому нестандартному дескриптору без перезаписи полей отправили
второй `F1D0=87`, то есть ровно тот одиночный пуск, который `isp_read.py --recover`
применяет к уже завершённому окну. Даже после полной подготовки он вызвал общий reset:
UART показал bootloader и затем штатный `NT68500`, а не probe `NT6850X`. Значит,
вторая запись не продолжает исполнение source первой фазы, а возвращает систему к
обычному reset/slot-selection пути.

**Нагляднее всего это видно, если сравнить обе таблицы дампа.** Запись №0:

```
слот 0 (0x6000):  00 01 00 00 00 00 f0 26
слот 1 (0x7000):  01 01 00 00 00 00 f0 16
                  ^^ единственная разница по адресу
F1D5:F1D4:F1D3  =  01:00:00  →  0x010000   у обоих слотов одинаково
байт [0] → 0xC5 →  банк 0    /  банк 1
полный адрес    =  0x00010000 /  0x01010000
```

Скалеру в обоих случаях называют **один и тот же адрес `0x010000`** — он про два
банка вообще ничего не знает и знать не может. Всё переключение происходит внутри
микросхемы флеша, и снаружи выглядит как «та же прошивка на том же адресе».

**При включении питания обе части нулевые**; сброс скалера не следует приравнивать
к сбросу внешней SPI NOR ([отказ после банка 1](#bank1-sw4101-reset)). Отсюда
раскладка начала флеша: загрузчик
обязан лежать со смещения 0, а всё, что ему нужно прочитать, обязано уместиться в
первые 32 КБ. Так оно и разложено — свой код `0x0000–0x18EB`, таблица JEDEC на
`0x4000`, таблицы разделов на `0x6000`/`0x7000`, маркер слота на `0x7FFF`. Выше
`0x7FFF` загрузчик не читает CODE ни разу.

### Поправка 2026-09-01: `F1D0 = 0x87` — не передача управления

Записанное выше «`F1D0 = 0x87` — вся передача управления» **неверно**, и это
измерено. На живом мониторе, в лёгком сеансе с **работающими** ядрами, дескриптор с
нештатными `source 0x300000` и `size 0x8000` был записан в порядке `FUN_0003` и
запущен одной записью `F1D0 = 0x87`. Команда исполнилась — `F1D1/F1D2` сменились с
`26 f0` на `00 80`, то есть на «приёмник + size», — но ядро не
перезапустилось: UART молчал пять секунд, а 8051 всё это время продолжал исполнять
`id=0x01` и отвечать на протокол.

Значит запись `F1D0` только завершает команду `F1D`, а перезапуск ядра — отдельное
событие, вызываемое чем-то ещё. Что именно его вызывает, не установлено. Первая
версия — «это тот тёплый сброс, о котором `id=0x01` печатает `0x4570[5] toggle ==>
warm Reset!!`» — **проверена по коду и отпала**: строку печатает `FUN_CODE_E261`
после того, как сама переключит бит 5 в `XDATA 0xD570`, а оба её вызывающих
(`CODE:4E71` — загрузка, `CODE:5142` — пробуждение) продолжают исполняться дальше без
всякого сброса. Полный разбор, пробный образ и логи — `docs/stbc-launch.md`.

Попутно это опровергает объяснение прежних отрицательных результатов через удержание
ISP: та же картина воспроизводится при живых ядрах.

### Это копирование — установлено 2026-09-02

Развилка «копирует или переотображает» закрыта, и не рассуждением, а замером.

**Довод от архитектуры.** У 8051 выборка инструкций возможна только из CODE,
исполнять из XDATA/IDATA нельзя. А драйвер флеша в `id=0x01` (`FUN_9A7F`,
`docs/flash-driver.md`) стирает сектор и **в это же время** крутит опрос `F0E5 & 1`,
ждёт `WIP` и печатает `sector erase`. Пока микросхема стирает, она не обслуживает
чтение вовсе, значит эти инструкции берутся не из неё. Загруженный образ исполняется
из кодовой памяти на кристалле.

**Довод от измерения.** На живом мониторе после `F1D0 = 0x87` служебный слейв
некоторое время отвечает отказом, и это время **растёт с размером**:

| `size` | отказов | занятость |
|---:|---:|---:|
| `0x000100` | 0 | 0 |
| `0x008000` | 4 | ~8 мс |
| `0x00F026` | 10 | ~20 мс |

Порядка 3–4 МБ/с — похоже на чтение по Quad SPI. Защёлкивание регистров столько бы
не заняло и от длины не зависело бы. Логи — `captures/boot-probe-2026-09-01/`,
разбор — `docs/stbc-launch.md`.

Остаётся **не установленным, куда** идёт копия: работающий `id=0x01` переживает
команду без единого сбоя, значит приёмник — не та кодовая память, из которой ядро
выбирает инструкции в этот момент.

## Кто запускает ядра

**Загрузчик не запускает ни одного ядра, кроме собственного.**

Он отдаёт железу ровно один образ — запись №0 таблицы, то есть `id=0x01`: адрес в
`F1D3..F1D5`, размер в `F1D6..F1D8`, номер банка — самой микросхеме командой
`0xC5`. Последнее действие — `F1D0 = 0x87`, и дальше предусмотрен цикл записи
`F00A=55`. **Перехода в загруженный образ в коде нет.** Точный аппаратный механизм
изменения PC/выбора кодовой памяти пока не измерен. Финальный цикл находится на
`CODE:159B..15A2`; простая замена его байт кодом STBC Main при сохранении PC
выводит выполнение в середину Main и даёт записи по неверному DPTR, а не переход
на startup. Побайтный разбор наложения (не опубликовано).

Остальные восемь записей таблицы он не загружает, а перекладывает в общий блок как
данные. Ни Tensilica, ни оба Leon2 в загрузчике не упоминаются: из 38 регистров,
к которым он обращается, ни один не относится к их сбросу.

Запускает их `id=0x01`. Строки `Leon2 vs AHB clk is 3:1`, `Leon2 (Main) RUN...`,
`Leon2 (Sub) RUN...`, `Leon2 (Main) STOP...` лежат в разделе `id=0x01`
(`0x90E4`, `0x912B`, …), в загрузчике их нет.

**Решает вопрос живой лог** (`captures/boot-standby/pin13-stbc-8051.txt`). Холодный
старт:

```
------STBC Boot Loader -----        ← загрузчик
Set Flash to Quad mode!!            ← загрузчик, FUN_0C83
Re-booting STBC code...             ← загрузчик, перед F1D0 = 0x87
0x4570[5] toggle ==> warm Reset!!   ← уже id=0x01
------NT68500 MCU Test program -----
Leon2 vs AHB clk is 3:1
Leon2 (Main) RUN...
Leon2 (Sub) RUN...
```

А выход из дежурного режима — совсем без загрузчика:

```
Wakeup!!! 0x4570[5] toggle ==> warm Reset!!
Leon2 vs AHB clk is 3:1
Leon2 (Main) RUN...
Leon2 (Sub) RUN...
```

Баннера нет, значит загрузчик не исполнялся, а ядра всё равно поднялись. Это
прямое доказательство того, что их запуск к загрузчику отношения не имеет.

**Что делает скрытый слой.** Он есть, но узкий: аппаратура (или масочный ROM)
умеет ровно одно — вычитывать код 8051 из флеша по заданному адресу и стартовать
ядро. Таблицу разделов она не понимает: её читает сам загрузчик через `MOVC` и
руками перекладывает в RAM. Про остальные ядра она тоже ничего не знает.

**Поправка 2026-08-23 к прежнему рассуждению.** Здесь стояло: «исполнять код записи
флеша из самого флеша нельзя, значит цикл записи живёт в ROM». Аргумент слабее, чем
выглядел. Если `F1D` **копирует** раздел в кодовую память, исполняемый образ от флеша
уже не зависит и может его переписывать — и `docs/flash-driver.md` действительно нашёл
полный примитив записи внутри `id=0x01`. Копирование это или отображение с дозагрузкой,
**не установлено** (`docs/usb-isp-protocol.md`), поэтому вывод про ROM на эту опору
ставить нельзя.

Существование ROM-кода опирается на другое, и опоры крепче: строка
`CMD_START_ISP_ROMCODE_MODE` в `id=0x02`, регистр фаз `0xF19A`, который 8051 только
читает, и главное — токен `F0 0F 6E 91 13 EC`, которым сопровождаются пишущие команды
сырого протокола: во всём флеше его нет, а проверяет его та сторона, что исполняет
запись (`docs/nt68503-i2c-service-protocol.md`, § «Где живёт сервер этого протокола»).

## Аварийное восстановление флеша

Вопрос: если во флеше цел только загрузчик, есть ли внешний канал, чтобы залить
остальное?

### Своими силами загрузчика — нет

**У загрузчика нет ни одного канала приёма.** Проверено по байтам:

| Канал | Признак | Результат |
|---|---|---|
| UART | `MOV A,SBUF` (`E5 99`) | **0 вхождений** — консоль только на передачу |
| I²C | программная шина, биты портов | ни одной операции над битами портов |
| Ножки/страпы | `JB`/`JNB` по битовым адресам портов | только `RI`/`TI` (`0x98`/`0x99`) и `EA` |
| USB | регистры `CDxx`, `F19x` | не трогает вовсе |

Единственный внешний вход — регистр `XDATA 0xD511` (вариант чипа). Всё остальное
загрузчик берёт из флеша.

**И проверять он ничего не умеет.** Контрольной суммы нет, ветка «таблица не
найдена» недостижима. При стёртом секторе `0x6000` он прочитает `FF FF FF …`,
пошлёт флешу `SetExtendedAddr(0xFF)`, зарядит базу `0xFFFFFF` и всё равно напечатает
`Re-booting STBC code...`. Дальше — тишина: аварийные циклы кормят сторож, поэтому
перезагрузки не будет.

Диагностическая ценность у этого всё же есть: по консоли 4800 бод на `CN4008`
контакт 13 сразу видно, докуда дошло. Баннер есть, `Set Flash to Quad mode!!` есть,
`Re-booting STBC code...` есть, дальше молчание — значит флеш читается, а образ
`id=0x01` испорчен.

### Что реально спасает

**1. Два слота — это и есть штатная защита, и она сильнее, чем кажется.**
Флеш поделён на два независимых 16-мегабайтных слота, выбор — один байт `0x7FFF`
нижнего банка (`docs/flash-u4002.md`). Обновление пишет в **свободный** слот и
переключает маркер только после того, как запись прошла целиком. Поэтому сценарий
«испорчено всё, кроме загрузчика» из обычного обновления не получается: получается
«испорчен один слот», а монитор продолжает грузиться со второго.

Заметим асимметрию, которая объясняет замысел: `0xAA → 0x00` — это гашение битов,
делается без стирания сектора, а `0x00 → 0xAA` требует стереть сектор `0x7000`
вместе с таблицей слота 1. То есть **откат на слот 0 дёшев и почти атомарен**, а
слот 0 — резервный по умолчанию.

**2. Загрузчик не переписывается штатным путём.** Разделы начинаются с `0x010000`,
первые 64 КБ не покрыты таблицей вообще. Обновление трогает сектор `0x6000` (таблица
и маркер) и сами разделы, а `0x0000–0x5FFF` — никогда. Поэтому загрузчик и одинаков
во всех трёх версиях прошивки.

**3. Встроенная защита от «не того банка»** — проверка `0xC8`/`0xC5` в `FUN_111F`.

**4. Программатор — единственный канал, работающий при любом повреждении.**
Проверено на этом мониторе: чип читается in-circuit тонкими проводками с Raspberry
Pi, выпайка не нужна (`docs/flash-u4002.md`). Восстановление из имеющегося дампа:

- если испорчен слот 0, а слот 1 цел — стереть сектор `0x7000`, записать туда
  таблицу слота 1 из дампа и `0xAA` в `0x7FFF`; монитор поднимется на FW.023.
  **Содержимое этого сектора есть только в дампе** — в файлах MSI его нет, поэтому
  без `flash/u4002_a.bin` такой откат невозможен;
- если испорчено всё — залить нижние 16 МиБ из дампа или из файла MSI.

**5. ISP в масочном ROM — существует, но вход не установлен.** Что ROM умеет писать
флеш, следует из `CMD_START_ISP_ROMCODE_MODE`. Но все найденные пути к нему
начинаются из кода во флеше (`id=0x02`, `docs/usb-isp.md`), то есть при испорченном
флеше недоступны. Есть ли у чипа аппаратный вход в ROM-ISP — страп на ножке при
сбросе или фиксированный I²C-адрес, на который отвечает сам ROM, — **из дампа не
выводится**: это код, которого во флеше нет. Закрыть можно только даташитом
NT68503 или экспериментом.

**Состояние на 2026-08-30.** Обе половины сдвинулись, и обе — в сторону «сложнее, чем
надеялись».

*Даташит отпадает как способ.* Документации Novatek на это семейство в открытом доступе
нет вовсе, и даже в утёкшем даташите родственного NT68667FG раздел про MCU отослан к
отдельной «MCU Spec», которой нет ни для одной модели (`docs/external-research.md`).

*Снаружи такого входа не нашёл никто.* Родственный проект по ASUS PG42UQ на NT68552 —
то же семейство NT68500, те же слейвы `0x6E`/`0xB0`, тот же кадр входа `04 34 06 36` →
`A5 00` — формулирует ровно нашу гипотезу («ISP отвечает и на пустом флеше, потому что
отвечает кремний, а не прошивка») и **прямо помечает её непроверенной**. Ни страпа, ни
отдельного аварийного адреса, ни окна после сброса не описано ни там, ни где-либо ещё.
Для сравнения: у MStar такой порт есть, задокументирован и поддержан в `flashrom`
(`mstarddc_spi`, адрес `0x49`), у Realtek, Parade и MediaTek — свои; **у Novatek в
`flashrom` нет ни одного программатора.** Подробности и ссылки —
`docs/external-research.md`, § «Семейство NT68500 снаружи».

*Первый эксперимент поставлен и дал отрицательный результат — но слабый.* Захват с
обесточенной платы показал окно **95,4 мс** между снятием сброса и первым байтом
загрузчика, и в этом окне на контактах `CN4008` 1, 2, 3, 4, 11 **нет ни одного фронта**
(`docs/boot-sequence.md`). Это значит, что ROM ничего не инициирует, и **не** значит,
что он не слушает: ведомый I²C пассивен по определению. Нужен активный опыт —
передатчик, работающий в эти 95 мс, — и, что важнее, ставить его надо на той шине, где
служебный слейв действительно живёт: на паре `PE.12`/`PE.13` между `U7005` и скалером
(`docs/mcu-u7005.md`), а не на отладочном разъёме.

### Итог

Штатного «залей прошивку по проводу в мёртвый монитор» в загрузчике нет и быть не
может — он ничего не принимает. Страховка построена иначе: два слота, дешёвый
откат на первый и загрузчик вне зоны записи. Отсюда практическое правило: **пока
цел хотя бы один слот и загрузчик, монитор восстанавливается; за пределами этого
нужен программатор, и без снятого дампа сектор `0x7000` восстановить неоткуда.**

## Что осталось неразобранным

- Назначение регистров `F1DF`, `F152`, `F1A8`, `F134`, `F11C`, `F11D`, `F0E0`,
  `D929`, `D434` — они пишутся константами, смысл из кода не следует.
- Точная семантика `F1D0 = 0x87` и `F1D1`/`F1D2`: что именно защёлкивается и
  сколько времени занимает перезапуск.
- Умеет ли аппаратура грузить кодом что-то кроме записи №0.
- Алгоритм контрольной суммы. В загрузчике его **нет вовсе** — значит считает и
  проверяет её тот, кто пишет флеш, а не тот, кто грузит. Это сужает поиск по
  открытому вопросу №4: единственная строка `CheckSum Fail!` во всём образе лежит
  в `id=0x02` (файл `0x2C301`, адрес `0xC301`), то есть в агенте обновления, а не
  на пути загрузки. Сумма проверяется при приёме образа, а не при старте.

## Свободная реализация `bootloader-libre` (2026-09-12)

В [`firmware/bootloader-libre/`](../firmware/bootloader-libre/) добавлена clean-room реализация на C
для SDCC под лицензией MIT. Она повторяет узкий контракт именно первичного
bootloader: инициализацию 8051/UART/SPI, GD25Q256E и Quad/Dual self-test, A/B-выбор,
`DUALFW`, сборку `XDATA:3000..3099`, дескриптор `F1D1..F1D8` и единственный пуск
`F1D0=87`. DDR, AUX, Tensilica и Leon2 в неё не входят: это обязанности `id=0x01`.

### Что заменено прямым кодом, а что пока не перенесено

Прежняя формулировка «штатная startup-таблица применяется к SFR и XDATA, а свободная
версия перенесла из неё лишь `D929/F0E6`» была неверна. Универсальный интерпретатор
Keil действительно умеет несколько типов записей, но таблица **этого bootloader** на
`CODE:185F..1872` содержит только три записи обычной внутренней DATA:

```text
06 08 0C 18 20 30 40 60   IDATA:08..0D = 0C 18 20 30 40 60
06 0E 0C 18 20 30 3C 44   IDATA:0E..13 = 0C 18 20 30 3C 44
01 14 00                  IDATA:14 = 00
00                        конец
```

Записей SFR и XDATA здесь нет. Первый массив нужен `FUN_17E2` для ветки
`D511!=20`, второй — для `D511==20`; поиск `60` или `30` даёт итоговый `D929=06`
или `04`. `IDATA:14` служит нулевым значением флагов неизвестной flash и при точном
совпадении JEDEC перезаписывается байтом `[5]` её записи. `F0E6` startup-таблица не
задаёт: `main` получает `04` или `00` отдельно из `FUN_18C9`. В свободной реализации
эти временные массивы и общий интерпретатор заменены прямым выбором тех же конечных
значений. `make verify` отдельно сверяет все 20 байт штатной таблицы в FW.034 и
FW.037.

Другое сознательное сокращение — **таблица 57 SPI NOR по `CODE:0x4000` пока не
используется**. Она остаётся физически нетронутой: записывался только первый сектор
`0x0000..0x0FFF`. Однако `bootloader-libre` не сканирует её, а содержит параметры
установленного GD25Q256E (`87 C8 40 19 05 01`) как константы. Поэтому сейчас удалена
совместимость с остальными 56 записями: их группами QE, выбором стирания `0x20/0xD7`,
классами размера и соответствующими ветками Quad/Dual. Это отложенная часть, которую
нужно вернуть вместе с алгоритмом, зависящим от найденного индекса; просто прочитать
шестибайтную запись недостаточно.

Остальные замены не убирают наблюдаемого поведения на установленном чипе: весь
`XDATA:3000..3FFF` по-прежнему очищается, промежуточная сборка дескрипторов через
`XDATA:A000` заменена прямой записью того же `Share Structure`, библиотечный `printf`
заменён маленькими UART-функциями, а диагностические тексты переписаны по требованию.
Аудит UART выявил одну настоящую потерю: штатный `CODE:1843..1856` обрабатывает
`XOFF=13` и ждёт `XON=11`. Эта обработка возвращена в исходник и машинную проверку,
но версия с ней ещё не записывалась в монитор.

Диагностические строки написаны заново; строк MSI в бинарнике нет. Сборка использует
только SDCC, GNU Make и Python. `make verify` проверяет reset vector, границу одного
сектора `0x1000`, отсутствие семи строк исходного bootloader, startup-константы,
UART-init/XON/XOFF/drain и полный `Share Structure` для FW.034, FW.037 и сохранённой
таблицы слота 1. Текущий исходник с XON/XOFF на SDCC 4.6.0 занимает 3686 байт;
дополненный до `0x1000` `bootloader-a.bin` имеет SHA-256
`72cdc9b6075242a6b289d7c03c7fa5ae99619f3ba4d34d079b2a56633a2a57e8`.

2026-09-12 первая аппаратная версия была записана в физический банк 0 `U4002`.
Полный read-back первых 16 КиБ доказал два факта: `0x0000..0x0FFF` совпало с тем
записанным `bootloader-a.bin`, а `0x1000..0x3FFF` побайтно осталось прежним. Затем
штатный recovery запустил FW.034 `stbc-main`, и служебный UART ответил
`5b00110000`. Сырые дампы и хэши сохранены в
`captures/bootloader-libre-2026-09-12/` (не опубликовано).

Первая версия с SHA-256 `ddd939be…31839` затем прошла аппаратный reset `SW4101`:
монитор успешно загрузил `stbc-main` и вернулся к работе. Это живое подтверждение
основной цепочки A/B-таблица → `Share Structure` → `F1D`, но её ранних строк на UART
4,8 кбод не было. Причина оказалась в нашей реализации, а не в разводке:

- штатный `FUN_1616` до запуска `stbc-main` использует исходную частоту 96 МГц при
  `D511 != 0x20`, умножает её на 2 и делит на 384 и 4800; результат 104 даёт
  `TH1 = -104 = 0x98`;
- для варианта `D511=0x20` исходные 48 МГц тем же расчётом дают 52 и `TH1=0xCC`;
- первая свободная версия ошибочно писала `TH1=0xF3`, взятый из UART AUX 8051 после
  перестройки тактирования. До `stbc-main` reload 13 давал около 38,5 кбод, в восемь
  раз больше ожидаемого, поэтому приём на 4,8 кбод не видел строк.

Исправленная версия содержит точные ветви `0xCC/0x98`, затем штатную последовательность
`SCON=0x52`, `TMOD=0x21`, `PCON=0x80`, `TR1=1`; передача ждёт и очищает `TI`, после
чего пишет `SBUF`. Этот машинный фрагмент теперь проверяется сборочным тестом. Новый
сектор снова записан и считан обратно, следующие 12 КиБ не изменились; доказательство —
`captures/bootloader-libre-uart-fix-2026-09-12/` (не опубликовано).

Повторный `SW4101` подтвердил это исправление: UART показал строки bootloader, затем
запустились `stbc-main` и весь монитор. Последняя строка при этом выглядела как
`0x4570[5] toggle ==> warm Reset!!ble 6000`. Это точный след незавершённого перевода
строки. Наша строка `libre: starting stbc-main from table 6000` содержит 41 символ,
строка `stbc-main` до своего `CR/LF` — 33, а остаток первой с позиции 33 равен ровно
`ble 6000`.

Причина в семантике передатчика: `uart_putc()` ждёт `TI` **перед** каждым байтом.
Перед последним `LF` он тем самым гарантирует завершение `CR`, очищает `TI`, пишет
`SBUF=LF` и возвращается. Следующие команда `F1D` и аппаратный переход к `stbc-main`
происходят раньше, чем UART заканчивает `LF`; повторная инициализация UART обрывает
байт. Терминал уже стоит в колонке 0 из-за `CR`, поэтому первая строка `stbc-main`
замещает начало старой строки и оставляет её хвост.
У штатного bootloader передача устроена так же (`CODE:1857 JNB TI`, `CODE:185A CLR TI`,
затем `SBUF`) и после сообщения сразу идёт `F1D`; старый живой лог аналогично содержит
слитые `Re-booting STBC code...` и `0x4570…`.

В третьей версии после заключительного `LF` добавлен `uart_drain()`: отдельный цикл
`JNB TI` перед `F1D0=87`. `make verify` требует последовательность `30 99 FD 22`,
чтобы оптимизация компилятора не убрала это ожидание. Снова записан только сектор
`0x0000..0x0FFF`; read-back совпал с образом, `0x1000..0x3FFF` не изменились, recovery
успешен. Дампы и хэши — в
`captures/bootloader-libre-uart-drain-2026-09-12/` (не опубликовано).

Версия с UART drain занимала 3666 байт и имела SHA-256 `01ac138c…9fcf`. Именно она
сейчас находится во flash и проверена `SW4101`. Кандидат `72cdc9b…a57e8` с XON/XOFF
не записан: после отменённой команды отдельный read-back первого сектора снова дал
`01ac138c…9fcf`, затем recovery успешно запустил `stbc-main`. Доказательство —
`captures/bootloader-libre-flow-control-2026-09-12/` (не опубликовано).

### Ранний опрос джойстика

По просьбе владельца в свободную версию добавлена первая исследовательская функция:
однократное распознавание направления джойстика с печатью в UART. Это не код из
штатного bootloader. Используется установленное ранее аппаратное соответствие
`0xCF03CF24 ↔ XDATA:F3C9`, полученное из формулы
`AHB = 0xCF000000 + 4 × XDATA`. Сама апертура проверена на живом мониторе, а значение
клавиатурного ADC `0xFF → 0x3B` отдельно наблюдалось через Main.

Инициализация повторяет значения функции Main `0x0007A4C8`: `F3C0=00`, `F3C2=80`,
`F3C3=01`, затем `F080 |= 01` для канала 5 и `F3C1=1B`. Инициализация выполняется до
стартового баннера, а чтение — после него, поэтому перед выборкой проходит время
передачи строки на 4800 бод. Цикла ожидания нет: загрузчик делает одну выборку и сразу
продолжает обычный путь к `F1D`.

Декодер использует подтверждённые границы `25–51`, `60–84`, `93–AF`, `BD–D3` и
печатает соответственно `direction 1`…`direction 4` вместе с сырым байтом. Центральное
нажатие `00–1E`, покой и защитные зазоры не печатаются. После записи владелец выполнил
аппаратные запуски с каждым направлением: вправо — `1 (3B)`, влево — `2 (74)`, вниз —
`3 (A2)`, вверх — `4 (CA)`. Все значения находятся внутри предсказанных диапазонов,
все строки появились в UART, монитор каждый раз продолжил штатную загрузку.

Статический verifier проверяет точную последовательность настройки канала 5, все
четыре сравнения, строку UART и порядок «ADC init → стартовый баннер → выборка».
Сборка занимает 3882 байта из сектора 4096, SHA-256
`078b1d967076b3d90c69c7c53ab40d30659cc95bbad794ded17db12238ae7b8c`. По команде
владельца она записана в физический `U4002` одним сектором. Read-back совпал с образом,
а `0x1000..0x3FFF` не изменились; recovery успешно запустил FW.034 `stbc-main` и
получил UART-макроключ `5b00110000`. Последующие запуски через `SW4101` исполнили новый
первичный путь и подтвердили раннюю выборку ADC для всех четырёх направлений. Доказательство —
`captures/bootloader-libre-joystick-2026-09-12/` (не опубликовано).

Базовый путь для установленного GD25Q256E физически записан и уже подтвердил запуск
`stbc-main`; `SW4101` с третьей версией подтвердил и чистое разделение строк UART.
Текущий кандидат с XON/XOFF и джойстиком записан, проверен read-back и успешно исполнен
аппаратным reset. Полный drop-in
replacement не доказан: оба слота и остальные функции монитора не проверены, а таблица
из 57 SPI NOR пока не используется. Поддержан фактический `JEDEC C8 40 19`;
неинициализированные в штатном коде хвосты дескрипторов детерминированно остаются
нулевыми после очистки XDATA.

### Первый запуск recovery: уровень GPIO без настройки пада недостаточен

Установленный recovery-кандидат был запущен удержанием джойстика вправо. UART показал
`direction 1 adc 3B` и `ISP ready`; строки `stbc-main` отсутствовали, то есть условие,
ветвление и обслуживающий цикл работают. При этом U7005 не появился; состояние VL211
в этом опыте отдельно не фиксировалось.
Опыт отрицательно проверил именно раннюю достаточность `F003.4=1`, `F008.4=0`, а не
назначение линии, ранее установленное на работающем мониторе.

Причина найдена повторным чтением инициализации GPIO Main. `FUN_000C075C` до
`App_Initialize` задаёт bank 4 тремя значениями: `DATA=AF`, `DIR=0C`, `REG3=50`.
`FUN_000C1CC8` ставит DATA bit 4 уже после этого. Третий регистр имеет адрес
`AHB:CF03C2CC`, следовательно его 8051-alias — `XDATA:F0B3`. `REG3=50` включает
bit 4 — ту же линию, а кандидат `F0B3` не настраивал.

В следующий кандидат добавлен read-modify-write `F0B3 |= 10` перед установкой DATA и
DIR. Остальные биты банка сохраняются; DDR, AUX и Leon2 по-прежнему не запускаются.
Сборка занимает 4022 байта, оставляет 74 байта `FF` и имеет SHA-256
`d5b9e151cb8b46b776b1eee2b9d694948e0d3a6f15ecf9e3a91e2c97c214fd56`.
Она записана только в физический сектор bank 0 `0x0000..0x0FFF`. Обратное чтение
сектора совпало с образом, а контрольный хвост `0x1000..0x3FFF` — с предыдущим
дампом. SHA-256 считанных 16 КиБ после записи —
`78c33c6728261248fb7c28d904c2491746c351a3649bec002b20932b61828724`; затем recovery
успешно запустил штатный `stbc-main`. Сам исправленный первичный путь начнёт
исполняться только после аппаратного reset.
Журнал первого опыта и статического вывода сохранён в
`captures/bootloader-libre-isp-2026-09-12/` (не опубликовано).

Аппаратный reset второго кандидата также дошёл до `ISP ready`, но U7005 не появился.
После обычной загрузки консоль Main позволила проверить остальные выходы из той же
последовательности. Bank 5 bit 4 и bank 13 bit 7 дали отрицательный результат. Снятие
bank 13 bit 5 (`CF03C478: BF→9F`) удалило только `MSI Gaming Controller`, сохранив
VL211; возврат `BF` перечислил мост заново. Снятие `REG3.5` того же банка
(`CF03C4D4: 31→11`) независимо повторило эффект.

8051-alias этих регистров: `F11E` DATA, `F11F` DIR, `F135` REG3. В третий кандидат
добавлена точная настройка `F135.5=1`, `F11E.5=1`, `F11F.5=0`. Вместе с прежним
bank 4 она должна сначала поднять VL211, затем отдельно разрешить U7005. Образ занимает
4043 байта, оставляет 53 байта `FF` и имеет SHA-256
`7d9b6536b8d7fa3091b2c3d25dd6f3a430a55d54be693944eb05db90ff50b370`. Он собран и
прошёл verifier. Затем записан только сектор `0x0000..0x0FFF`; read-back совпал с
образом, `0x1000..0x3FFF` не изменилось, recovery запустил `stbc-main`. SHA-256
считанных 16 КиБ —
`d344e97e96047aa2bf5f0bee82234e1e1ae090dc21eabd066a8517806c096964`. Новая ветка
вправо была исполнена: UART дошёл до `ISP ready`, но владелец отдельно проверил, что
не появился ни VL211, ни U7005. Значит даже доказанные по отдельности bank 4 bit 4 и
bank 13 bit 5 не образуют достаточную раннюю последовательность.

Повторная сверка с `App_Initialize` выявила ещё один реально меняющийся выход —
bank 6 bit 7. Его живое переключение после полной инициализации Main ранее не влияло
на USB, но это не исключает роли при холодном старте. Банк `0xFF`, вокруг которого
Main выдерживает 50 мс, по полному switch `GPIO_Write` является no-op. Четвёртый
кандидат воспроизводит относящиеся к последовательности полные значения
`REG3/DATA/DIR` банков 4, 6, 7, 5 и 13 и паузу между группами. Он занимает `0x1007`
байт кода, дополнен `FF` до двух секторов `0x2000`, имеет SHA-256
`613e0178b1c50331647f350a198b694508b5a23046a637112c0caf55e5ec02cd` и прошёл
статическую проверку. Перед записью первые 16 КиБ совпали с предыдущим read-back
`d344e97e…964`. Записаны только `0x0000..0x1FFF`; целевые два сектора совпали с
образом, `0x2000..0x3FFF` не изменились, полный SHA-256 после записи —
`482ffe5df918d5ce74389990569ec3843dbb71f14a318f7e0ced8d564e6dc8f9`. Recovery
запустил FW.034 `stbc-main`; Main-консоль и оба USB-устройства вернулись. Новая ветка
вправо была исполнена аппаратным reset, но не появился ни VL211, ни U7005.

Это выявило ошибку в формулировке «воспроизводит последовательность»: четвёртый
кандидат воспроизводил лишь **конечные состояния**. `FUN_000C075C` сначала пишет
холодные DATA `AF`, `7C`, `8E`, `DE`, а `App_Initialize` позже поднимает нужные биты.
При `SW4101` конечные уровни GPIO могут сохраняться, поэтому прямая повторная запись
`BF/FC/8F/FE` не создаёт фронта, необходимого enable/reset-линии.

Пятый кандидат сначала задаёт холодные уровни банков 4, 6, 7, 5 и 13, держит их около
50 мс, затем повторяет высокоуровневые записи и вторую паузу. Перед `ISP ready` он
печатает read-back `REG3/DATA/DIR` каждого банка. Образ заканчивается на `0x1117`,
дополнен до `0x2000`, имеет SHA-256
`e4c0f88f3f27b1066dbce9a83ef26baa84696035e6f58f7546c441763588fbef` и прошёл
статический verifier. Перед записью первые 16 КиБ побайтово совпали с read-back
четвёртой версии (`482ffe5d…e6dc8f9`). Записаны только `0x0000..0x1FFF`; целевые
сектора совпали с образом, `0x2000..0x3FFF` не изменились. SHA-256 новых первых
16 КиБ — `2a09afeaccffd7c5e753821172af5db2c3578b6ae03d19dc13ef1d740b47b2d8`.
Recovery проверил окно FW.034, запустил `stbc-main` и получил макроключ
`5b00110000`. Затем аппаратный reset с удержанием вправо исполнил первичную ветку:
UART напечатал `50/BF/0C`, `83/F8/74`, `70/CD/C2`, `10/FF/2F`, `31/BE/42`, но ни
VL211, ни U7005 не появились. В этих тройках все несовпадения DATA с записанным
значением приходятся на биты, для которых `DIR=1`, то есть на входы. Тем самым
проверено, что ранний GPIO-домен работает и специально выбранные выходы принимают
нужные уровни; гипотеза о достаточности одних низких импульсов опровергнута.

Сравнение с работающим Main показало пропущенную выходную пару. Активное состояние
имеет `bank4.7=0 / bank13.0=1`, а пятый recovery оставлял
`bank4.7=1 / bank13.0=0`. Это не случайное различие: `FUN_000C1244` Leon2 Main
опускает bank4.7, ждёт 50 мс, поднимает bank13.0 и вызывает `FUN_000D4900(0)`;
`FUN_000C127C` выполняет обратную последовательность и вызывает
`FUN_000D4900(1)` при переходе в энергосбережение. Отдельная `FUN_000C1214`,
безусловно вызываемая из `System_Initialize`, также поднимает bank13.0.

Шестой кандидат переносит установленную GPIO-часть активного пути: bank4 DATA `3F`,
пауза около 50 мс, bank13 DATA `FF`. Образ заканчивается на `0x112F`, дополнен до
`0x2000`, имеет SHA-256
`f48ad48b42b5039a34925caa80d344ff232fdff3e0d7c75c9d59af332f488f7e` и проходит
статический verifier. Следующий вызов `FUN_000D4900(0)` формирует команду `0x91` с
четырьмя байтами через `FUN_000D33A0`; точный адресат и необходимость этой команды
до появления U7005 пока не установлены, поэтому она не перенесена.
Журнал опыта (не опубликовано).

Перед записью первые 16 КиБ совпали с предыдущим read-back `2a09afea…b2d8`.
Записаны только `0x0000..0x1FFF`; целевой диапазон совпал с образом, а следующие
8 КиБ не изменились. SHA-256 новых первых 16 КиБ —
`1c84d0981e7785743af8c1e6c4b16dd666537140418b102219538157c986c204`. Recovery
запустил FW.034 `stbc-main`, получил макроключ, после чего U7005 снова перечислился.
Аппаратный reset с удержанием вправо дал ожидаемые `gpio4 50 3F 0C` и
`gpio13 31 BF 42`, но не перечислил ни VL211, ни U7005. На U7005 при этом измерены
3,3 В, как и при прошлом опыте. Поэтому питание самого моста есть, а отсутствует
родительский USB-хаб или связь с ним.
Журнал записи (не опубликовано).

Уточнён и следующий вызов штатной функции. `FUN_000D33A0` использует
`SharedPortal_WriteWords(portal=1)`, то есть пишет в физическое окно `0x9F130100`
между Leon2 Main и Sub. Команда `0x91` из `FUN_000D4900` не адресована U7005 и не
является недостающим шагом его USB enumeration.

Вместо неё найден собственно `UsbModeSelect=0`. Он ставит bank3.2 в единицу через
`FUN_000C1D90`, а `FUN_000C1D58` опускает bank10.4, ждёт 200 тиков и снова поднимает.
Холодные `REG3/DATA/DIR` равны соответственно `04/F3/FB` и `E3/1C/E4`; в XDATA
первого 8051 это `F0B2/F002/F007` и `F132/F118/F119`.

Обе линии проверены обратимо на работающем FW.034. При bank3 DATA `0D→09`
исчезли и VL211, и U7005, а при возврате `09→0D` оба перечислились снова. При
bank10 DATA `9E→8E` исчезли те же два устройства, а `8E→9E` их вернул. DIR и REG3
при этом совпали с холодной таблицей. Тем самым bank3.2 доказан как подключение
VL211 к USB-B upstream, а bank10.4 — как reset всего этого USB-тракта. Седьмой
recovery-кандидат воспроизводит полную последовательность `UsbModeSelect=0`: холодные
значения обоих банков, bank3.2=1 и импульс 1→0→1 на bank10.4 длительностью около
200 мс. Он заканчивается на `0x11A6`, дополнен до `0x2000`, дважды собран побайтно
одинаково с SHA-256
`afdeec358b98ade08c94abfdf6d868b6650417b3fe9b7d96eb15a03594e33601` и прошёл
статический verifier. Перед записью первые 16 КиБ совпали с установленной шестой
версией. Записаны и сверены только `0x0000..0x1FFF`; следующие 8 КиБ не изменились.
SHA-256 полного read-back 16 КиБ —
`80af09fc2a37b811e422da8134a33dde2c15147bfa35e687b4666654fbc89761`. Recovery
запустил FW.034 `stbc-main`, VL211 и U7005 вернулись.

Новый первичный код затем исполнен аппаратным reset с удержанием вправо. UART дал
`gpio3 04 0D FB`, `gpio10 E3 1C E4` и `ISP ready`; VL211 и U7005 появились до
`stbc-main`. Через этот тракт прочитаны JEDEC `C8 40 19`, начало bootloader и таблица
`0x6000`; оба диапазона совпали с локальными эталонами. Это доказывает автономный
USB-ISP read path. Запись лишнего тестового сектора не выполнялась.

Программный recovery пока ограничен. Ветка вправо вызывается до разбора разделов и
не строит `Share Structure`, поэтому F1D-окно осталось `AA 00 00 00 00 00 00 00 00`.
`isp_read.py --recover --reuse` правильно отказался запускать `stbc-main` с таким
дескриптором. Аппаратный SW4101 без удержания вправо прошёл обычный путь, вернул оба
USB-устройства и ответ `5b00110000`.

### Текущий инженерный статус (2026-09-13)

После этой аппаратной проверки текущая версия признана полностью работоспособной
для данного монитора и его GD25Q256E. Обычная ветка загружает штатную прошивку, а
ветка вправо поднимает автономный USB ISP. Через неё утилиты хоста умеют читать,
стирать, программировать и проверять любой диапазон 32-МиБ `U4002`; запись первых
двух секторов каждого банка требует отдельного `--allow-bootloader`.

Это не вывод о переносимости на другие SPI NOR и не обещание восстановления после
стирания самого первичного загрузчика. Но пока boot region остаётся исправен,
`bootloader-libre` является рабочей страховкой для экспериментов с любыми остальными
разделами и для разработки собственных образов ядер. Провода к `U4002` теперь нужны
не как единственный канал восстановления, а как независимый резерв на время
рефакторинга загрузчика. После его модульной переработки, документирования и финальной
аппаратной проверки провода можно снять и вернуться к исследованию монитора и скалера.

### Модульный C-кандидат (2026-09-13)

Большой `__naked`-блок `recovery_hardware_init` и десять ручных `NOP` в `delay10`
удалены. Их поведение выражено обычным C: recovery разбит на именованные фазы
холодной таблицы GPIO, подъёма устройств, выбора USB-B/reset VL211 и включения raw-I2C;
задержки — на отдельные C-функции с явными циклами. В `.c` больше нет `__asm`,
`__endasm` или `__naked`.

Исходник разделён по контрактам: `bootloader.c` оставляет только политику загрузки и
ABI `Share Structure`/F1D, `flash.c` владеет SPI, `gpio.c` — отображением GPIO на
XDATA и операциями с выводами, `recovery.c` — ADC и автономным ISP, `uart.c` —
консолью, `timing.c` — ранними задержками. Единственный ассемблерный файл —
минимальный `crt0.asm`, который принимает reset, очищает IDATA, задаёт стек и вызывает
C `main()`.

На SDCC 4.6.0 новый бинарник занимает `0x1105` байт до дополнения `FF` до `0x2000` и
имеет SHA-256
`18426a37cd511b902de052317bef04c926b7602f9efcf3b4f3b22d53ec23fe3e`.
`make verify` проходит и теперь отдельно запрещает inline assembly, проверяет набор
модулей, машинную форму C-задержки, raw-I2C setup, выбор recovery до SPI и прежний ABI
трёх реальных таблиц. Этот результат пока **статический**: рефакторированный бинарник
не записывался в монитор. До аппаратного reset обеих веток доказанным рабочим эталоном
остаётся предыдущая установленная версия.

### Аудит назначений GPIO в recovery (2026-09-13)

Полная карта известных и исследованных выводов именно платы монитора ведётся в
[`gpio.md`](gpio.md); здесь оставлены только линии, нужные первичному загрузчику.

Повторная проверка исходных разборов и живых журналов показала, что говорить о
точном назначении **всех** GPIO из cold-таблицы нельзя. Четыре линии установлены
функционально достаточно надёжно:

| GPIO | Проверенный смысл | Граница доказательства |
|---|---|---|
| bank 3 bit 2 | выбор USB-B upstream для VL211 | отдельное снятие убирало VL211 и U7005, возврат перечислял оба; линия находится в `UsbModeSelect` |
| bank 10 bit 4 | reset VL211 и downstream-тракта | отдельный импульс убирал и возвращал оба устройства; Main формирует тот же импульс `1→0→1` |
| bank 4 bit 4 | отдельное разрешение VL211 | снятие убирало VL211 и подключённый через него U7005; отдельность подтверждена тем, что bank 13 bit 5 выключает только U7005; power/reset/enable не различены |
| bank 13 bit 5 | отдельное разрешение U7005 | снятие DATA или REG3 убирало только U7005 при живом VL211; power/reset/enable не различены |

Для bank 4 bit 7 и bank 13 bit 0 доказана парная смена между active и power-save
в коде Main, но точная электрическая функция не измерена. Bank 6 bit 7, bank 7 bit 0,
bank 5 bit 4 и bank 13 bit 7 входят в скопированное состояние либо последовательность
Main; индивидуального назначения для них нет. Отдельные опыты лишь показали, что
bank 6 bit 7, bank 5 bit 4 и bank 13 bit 7 после полной инициализации не управляют
видимостью USB-устройств. Сильная выходная единица по `REG3` измерена только на
GPIO8.0 ([нагрузочный опыт](gpio.md#reg3-cn4008)); для bank 4, bank 13 и остальных
банков назначение `REG3` не измерено.

Эта граница теперь выражена и в исходнике. `gpio.c` содержит единственное отображение
номера `bank.bit` на XDATA. `recovery.c` вызывает
`gpio_configure(GPIO_VL211_USB_B_SELECT, GPIO_OUTPUT_HIGH)` и аналогичные операции по
смысловым именам; адреса регистров и маски туда больше не передаются. Неопознанные
соседние выводы не получили вымышленных имён: полные `REG3/DATA/DIR` байты сохранены
отдельными дословными таблицами, потому что именно такая последовательность прошла
аппаратную проверку. Verifier фиксирует обе таблицы, наличие именованных GPIO и запрет
обхода pin-level API из `recovery.c`.

## Выбор банка джойстиком в свободном загрузчике (2026-09-15)

В `bootloader-libre` ранняя выборка направления теперь выбирает таблицу разделов:
вверх (`direction 4`) — `CODE:0x7000`, вниз (`direction 3`) — `CODE:0x6000`.
Остальные значения сохраняют штатное правило `CODE:0x7FFF == 0xAA`; вправо
(`direction 1`) по-прежнему уводит в автономный ISP до обращения к flash.
Маркер не перезаписывается, поэтому override действует только на текущий старт.

Это использует два ранее подтверждённых контракта: карту направлений
[раннего АЦП](buttons.md#опрос-из-bootloader-libre) и штатные таблицы слотов (§5–6
выше). Банк STBC передаётся через EAR, остальные адреса — через Share Structure
из той же выбранной таблицы. Простого изменения EAR без смены таблицы недостаточно:
оно оставило бы другим ядрам адреса прежнего слота. Для штатной раскладки таблица
`6000` описывает нижний банк, `7000` — верхний; произвольные или повреждённые таблицы
загрузчик по-прежнему не валидирует.

**Проверено на хосте:** сборка SDCC, полный `make verify`, все 65536 сочетаний
байтов маркера и направления, 1536 исполнений настоящей входной функции до записи
F1D либо входа recovery с подменёнными периферией и CODE/XDATA. Эти исполнения
проверяют сохранение одной выборки, банк, адрес/размер STBC и все байты общего блока
по реальным таблицам из дампа U4002. Статическая проверка учитывает сохранение R7
вокруг вызовов после выборки. Код занимает `0x11CA` байт, файл дополнен до `0x2000`;
SHA-256: `28b163cb232c6cc198451c676df569f7194c12030399d428987a579d9a566137`.

**Установка 2026-09-15:** новая сборка записана в банк 0, `0x0000..0x1FFF`;
полное чтение 32 КиБ через 4A подтвердило образ и неизменность `0x2000..0x7FFF`,
включая обе таблицы и маркеры. Резервная копия и журналы (не опубликовано).
После установки монитор был оставлен в ISP. Позднее 2026-09-15 владелец подтвердил
все четыре режима; журнал для вверх показывает запуск обоих Leon2 и базу Main
`01108000`. Одновременно обнаружен отказ следующего SW4101 после банка 1 —
[наблюдение и разбор](#bank1-sw4101-reset).

## Проверка режимов и отказ SW4101 после банка 1 (2026-09-15)

**Первичное свидетельство — сообщение владельца**, а не автоматически снятый
нами UART-захват: дословный текст (не опубликовано).
Проверялась установленная сборка `99942d8`, SHA-256
`28b163cb232c6cc198451c676df569f7194c12030399d428987a579d9a566137`.

| Ввод при старте | Результат по проверке владельца |
|---|---|
| Без отклонения | Обычная загрузка |
| Вправо | ISP загрузчика |
| Вниз | Загрузка по таблице `0x6000` |
| Вверх | Загрузка по таблице `0x7000` |

Для вверх прислан лог: `direction 4 adc CA`, `quad read verified`,
`flash bank 01`, `starting stbc-main from table 7000`, запуск Main/Sub и
`FE2P_SetLeon2BaseAddress 01108000`. Последняя строка независимо согласуется с
адресом Main в верхнем банке: `0x01000000 + 0x00108000`.

**Отказ воспроизведён владельцем:** после загрузки верхнего банка SW4101 больше
не возвращает загрузчик — нет UART и реакции монитора, независимо от желаемого
режима. Обесточивание восстанавливает работу загрузчика. Число повторов и точные
длительности удержания не сообщены. В ответ на уточнение владелец сообщил, что
уже обесточил монитор и вернул обычную работу. Поэтому значение EAR именно в
состоянии отказа в этом сеансе не измерялось; повторного аппаратного опыта не было.

### Что подтверждает гипотезу сохранения EAR

1. **EAR — состояние внешней flash, а не скалера.** GD25Q256E Rev1.1, §6.2
   (стр. 17) определяет volatile A24; §7.6 (стр. 25) устанавливает сброс EAR в 0
   при подаче питания и software/hardware reset **самой микросхемы flash**.
   Сброс другого чипа не является таким событием.
   Локальный даташит (не опубликовано).
2. **SW4101 подтверждён как reset скалера**, но соединение с RESET# U4002 и
   команда `66/99` перед первичным чтением при SW4101 не доказаны.
   Наблюдение «сбросил монитор» само по себе не доказывает очистку EAR.
3. **Начало банка 1 действительно отличается от первичного загрузчика.** В двух
   независимых чтениях до нынешних нажатий (4A и legacy) первые 512 байт по offset 0
   банка 1 совпали между собой и с `id=0x01` по file `0x10000` обоих FW.034/FW.037.
   Первые байты `02 B6 86` — `LJMP 0xB686`, reset-вектор STBC Main, подтверждённый
   листингом Ghidra. У штатного первичного загрузчика вектор `02 13 F7`; у libre —
   `02 00 30`. Это не пустые `FF`, а начало другого образа.
   Побайтовая сверка и источники (не опубликовано).
   Проверены только эти 512 байт, а не весь boot region; когда и чем такое
   содержимое попало в банк 1, не установлено. Заводской дамп `u4002_a.bin`
   содержал там штатный первичный загрузчик и не описывает нынешнее состояние.
4. **ROM копирует начало flash до исполнения libre.** По прежнему SPI-захвату
   при холодном старте ROM читает 64 КиБ от 24-битного адреса 0 в CODE (§ выше).
   Если при следующем SW4101 этот же путь исполняется при EAR=1, источник будет
   `0x01000000`, а не `0x00000000`. Выполнится чужой вектор без раннего UART libre.

Таким образом, последовательность «EAR=1 сохраняется → ROM читает верхний boot
region → libre не исполняется» **хорошо объясняет наблюдение, но ещё не доказана
прямым измерением после SW4101**. Не исключены сохранённые настройки SPI/адресного
режима или другая ветка reset на стороне скалера. Одна тишина UART их не различает.
Полный образ текущих верхних 64 КиБ и источник дальнейшего перехода `0xB686`
на этом этапе также не проверены, поэтому утверждать точное место зависания STBC
нельзя. **Последующее чтение из ISP подтвердило физический адрес и отсутствие
startup по `0xB686` — [результат ниже](#bank1-live-identity).**

### Почему имеющаяся защита не спасает

В `bootloader.c` проверка `flash_get_bank()` находится **после** startup, настройки
UART и баннера `bootloader-libre: start`. При EAR≠0 она вызывает WREAR(0), печатает
`reset flash bank; power cycle required` и остаётся в `wait_forever()`.
Если ROM уже прочитал другой код, эта защита вообще не исполняется. Если бы отказ
дошёл именно до неё, ожидались бы баннер и сообщение, которых владелец не видит.
Это аргумент в пользу более раннего отказа, не абсолютное доказательство: ранняя
настройка UART сама зависит от состояния скалера.

Строка `0x4570[5] toggle ==> warm Reset!!` из успешного лога относится к STBC Main
и переключению D570.5; оба вызывающих продолжают выполнение после неё (§ выше,
`docs/stbc-launch.md`). Она не доказывает новый цикл ROM → bootloader и не является
контрпримером отказу физического SW4101.

Проверка, которая различит гипотезы: сохранить EAR без записи `0F/C5` сразу после
неудачного SW4101, если сервис доступен, либо снять SPI от нажатия до остановки с
видимыми командами reset/выбора банка и данными первого чтения. Опкод 4A для первой
части не подходит: он **сам выбирает банк**, уничтожая исходное свидетельство.
После обесточивания такое измерение также уже не относится к состоянию отказа.

**Вывод для исправления:** гарантировать правильный первый код нужно до выбора
таблицы. Простое копирование нынешних 8 КиБ libre в банк 1 не решает задачу целиком:
при EAR=1 его существующая защита всё равно остановится после WREAR(0), а таблицы
CODE останутся копией выбранного ROM банка. Нужны согласованный ранний этап в
обоих банках и проверенный возврат к нижнему boot region/таблицам либо доказанный
reset самой flash до чтения ROM. Возврат EAR в обычной прошивке перед «плановым»
reset не покрывает внезапное нажатие SW4101. Код и flash в этом исследовании не
менялись; исправление пока не устанавливалось.

### Свежее чтение 0x01000000: заменён первый сектор верхнего boot region

После уточнения владельца монитор вручную переведён в ISP. Прочитаны 64 КиБ
с физического `0x01000000`; первые 512 байт независимо сверены тремя путями:

- прямой SPI `0B 00 00 00 00` после WREAR(1) и подтверждения RDEAR=1;
- расширение USB 4A с абсолютным адресом `0x01000000`, без `Bridge.read_flash()`;
- SPI `13 01 00 00 00` — отдельная команда чтения с четырёхбайтовым адресом,
  **при EAR=0**, без смены адресного режима flash.

Все три чтения совпали. Тем самым версия, что данные STBC Main появились лишь
из-за ошибки преобразования EAR/адреса в хостовой обёртке, исключена этими проверками.
Контроль в нижнем банке вернул вектор libre `02 00 30`.

**Установлено по полному дампу:** `0x01000000..0x01000FFF` побайтно совпадает с
первыми 4096 байтами STBC Main из FW.034, file `0x10000..0x10FFF`.
Следующий сектор `0x01001000..0x01001FFF` совпадает с прежним первичным загрузчиком,
file `0x1000..0x1FFF`. Это смешанный boot region, а не целый образ STBC Main.
Вектор `02 B6 86` ведёт на CODE `0xB686`, но весь диапазон физической flash
`0x01008000..0x0100FFFF`, включая `0x0100B686`, заполнен `FF`.

При копировании этих 64 КиБ ROM в CODE переход уйдёт в область `FF`, а не в
startup Main или libre. Это конкретный дефект содержимого верхней загрузочной
области и достаточное объяснение отсутствия баннера **при условии чтения ROM из
банка 1**. Само сохранение EAR=1 после неудачного SW4101 ещё не измерено.
Когда и какой записью заменён первый сектор, не установлено. Адрес `0x00100000`
из вопроса владельца — 1 МиБ, а начало верхнего банка — `0x01000000`, 16 МиБ;
старый полный дамп содержал по последнему адресу правильный штатный загрузчик.

Дамп, два сценария, исходные USB-пакеты и сравнение (не опубликовано).
EAR возвращён в 0, монитор оставлен в ISP. Flash и прошивки не записывались.
