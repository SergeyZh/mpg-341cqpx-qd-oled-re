# Чтение USB Flash из bootloader: стек `id=0x02`

Дата: 2026-09-07. Опорный образ — FW.037, но весь раздел побайтово одинаков
в FW.023, FW.034 и FW.037. Это документация статически восстановленного тракта,
**не отчёт об успешном чтении флешки на мониторе** и не готовый recovery patch.

## 1. Результат и граница доказанного

В `id=0x02` есть самостоятельный USB Host: перечисление устройства, control/bulk
передачи через EHCI-подобный FOTG, Bulk-Only Transport (BOT), SCSI `READ(10)`,
разбор FAT32/exFAT/NTFS и загрузка файла в DMA-память. Для чтения секторов не нужны
ни `.IMG`, ни `NVTSC_IMG`, ни ISP ROM: они появляются **выше** блочного драйвера.

Минимальный полезный срез — `C60E` (LBA → DMA) и `CBD9` (LBA → локальная память
8051). Это функции **второго 8051**, а не команды основного загрузчика. `LCALL C60E`
на первом 8051 попадёт в его собственный CODE, не в AUX.

```text
bootloader / первый 8051
  └─ загрузка и запуск сохранённого AUX + настройка DMA
       └─ второй 8051: B5B4 → A6FA/B706 → 467E
            └─ C60E READ(10) → 76B4 BOT → 8A0E/69DA qTD → USB
                 └─ DMA → ABCE, окно CD30…CD38 → сектор в XDATA
                      └─ FAT reader → байты файла → отдельная проверка образа
```

Подтверждено листингом Ghidra и независимым чтением констант из бинарника:

- ABI чтения сектора, DMA-единицы адресации, порядок байтов и регистровых операций;
- таблица инициализации контроллера, запросы enumeration, CDB/CBW;
- явный начальный режим `2`, а не Host и не неинициализированный мусор;
- отсутствие надёжного запрета загрузки при неверной `NVTSC_IMG`: есть конкретный
  путь, возвращающий успех без этой сигнатуры;
- ограничения штатных процедур, перечисленные ниже.

На аппаратуре ранее подтверждены отдельное ядро, его запуск через `F1E0`, обработка
`F198` и включение Host командой `70` — [usb-isp.md](usb-isp.md). **Не подтверждены**
подключение обычных USB-A к этому Host, передача сектора, допустимая DMA-база при
холодном старте и работа без инициализации основной прошивкой. Поэтому утверждать
«добавить вызов AUX — и восстановление через USB-A заработает» пока нельзя.

## 2. Как воспроизвести разбор

Раздел: файл `0x020000…0x02E551`, длина `0xE552` = 58 706, CODE base `0`.
SHA-256 этих байтов:

```
bed2d9922e6e98990573dee3066d5871806e4ecd703a48d184c2135be128e592
```

Он совпал у обоих файлов MSI и у заводского FW.023 в сохранённом дампе
`flash/u4002_a.bin`, смещение `0x1020000`. Дамп читался, не изменялся.

```sh
.venv/bin/python tools/usb_flash_map.py MSI_MPG_341CQPX_QD-OLED_FW.037_0225.bin
.venv/bin/python tools/usb_flash_map.py MSI_MPG_341CQPX_QD-OLED_FW.034_D728.bin
.venv/bin/python tools/usb_flash_map.py flash/u4002_a.bin --offset 0x1020000
```

Скрипт проверяет хеш до адресного разбора, декодирует Keil startup table, печатает
Host init и SETUP-шаблоны, проверяет байты ветки ложного успеха. Это **не эмуляция**
8051 и не проверка USB. Для вырезанного `out/stbc_aux_020000.bin` нужен `--offset 0`.

Старые листинги AUX неполны. `AuxUsbListing.java` восстанавливает достижимый код от
reset, обрабатывает inline store `34ED`, switch helper `353E`, таблицу `bRequest`
на `53AE` и таблицу generic memcpy на `30D3`. Результат: **32 985 инструкций,
103 достижимых inline store, 3 inline switch**. Это не заявление о достижимости
всех байтов образа; произвольные вычисляемые переходы автоматически не доказываются.
Скрипт перестраивает анализ CODE, но не меняет байты. Старые имена/границы функций
Ghidra могут быть неверны; доказательством служат инструкции и переходы.

```sh
# JAVA_HOME — JDK 21+, например JetBrains Runtime из IntelliJ (см. tools/ghidra_import.sh)
~/ghidra_12.0.2_PUBLIC/support/analyzeHeadless "$PWD/ghidra" nt68503 \
  -process stbc_aux_020000.bin -noanalysis -scriptPath "$PWD/tools/ghidra_scripts" \
  -postScript AuxUsbListing.java "$PWD/out/usb_flash_aux.asm"
```

Для отдельной процедуры, например:

```sh
awk '$1 >= "CODE:c60e" && $1 < "CODE:c6fa"' out/usb_flash_aux.asm
```

Ниже адрес без префикса в столбце «CODE» — адрес инструкции AUX; `X:` — его
локальная XDATA. Названия функций — исследовательские, см. [CSV](../names/stbc_aux_usb.csv).

## 3. Запуск, память и связь с bootloader

Сохранённый AUX загружается во **второе кодовое окно**: `F168/F169=0` (адрес
назначения CODE), `F16A…F16C` = LE24 источник во SPI, `F16D…F16F` = LE24 длина
`52 E5 00`; штатный загрузчик окна из `id=01` записывает `F166=FF`, затем `F167=87`
и ждёт `F167==0`. Для обычного раздела источник `00 00 02`, но это смещение
**в выбранном банке SPI**, не полный 32-битный адрес. Банк и более ранние platform
gate/reset нельзя игнорировать. Раскладка и наблюдение переноса —
nt68503-hardware.md §4.1 (не опубликовано), исходный вызов —
[usb-isp.md](usb-isp.md) § «Кто и когда поднимает id=0x02».

Завершение переноса не запускает ядро. Ранее проверенная на живом мониторе
последовательность освобождения reset — `F1E0=01`, затем `F1E0=02`; это отдельный
шаг после загрузки. Для cold recovery всё равно нужны проверки питания/тактирования
USB и DMA, перечисленные ниже. Здесь эту последовательность на аппаратуре не повторяли.

### 3.1. AUX не стартует хостом сам

Reset `0000 → D426`: очистка IDATA `01…7F`, `SP=61`, затем интерпретатор
инициализации `D46D`, таблица `C36D…C44D`, затем `B5B4`.

| Запись в CODE | Что устанавливает |
|---|---|
| `C36D`, `C371` | `X:09CE=81`, `X:09CF=81`: состояния каналов |
| `C375` | `X:09CD=02`: предыдущий режим |
| `C3F1: 41 09 C6 02` | **`X:09C6=02`: текущий режим** |
| `C3EA` | `X:08C9=00000000`: DMA-база ещё не задана |
| `C3F5` | `X:09CC=FF`: параметр настройки блока `505x` |
| `C38B` | `X:08DE=00000001`: следующий BOT tag |
| `C392` | 80 байт SETUP-шаблонов → `X:07D9…0828` |

Начальный `mode == previous == 2`; ветка `Host Mode Init` не исполняется.
Команда `70` меняет mode: `0` Host, `1` Device, `2` вне этих обработчиков.
Device — Billboard, не Mass Storage; для чтения накопителя он не нужен.

`B5B4` настраивает собственные UART/SFR, сбрасывает блоки через `CD0A/CD2A`, меняет
`F101`, обслуживает `F198`. При смене на Host публикует `F190/F192=81`, выбирает
поочерёдно канал 0 и 1 (`A6FA`) и вызывает `B706`. Далее опрашивает каждый канал
через `6E16`, кроме случая команды канала `21`.

### 3.2. Почтовый ящик

`F198` — команда, `F199…F19F` — параметры/ответ. Записывать параметры **до** команды,
ожидать `F198==0` с собственным deadline; это подтверждение завершения обработчика,
а не гарантия успеха операции. Диспетчер — `A36C`.

| Команда | Контракт |
|---|---|
| `31` | `F19C,D,E,F` составляют BE32 `X:08C9` через `CFA5`; `X:09CC=F199` |
| `70` | `X:09C6=F19A` |
| `11` | `D393(F19E,F19F)`, настройка UART/программных задержек |
| `52…58` | шесть байт имени из `X:011D + 6*(cmd-52)` → `F19A…F19F` |
| `59` | `X:0156=BE16(F19A,F19B)`, параметр выбора файла |
| `5A` | размер файла `X:0109` → **LE32** `F19B…F19E` |
| `5B` | адрес начала файла `X:0717` → **LE32**, в единицах 32 байта |
| `60` | младшие **24 бита** `X:0113` → `F19B…F19D`, не 32 бита |

Для Host: сначала выделить память и задать `31`, затем `70/0`. Значение `F199`
нельзя выбирать по названию предполагаемого поля: `DA02` использует его для
настройки `5050…5052` (ниже), полного аппаратного смысла пока нет.

Команды портов отдельные: `F191` для 0 и `F193` для 1; состояния `F190/F192`.
`6E16 → 722D` публикует состояние и обнуляет ненулевую потреблённую команду.
`81/82` — ожидание подключения; `83` — инициализация/enumeration; сочетание класса
`08` и протокола `50` ведёт в `8CDC` (mount) и состояние `96`.
Команда `46` в `96` запускает файловую загрузку `9D97`; её `97` не доказывает
целостность данных. Для собственного секторного reader этот автомат ФС не нужен.

**Готовой команды «прочесть произвольный LBA» в таблице `A374` нет.** Она вызывает
перечисленные обработчики, а `C60E/CBD9` вызываются внутренним файловым кодом.
Практичный вариант расширения — собственный обработчик AUX с явным LBA, длиной,
DMA-адресом и статусом. Это предложение, ещё не реализованный протокол.

Локальная XDATA второго 8051 не совпадает с XDATA первого. Служебное чтение `09C6`
через основной I²C-приёмник читает **другую память**. Через общий ящик можно передавать
параметры, но нельзя этим способом напрямую заполнить `X:0931` AUX.

### 3.3. DMA: различать адрес в блоках, адрес в байтах и CPU-адрес

`A6FA` вычисляет следующие адреса. Пусть `B = X:08C9`, `p=0/1`, `S=B+p*0x380`.
Все величины в среднем столбце — **номера 32-байтных блоков**. `A=32*B` — адрес
в адресном пространстве DMA; это ещё не доказанный адрес в AHB/CPU DRAM.

| XDATA | Вычисление | Байтовое смещение от `A` |
|---|---|---|
| `07D5` | `S` | `p*7000`: секторный scratch |
| `08BD` | `S+280` | `p*7000+5000`: SETUP/CBW/CSW scratch |
| `08C1` | `S+2A0` | `p*7000+5400`: четыре QH по 64 байта |
| `08C5` | `S+2A8` | `p*7000+5500`: восемь qTD по 32 байта |
| `08B4` | `S+300` | `p*7000+6000`: periodic list |
| `0717` | `B+700` (`D6D1`) | `E000`: начало буфера файла |

Числа в таблице шестнадцатеричные. По портам зарезервировано `0x7000` байт;
файловая загрузка начинается после обоих. При сохранении штатной раскладки нужна
база, выровненная как минимум по 4 КиБ, и доступный диапазон минимум `0xE000` байт
для двух каналов, **плюс весь загружаемый файл** при использовании `9D97`.
Для своего потокового reader достаточно отдельных проверенных DMA scratch/QH/qTD;
весь файл в RAM держать не обязательно.

`A6FA` также сохраняет/восстанавливает контексты: 46 байт `082A` ↔ `0858+p*2E`,
39 байт `075C` ↔ `0783+p*27`, индексы qTD `08CD/CE/CF` через массивы `08D0…D5`.
Нельзя менять только `075B`, минуя переключение контекста.

`DA02`, вызываемый из Host init, дополнительно настраивает общий блок:

```c
if (X[0x09cc] < 0x20) {
    X[0x5050] |= 0x20;
    X[0x5052] = ((X[0x5052] | 0x60) & 0xe0) | X[0x09cc];
    X[0x5051] = 0x20; delay(1); X[0x5051] = 0;
} else {
    X[0x5050] &= ~0x20;
    X[0x5052] = 0x10;
}
```

Это точные операции MSI, **не доказательство**, что поле означает банк DRAM или
частоту. Настройку DDR, трансляцию DMA→физическая память и пригодность этой памяти
до Main нужно закрыть отдельно; см. ddr-init.md (не опубликовано),
[boot-sequence.md](boot-sequence.md) и
аппаратную адресацию (не опубликовано). Слепое `B=0` может затереть занятую память.

## 4. Доступ к USB-регистрам и DMA FIFO

### 4.1. Индексное окно контроллера

`9B91`: читать u32, аргумент `R6:R7` = offset, результат `R4:R5:R6:R7` (BE).
`B317`: писать u32, offset так же, значение BE32 в `X:0992…0995`.
Маска offset — `0x1FF`; `p=X:075B` выбирает окно `W=CD00+p*20`.

| Регистр | Назначение по обращениям |
|---|---|
| `W+0` | команда: `40` read / `80` write, бит 4 = offset bit 8; бит 0 опрашивается |
| `W+1` | младшие 8 бит offset |
| `W+2…5` | записываемое значение, младший байт первым |
| `W+6…9` | прочитанное значение, младший байт первым |
| `W+A` | reset/control обёртки; это не регистр по offset `0A` внутри FOTG |

```c
u32 hc_read(u16 off) {
    off &= 0x1ff;
    X[W+1] = off;
    X[W+0] = 0x40 | ((off >> 4) & 0x10);
    wait_until(!(X[W+0] & 1), deadline);
    return le32(X[W+6], X[W+7], X[W+8], X[W+9]);
}
void hc_write(u16 off, u32 value) {
    off &= 0x1ff;
    write_le32(W+2, value);
    X[W+1] = off;
    X[W+0] = 0x80 | ((off >> 4) & 0x10);
    wait_until(!(X[W+0] & 1), deadline);
}
```

Deadline здесь — требование к новому драйверу. Оригинал делает до десяти проходов
с `E44B(1)` и не возвращает отдельной ошибки timeout. `DFBE` ставит биты маски
`X:0988`, `DDBB` сбрасывает их (read → AND с дополнением маски → write).

Абсолютные offsets внутри FOTG, **не относительно operational base**:

| Offset | Интерпретация |
|---|---|
| `010` | USBCMD: Run bit 0, Reset bit 1, Async Schedule Enable bit 5 |
| `014` | USBSTS: ошибки/события, Async Schedule Status bit 15 |
| `018` | USBINTR |
| `024` | PERIODICLISTBASE |
| `028` | ASYNCLISTADDR; `B308` переводит адрес из блоков в байты |
| `030` | PORTSC: connection bit 0, reset bit 8 |
| `080` | OTGCSR; `8F95` использует bits 23/22 для HS/LS, иначе FS |
| `088` | OTG interrupt enable |
| `0E0` | значение из Novatek init; смысл полей не установлен |
| `100` | device control, используется и при переключении на Host |

Названия стандартных полей сопоставлены с первичным исходником
[Linux FOTG210, v6.12](https://github.com/torvalds/linux/blob/v6.12/drivers/usb/fotg210/fotg210-hcd.h).
Совпадение регистров/QH/qTD подтверждает семейство, но не тождественность всех
нестандартных регистров NT68503 опубликованному FOTG210.

### 4.2. Чтение/запись памяти через `CD30…CD38`

`ABCE` читает память, `B1A9` пишет память. **Запись здесь — в DMA RAM, не в USB Flash.**
Общее окно одно, без прибавки `p*20`.

| Аргумент | Контракт |
|---|---|
| `R4…R7` | адрес DMA в блоках по 32 байта, BE32 |
| `R3:R2:R1` | generic pointer: `R3=0` IDATA, `1` XDATA, `FF` CODE для источника |
| direct `0F` | количество 32-байтных блоков |
| direct `10` | `1`: прямые байты; `0`: развернуть байты каждой четвёрки |

Для **одного** блока:

```c
void dma_read32(u32 block, u8 dst[32], bool direct_order) {
    write_le32(0xcd35, block);       // CD35,36,37,38
    X[0xcd30] = 0x80;
    X[0xcd32] = 0x80;
    wait_until(X[0xcd33] == 0x80, deadline);
    for (unsigned j=0; j<32; j++)
        dst[direct_order ? j : (j ^ 3)] = X[0xcd34];
}
void dma_write32(u32 block, const u8 src[32], bool direct_order) {
    write_le32(0xcd35, block);
    X[0xcd30] = 0x80;
    for (unsigned j=0; j<32; j++)
        X[0xcd31] = src[direct_order ? j : (j ^ 3)];
    // В B1A9 нет дополнительной записи CD32 и ожидания CD33.
}
```

Исходный `ABCE` ограничивает ожидание 250 проходами, но после исчерпания всё равно
читает FIFO и не сообщает timeout. Для новых функций нужна явная ошибка.

В обоих циклах адрес обновляется `address += i`, а не `base+i`:
`base, base+1, base+3, base+6…` (`ABCE` и `B1C8…B1DB`). Это наблюдаемый дефект при
`count>=3`. Не использовать их как произвольный многоблочный memcpy.
Для 512 байт делать **16 отдельных вызовов по одному блоку**. Так поступает `CBD9`.
Для QH штатный count=2 ещё даёт правильные соседние блоки.

Служебные обёртки: `E36D` читает один блок в IDATA `22…41` с разворотом слов;
`E362` предварительно берёт block-address из XDATA по DPTR. `E193` пишет обратно.
`999F` снова разворачивает слова при копировании в обычный байтовый буфер.
Итого: сектор в `X:01E6` имеет нормальный on-disk порядок, QH в IDATA — BE32,
QH в DMA — LE32. **Не добавлять третью перестановку.**

## 5. Host init, QH/qTD и enumeration

### 5.1. Таблица инициализации

`B706` исполняет записи по 7 байт с `C9D2`: BE16 operation/offset, BE32 value,
u8 delay. High nibble operation: `0` write, `1` set bits, `2` clear bits;
`FFFF` завершает таблицу. Здесь все записи — write:

| CODE | Offset | Value | `E44B` argument |
|---|---|---|---|
| C9D2 | 100 | 00000020 | 5 |
| C9D9 | 0E0 | 00AE006E | 5 |
| C9E0 | 100 | 00000022 | 5 |
| C9E7 | 088 | 00001F30 | 5 |
| C9EE | 080 | 000E0000 | 5 |
| C9F5 | 080 | 000E8000 | 5 |
| C9FC | 080 | 000E0000 | 5 |
| CA03 | 080 | 000E0010 | 5 |
| CA0A | 010 | 00080B02 | 50 |
| CA11 | 010 | 00010900 | 5 |
| CA18 | 040 | 0000000D | 5 |
| CA1F | 018 | 00000017 | 5 |
| CA26 | 010 | 00010901 | 5 |
| CA2D | 030 | 00000903 | 250 |
| CA34 | 030 | 00000803 | 5 |

Последняя колонка десятичная; это **аргументы программной задержки, не измеренные
миллисекунды**. `E44B` четырежды вызывает `E478` на единицу, а счётчик `E478`
берётся из `X:09D0` (startup `1200`). `D393` может его менять. Нельзя переносить
эти числа на другую частоту 8051 как готовые USB-тайминги.

После таблицы задаются индексы `08CD=0`, `08CE=4`, `08CF=6`, указатели staging
`08BC=0829=22`, выполняется `DA02`; адрес устройства для каждого порта начинается
с `3`. Глобальные сбросы `CD0A/CD2A` и `F101` до этого — в `B5B4`, а повторные
сбросы при ошибке — в `6E16`. Одна таблица не заменяет полный cold init.

### 5.2. Формат DMA-дескрипторов

`467E` создаёт восемь qTD и четыре QH. `8F95` собирает QH; адрес QH слота `n`
равен `32*(X:08C1+2*n)`. Слоты 0/1 — control, 2/3 — bulk. Это **не номера USB
endpoint**. Реальный endpoint number и направление извлекаются из дескрипторов.

| Структура | Смещение байт | Поле |
|---|---|---|
| QH | 00 | horizontal link, тип QH=2 в младших битах |
| QH | 04 | address, endpoint, speed, DTC, head, max packet |
| QH | 08 | endpoint capabilities |
| QH | 0C | current qTD |
| QH | 10 / 14 / 18 | next / alternate / token overlay |
| QH | 1C…2C | пять buffer page pointers overlay |
| qTD | 00 / 04 | next / alternate; bit 0 = terminate |
| qTD | 08 | token: toggle bit 31, bytes bits 30:16, IOC 15, CERR 11:10, PID 9:8, status 7:0 |
| qTD | 0C…1C | пять buffer page pointers, первый содержит offset внутри 4 КиБ |

Все слова в DMA little-endian. PID: OUT=0, IN=1, SETUP=2; Active bit 7,
Halted bit 6. Структуры совпадают с определениями в упомянутом Linux header;
их заполнение здесь независимо видно в `467E`, `8F95`, `8A0E`, `69DA`.

`8A0E` — bulk submit: `R7` = QH slot (2/3), `R4:R5` = u16 длина,
`R3:R2:R1` = указатель на пять BE32 адресов страниц, `X:0960` = offset,
`X:0964` = направление (0 OUT / 1 IN). qTD берётся из `08C5` с индексом
`08CE` либо `08CF`; это состояние очереди, не постоянный адрес дескриптора.

`69DA/69E5` выполняет очередь с dummy qTD: выключает Async Schedule, ожидает ASS=0,
переносит подготовленный qTD в старый dummy, связывает новый dummy, включает
schedule, активирует token, опрашивает Active. После передачи подтверждает USBSTS,
очищает overlay и снова останавливает schedule. В ожиданиях есть счётчики порядка
101 прохода и накопители ошибок `07D3+port`, но универсального результата
`status + transferred_bytes` наружу нет. Новый reader должен возвращать их явно.

### 5.3. Control и последовательность запросов

`5219`: `R7` — control QH slot (0 для SET_ADDRESS, затем 1), `R3:R2:R1` — generic pointer на
8 байт SETUP, `X:0905…0906` — BE16 длина данных. Принятые данные копируются в
`X:071B`. SETUP помещается в scratch `08BD`, qTD получает PID SETUP и длину 8;
для GET_DESCRIPTOR идёт IN DATA1 и нулевой OUT DATA1 status. SET_ADDRESS и
SET_CONFIGURATION без данных завершаются IN status. Ветвление по `bRequest`
на `53AE` важно: эту таблицу прежний Ghidra-анализ пропускал.

Это специализированная процедура под шаблоны SDK, **не общий control API**.
Например, копирование IN-ответа использует один 32-байтный staging-блок.
Для своего перечислителя нужны контроль длины и полноценный цикл DATA.

`467E` делает:

1. SET_ADDRESS, сначала адрес `3`; затем исправляет QH (`B45F`).
2. GET_DESCRIPTOR(Device) на 8 байт, обновление EP0 max packet по byte 7;
   повтор на `bLength` (обычно 18).
3. GET_DESCRIPTOR(Configuration) на **32 байта**. Не обход произвольного
   `wTotalLength`: class берётся с offset 14, protocol с 16, адреса endpoint
   с 20 и 27. Предполагаются конфигурация, первый interface и два обычных
   endpoint подряд. Composite и нестандартная раскладка не покрываются.
4. Назначает `X:0856` = IN QH slot и `0857` = OUT QH slot по bit 7 первого
   endpoint. Сами номера endpoint берутся из младших четырёх бит.
   Первоначальный max packet bulk QH — **512**, а не произвольное значение
   `wMaxPacketSize` (`48E0` и соседняя настройка второго bulk QH).
5. SET_CONFIGURATION со значением **1**, GET_MAX_LUN для **interface 0**.
   BOT ниже всегда ставит LUN=0; поддержки произвольного LUN из ответа это не даёт.
6. TEST UNIT READY; при ошибке REQUEST SENSE (18 байт), ожидания и повторы
   до десяти попыток. Затем INQUIRY (36 байт), READ CAPACITY(10) (8 байт).

READ CAPACITY отправляется в `4E0D…4E2F`, затем эта ветка завершается: геометрия
не передаётся в `C60E`, где размер сектора жёстко 512. Новому reader следует
разобрать ответ: первые четыре байта BE32 — последний LBA, следующие четыре —
BE32 размер логического блока; неподдержанный размер или ёмкость нужно отвергнуть.

Исходные SETUP-шаблоны (числа — байты на USB, поля u16 little-endian):

```
GET device       80 06 00 01 00 00 12 00   X:07F9, wLength меняется
GET config       80 06 00 02 00 00 08 00   X:07D9, wLength меняется на 32
SET address      00 05 03 00 00 00 00 00   X:07E1
SET config       00 09 01 00 00 00 00 00   X:07E9
GET MAX LUN      A1 FE 00 00 00 00 01 00   X:07F1
BOT reset        21 FF 00 00 00 00 00 00   X:0801
```

Наличие последнего шаблона не доказывает полноценное BOT Reset Recovery на каждом
пути ошибок. В образе есть отдельный hub-обработчик `BA96`; это не основание
считать произвольное дерево USB-хабов поддержанным. Для первого recovery target
целесообразно ограничиться непосредственно подключённым USB 2.0 HS BOT-накопителем.
Для нового стека лучше разобрать дескрипторы по `bLength/bDescriptorType`, проверить
interface `08/06/50`, взять настоящий configuration/interface/max packet.

## 6. BOT и точный примитив чтения сектора

### 6.1. SCSI → CBW → data → CSW

`76B4` строит CBW в `X:082A`. Командный блок начинается в `X:075C`,
`E1EB` обнуляет его 39 байт перед новой командой.

| XDATA | Значение |
|---|---|
| `0761` | длина CDB |
| `0762` | 2 = IN, 1 = OUT |
| `0763…0772` | CDB до 16 байт |
| `0773…0776` | длина данных BE32 |
| `0777…077A` | DMA-адрес данных **в байтах**, BE32 |
| `0780/0781` | результат; `0781` получает CSW status |
| `08DE…08E1` | монотонный tag, начальное значение 1 |

CBW на USB — 31 байт: `55 53 42 43`, LE32 tag, LE32 byte length,
flags `80` для IN, LUN `00`, CDB length, 16 байт CDB. Его `76B4` передаёт OUT,
затем делает data transfer по нужному bulk endpoint, затем принимает CSW по IN.
Приём CSW в оригинале тоже запрашивает **31 байт** через короткий вход `8A08`,
хотя сам CSW имеет 13; устройство должно завершить его коротким пакетом.
После чтения staging берётся byte status по логическому offset 12, tag увеличивается.

В пределах `76B4` до возврата видна передача этого status, но нет сравнения
сигнатуры CSW, возвращённого tag и residue с запросом. Для recovery нужно проверить
длину 13, `USBS`, tag, status и остаток, а при phase error выполнить корректное
восстановление транспорта. Это требования BOT, не доказанная функциональность MSI.
Источник формата и recovery: [USB-IF Bulk-Only Transport 1.0](https://www.usb.org/sites/default/files/usbmassbulk_10.pdf), §§5–6.

BOT Reset Recovery для нового драйвера: class-specific reset (`21 FF`, wIndex =
номер interface), затем CLEAR_FEATURE(ENDPOINT_HALT) для bulk IN и bulk OUT.
Состояние toggle/очереди должно быть согласовано с этим сбросом; простой повтор
старого qTD после phase error не заменяет recovery.

Пять page pointers позволяют покрыть максимум пять 4-КиБ страниц с учётом начального
offset. При переполнении массива оригинал печатает ошибку и зацикливается (`78D3`).
Для переноса без изменения кода разумный верхний предел — 16 КиБ на запрос при
проверенном выравнивании; первый опыт — один сектор 512 байт.

### 6.2. `C60E`: READ(10) в DMA

Вход: `R4:R5:R6:R7` = LBA32 BE; `X:0931` = BE32 длина **в байтах**;
`X:0935` = BE32 DMA destination **в 32-байтных блоках**.

```c
// Семантика оригинала, не готовый C ABI.
void aux_read10(u32 lba, u32 byte_count, u32 dst_block) {
    clear_command_39_bytes();
    cdb[0] = 0x28;
    put_be32(cdb+2, lba);
    cdb[8] = (byte_count / 512) & 0xff;
    // cdb[7] остаётся нулём!
    cdb_length = 10;
    direction = IN;
    data_length = byte_count;
    data_dma_address = dst_block << 5;
    bot_transfer();
}
```

Оригинал использует только младший байт sector count, хотя стандартное поле
двухбайтное. `>=256` секторов недопустимы; некратная 512 длина даёт рассогласование
CDB/CBW. Лимит страниц наступает ещё раньше. Это аргумент **не переносить функцию
без проверок** и не считать BPB bytes-per-sector произвольным.

Пример READ(10) LBA=0, один сектор: CDB
`28 00 00 00 00 00 00 00 01 00`; CBW data length=512.
LBA=1 меняет байт 5 на `01`. LBA и sector count в CDB big-endian, длина CBW
little-endian — это разные порядки в одной операции.
Опознание команд сверено с [USB-IF MSC Bootability](https://www.usb.org/sites/default/files/usb_msc_boot_1.0.pdf), разделом SCSI commands.

### 6.3. `CBD9`: READ(10) с копированием в XDATA

Вход: LBA в `R4…R7`; назначение generic pointer `R3:R2:R1`;
`X:0927…092A` = BE32 byte count. Процедура сохраняет указатель в `0924…0926`,
использует scratch `07D5`, затем копирует по одному DMA-блоку:

```c
void aux_read_to_local(u32 lba, pointer dst, u32 n) {
    X32BE[0x0931] = n;
    X32BE[0x0935] = X32BE[0x07d5];
    aux_read10(lba, n, X32BE[0x07d5]);
    for (u16 i=0; i<n/32; i++) {
        E36D(X32BE[0x07d5] + i);    // 32 байта → IDATA:22, reversed words
        copy_swap32(dst + 32*i);   // 9981/999F → нормальные байты файла
    }
}
```

Пример для штатного sector buffer `X:01E6…03E5`: записать
`X:0927=00 00 02 00`, поставить `R3=1,R2=1,R1=E6`, LBA в `R4…R7`, вызвать `CBD9`.
Предусловия: это исполняется **на AUX**, выбран и перечислен порт, настроены
DMA/QH/qTD; буфер не занят другим кодом. Процедура не reentrant; прерывать штатный
filesystem reader собственным вызовом нельзя.

Она копирует только `floor(n/32)*32` байт и не даёт полноценного результата чтения.
Для надёжного API дополнительно нужны status qTD/CSW и actual transfer length;
иначе после ошибки можно принять старое содержимое scratch за новый сектор.

## 7. Файловый слой и отделение от обновления

### 7.1. Что действительно делает mount `8CDC`

Сначала читает LBA0 в `01E6`. OEM bytes 3…10 сравниваются **посимвольно** с
`MSDOS5.0` (`E0B9`) или `NTFS    ` (`E0C1`). Каждый символ может совпасть с одним
из двух шаблонов; это эвристика VBR, не проверка типа FAT.
При несовпадении берётся LE32 по offset `1C6` — LBA **первого MBR-раздела**,
сохраняется в `0105`, и этот сектор читается как VBR. При совпадении `0105=0`.
Следствие: exFAT superfloppy не проходит эту эвристику как самостоятельный VBR.
Нет оснований считать этот участок GPT-reader или безопасным валидатором MBR.

Затем отдельная классификация OEM: `EXFAT` → `X:041C=1`, `NTFS` → `2`,
остальное → `0` и **поля FAT32 BPB**, а не универсальный FAT12/16/32.

| Поле | FAT32 | exFAT | Куда кладёт AUX |
|---|---|---|---|
| bytes/sector | LE16 VBR+11 | `1 << VBR[108]` | `042A` u16 |
| sectors/cluster | VBR[13] | `1 << VBR[109]` | `01DC` u16 |
| FAT offset, sectors | LE16 VBR+14 | LE32 VBR+80 | `0158` u32 |
| data/heap offset | reserved + FATs*LE32(VBR+36) | LE32 VBR+88 | `0405` u32 |
| root cluster | LE32 VBR+44 | LE32 VBR+96 | `0418` u32 |

`0414`, `0410`, `01DE` — текущий cluster, его смещение в FAT и сектор FAT;
`D5C5` сбрасывает курсор обхода. NTFS ветвь читает BPB и MFT через `AA43`;
она сложнее и для минимального bootloader не требуется. Наличие этой ветви не
означает поддержки всех NTFS data runs, compression, sparse и больших томов.
Адреса/размеры в этом пути часто усечены до 32 бит.
Поля exFAT независимо сверены с [Microsoft exFAT specification](https://learn.microsoft.com/en-us/windows/win32/fileio/exfat-specification).

`9D97` и `A17E` **не ограничены NTFS**: проверка `041C!=2` переходит в отдельную
FAT/exFAT ветку, а не возвращает. Прежний вывод по неполному листингу был неверен.

### 7.2. Каталог → файл

`1000/1E55` обходят каталог, `813C` извлекает параметры выбранной записи.
Для FAT: cluster high16 из entry+20 и low16 из +26 → `03E6`, file size LE32
из +28 → `0109`. Для exFAT stream entry: cluster +20, low32 data length +24;
бит NoFatChain из flags сохраняется в bit-address `0D`.
Курсор выбранной записи лежит в `041D/0421/0425` (cluster/sector/record offset).

`3E68` читает файл с обходом FAT, группирует соседние кластеры, разбивает передачи
на порции до `0x4000` байт. `D6D1` задаёт `0717=B+700` и вызывает `C60E` с
назначением `0717 + byte_offset/32`; аргументы обёртки: LBA в `R4…R7`, длина
в `X:0924`, file offset в `X:0928` (оба BE32).

Для проверки переноса отдельно проверить FAT32 с root cluster !=2: в `813C`
есть расчёт относительно `0418`, тогда как обычная нумерация data clusters
начинается с 2. Не использовать исходные формулы вслепую на произвольном томе.

Штатный поиск отбирает `.IMG`, а не конкретное имя. Проверки короткого расширения
в `1D54`, длинного — `87CE/8835`. Буфер имени `011D` — 45 байт, mailbox выдаёт
только первые 42. Для собственного recovery разумнее фиксированное короткое имя
в корне, например `RECOVER.BIN`; это **предложение**, не имя из прошивки MSI.

Минимальный новый FAT32 reader поверх `read_sector` может быть таким:

```text
1. Проверить сектор устройства = 512, границы носителя; выбрать допустимый VBR/MBR.
2. Проверить BPB и вычислить FATStart, DataStart, число data clusters.
3. Начать с BPB_RootClus; читать directory entries по 32 байта.
   00 = конец; E5 = удалено; LFN/volume/directory не принимать как файл образа.
4. Найти точное короткое имя, получить first cluster и file size.
5. Для cluster C читать LBA = DataStart + (C-2)*sectorsPerCluster.
6. Следующий C = LE32(FAT[C*4]) & 0x0FFFFFFF; учитывать границу FAT-сектора.
7. Проверять EOC/bad/free/reserved, диапазон и циклы; выдавать ровно file size байт.
```

Это спецификация предлагаемого упрощения, а не построчная трансляция `3E68`.
Выбор active FAT/отказ при отключённом mirroring нужно сделать явно; отвергать
неподдержанный формат безопаснее, чем трактовать его как FAT32. Остаток последнего
сектора не должен попадать в записываемый образ. Перед erase требуются собственные
проверки длины, целевых диапазонов и целостности/подлинности, независимо от ФС.

### 7.3. `NVTSC_IMG` — не барьер перед записью

`DB76` читает **32 байта** с DMA-базы файла `0717` в `X:0912`, разворачивая слова.
Сравнения `0914,0913,0912,0919,0918,0917,0916,091D,091C` соответствуют
**file offsets 1…9**: `NVTSC_IMG`. Byte 0 не проверяется. Положение определяется
по коду `D6D1 → E4E9 → ABCE`, реальный контейнер для этого не нужен.

`A547` при совпадении разбирает заголовки: byte 10 файла задаёт число записей;
первая запись начинается с byte 32. В `X:0652` строится таблица с шагом 8 байт:
BE32 block offset и BE32 размер. Размер извлекается из bytes 4…7 заголовка записи
как big-endian; следующий block offset равен предыдущему плюс `(size+32)/32`.
Это не доказательство произвольного выравнивания или полной спецификации контейнера:
назначение всех полей и реальный допустимый файл здесь не проверены.

Важнее точный контрпример прежнему утверждению о checksum:

```text
9F84: call 3E68       загрузка файла
9F87: SETB bit00      успех установлен ПОСЛЕ чтения
9F89: call A547
9F8C: MOV C,bit00
9F8E: RET

A547: call DB76
A54A: JC A54F         сигнатура есть → разбор
A54C: LJMP A6F9       сигнатуры нет → обычный RET
```

На ветке без сигнатуры `bit00` не сбрасывается. Следовательно,
**отсутствующая `NVTSC_IMG` не ведёт здесь к `CheckSum Fail!`**, а команда загрузки
может вернуть успех. Это строгое опровержение достаточности этой проверки;
оно не утверждает, что все другие слои/ROM вообще не проверяют данные.
Строка `CheckSum Fail!` сама по себе не свидетельствует о вычислении checksum.
Нельзя разрешать стирание SPI по одному состоянию `97` или carry из `9D97`.

## 8. Архитектура recovery и критерий готовности

Предлагаемый путь — сохранить bootloader и отдельную проверенную recovery-копию
AUX, запустить второй 8051 и предоставить ему минимальную секторную команду.
Альтернатива — перенести Host/BOT на первый 8051, но доступ его ядра ко всем
нужным CD/DMA операциям и совместимость SFR/таймингов требуют отдельной проверки.
Это не эквивалентная замена адресов `LCALL`.

Recovery не должен зависеть от исправности восстанавливаемых `id=01`, `id=02`,
Main и их конфигурации DDR. Если AUX/настройки памяти хранятся в том же повреждённом
слоте и ничем не защищены, recovery работает лишь при части повреждений. Необходимы
фиксированный защищённый источник и проверка загружаемого кода. Образы обоих слотов
на физическом мониторе сейчас FW.034; заводская FW.023 осталась только в дампе.

Прежде чем разрешать запись, аппаратная квалификация должна показать:

1. **Физический порт.** VBUS, роль Host и принадлежность D+/D− конкретному FOTG.
   USB-A за VL211 не равнозначен root port NT68503; нельзя соединять два источника
   VBUS или считать USB-B upstream входом для флешки.
2. **Cold init памяти.** Без Main запустить AUX, задать зарезервированную DMA-базу,
   проверить RAM round-trip с несколькими 32-байтными блоками и обоими порядками байт.
   Нужны доказанная трансляция адреса и отсутствие пересечения с кодом/стеком.
3. **Enumeration.** Сохранить реальные device/config/endpoint descriptors,
   negotiated speed, QH/qTD и статусы; проверить disconnect и timeout.
4. **Сектор.** Дважды получить LBA0 и несколько непоследовательных LBA известной
   флешки, побайтово сравнить с дампом на ПК. Это проверяет адресацию, а не только magic.
5. **Файл.** Проверить непрерывный и фрагментированный FAT32-файл, переход FAT-сектора,
   размер не кратный 512, отсутствие файла, повреждённую цепочку, ошибку USB посередине.
6. **Независимость.** Повторить из bootloader без старта основной прошивки; только
   после этого обсуждать dry-run плана записи и атомарное переключение слота.

Это критерии доказательства для шага 46 (не опубликовано), а не новый
параллельный список статусов. В этом исследовании аппаратные опыты не выполнялись,
прошивка не патчилась и память монитора не записывалась. **`U4003` не трогать никогда**:
там калибровки и данные экземпляра. USB reader должен только читать накопитель;
SPI erase/program — отдельный, проверяемый после валидации образа слой.
