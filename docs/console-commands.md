# Команды отладочных консолей

Консоли на `CN4008` отвечают на ввод — это проверено на железе 2026-08-15. Здесь: куда
подключаться, какие команды понимает каждое ядро и откуда это известно.

## Подключение: пары TX/RX

| Ядро | `TX` | `RX` | Скорость | Ввод проверен |
|---|---|---|---|---|
| Leon2 Main | 7 | **5** | 115200 | да, есть ответная активность |
| Leon2 Sub | 8 | **6** | 115200 | да, есть ответная активность |
| Tensilica | 14 | **12** | 115200 | **да, ответ `Command not found`** |
| 8051 (STBC) | 13 | 11? | 4800 | нет, молчит |

**`RX` = `TX` − 2** во всех трёх найденных парах — соседний контакт в том же ряду
разъёма. Все три отвечают на одиночный `\n`, поданный на **115200**, включая Tensilica,
чей передатчик работает 11-битным кадром.

**У 8051 приёма, судя по всему, нет вообще.** Подача на контакт 11 и на 4800, и на
115200 не дала на контакте 13 никакой реакции, и это объясняется образом: во всём
диапазоне STBC `0x000000–0x02E600` нет ни строки `Command Not Found!`, ни приглашения
`DBG >`, ни таблицы команд — только вывод. Единственное вхождение слова `command` там —
`command finish` в драйвере USB-контроллера FOTG210 (`0x027E13`), к консоли отношения не
имеющее. Так что контакт 11 остаётся вероятным `RX` по геометрии, но принимать в 8051
некому.

## Таблицы команд

Формат записи одинаковый у всех трёх ядер: **32 байта имени, дополненные нулями, плюс
4-байтовый указатель на обработчик**, всего `0x24`. Порядок байтов указателя — по ISA
ядра: little-endian у Tensilica, big-endian у обоих Leon2.

**Ловушка при чтении дампа строк:** наивный вывод печатных последовательностей склеивает
последний байт указателя с началом следующего имени, и команды выглядят как `@wmem`,
`^,mdw`, `]Pmww`, `Xmww`, `Dhelp`. Символа `@` в именах нет — это `0x40` из адреса
`0x40xxxxxx`.

### Tensilica — таблица `0x03B228`, база `0x40000000`

| Команда | Обработчик |
|---|---|
| `mem` | `0x40004894` |
| `wmem` | `0x40004AD4` |
| `mdw` | `0x40004A10` |
| `mww` | `0x40004AD4` |
| `gpio` | `0x40005BB4` |
| `help` | `0x40005B44` |
| `rsa` | `0x40005B80` |
| `msg1` | `0x40005B94` |
| `msg0` | `0x40005BA4` |

Рядом лежит встроенная подсказка (`0x03B3B8`–`0x03B480`), то есть синтаксис не надо
угадывать:

```
mem [addr] [count] : display memory data ( 8 bits format)
wmem [addr] [data]: write data to memory
mdw [addr] [count] : display memory data (32 bits format)
proc [p1] [p2] [p3]: function test
gpio [port]: GPIO test
```

`proc` описан в подсказке, но в таблице его нет; `rsa`, `msg0`, `msg1` есть в таблице, но
не описаны. `wmem` и `mww` указывают на один обработчик — вероятно, он сам разбирает
разрядность по имени.

Приглашения этого ядра — `TDBG >>` (`0x03B504`) и `DBG >>` (`0x03B512`), приглашение
ввода — `Please enter the command: ` (`0x03B20C`).

Здесь же лежит заводской тест порта: `*** UART TX Test Start ***`,
`*** UART RX Test Start ***`, `Please input a character ('q' to exit):`, `User input: %c`,
`UART test done!` (`0x03B5DC`–`0x03B698`). То есть **приём в этом порту предусмотрен
заводом**, что согласуется с тем, что он ответил первым.

Подсказка короче тензиликовой: `mem [addr] : display memory data`,
`wmem [addr] [data]: write data to memory`. Ошибки разбора: `Argc is overflow`,
`Argv is overflow`.

Интересны четыре последние команды: `ldc` — почти наверняка модуль локального затемнения
(`docs/oled-panel-abl.md`), `DDRStress` и `ATTIMING` — память и тайминги, `AT` —
неизвестно.

### Leon2 Sub — таблица `0x09D1EC`, база `0xA0060000`

| Команда | Обработчик |
|---|---|
| `mem` | `0xA0065BC4` |
| `wmem` | `0xA0065E2C` |
| `mdw` | `0xA0065D50` |
| `mww` | `0xA0065E2C` |
| `hrx21` | `0xA009991C` |
| `maild` | `0xA00A7D0C` |
| `rt` | `0xA0065BB0` |

**`help` у этого ядра нет** — ни записи в таблице, ни самой строки `help` во всём
образе Leon2 Sub. Поэтому консоль на него отвечает отказом, и это не сбой, а
подтверждение таблицы (`captures/leon2sub-help.log`):

```
DBG >>help

Command Not Found!
DBG >>
```

Заодно это третья консоль, у которой получено приглашение, — работают все три.

Приглашение — `DBG >>` (`0x09D382`), рядом `MAILBOX_DUMP 0x%d` (`0x09D462`), что вяжется
с командой `maild`. `hrx21` по имени похоже на HDMI-приёмник (`type = 21` печатается в
`[MODEDET]`, `docs/boot-sequence.md`).

**Побочно подтверждены базы загрузки.** Указатели в таблицах попадают ровно в свои
диапазоны: `0x40004894` при базе Tensilica `0x40000000`, `0xA00A7D0C` при базе Leon2 Sub
`0xA0060000` (файл `0x97D0C`, внутри `0x050000–0x0A5600`), `0x00079B6C` в FW.034 и
`0x00079E64` в FW.037 при базе Leon2 Main `0` (файлы `0x181B6C` / `0x181E64`).
Это независимая проверка баз из `README.md` — таблицы собраны компоновщиком, а не
выведены анализом.

## Что это даёт

`mem` и `mdw` подтверждённо читают CPU-visible память на живом железе. `wmem`/`mww`
выполняют прямой 32-битный store, но строка `[address] : value` и `wmem OK` лишь
повторяют аргументы и не являются read-back. Это проверено 2026-08-18 на FW.034:
запись `0xC0DEC000` по низкому адресу `0x00017900` получила `wmem OK`, а следующий
`mem` прочитал ноль (`captures/leon2main-fw034-wmem-probe-2026-08-18.log`).

**Осторожно с `wmem`.** Запись работает в окне `0xA8xxxx` (DDR/globals в
RAM): там значение сохраняется и читается обратно (проверено на FW.034 по `0xA8030070`).
Низкое окно приложения `0x0000xxxx` и runtime `0xA002xxxx` — read-only для `store`:
запись безмолвно игнорируется (проверено по `0x00017900` и `0x00151FA4`).

**Дополнено 2026-08-31: почтовый ящик `0x9F0A0100` тоже пишется, и это даёт консоли
управление аппаратным slave-движком.** Слово команды кладётся прямо: `wmem 0x9F0A0100
0x00CC5607` — команда `0x07` (назначить слейва), маска каналов `0x56`, адрес `0xCC`.
Следующий `mdw 0x9F0A0100 1` показывает ноль, то есть 8051 команду забрал, а на шине
DDC разъёма адрес слейва действительно меняется — проверено с ПК
(`docs/nt68503-i2c-service-protocol.md`, § «Канал 4 обслуживает HDMI-2»,
`captures/chanmap-2026-08-31/`). Служебный сеанс, мост `U7005` и остановка ядер для
этого не нужны, картинка и DDC остальных портов живут, откат — обратной командой.

**Дополнено 2026-09-02: регистры скалера доступны с консоли напрямую.** Те же
8-битные регистры, которые 8051 видит подряд в XDATA, Leon2 видит 32-битными словами
с шагом 4: `AHB = 0xCF000000 + 4 × XDATA`, значение в младшем байте. Проверено чтением
(`F050 = 0x15`, `F055 = 0x06`, `F1A8 = 0x02`, `F1AB/F1AC/F1AD = E9 06 C5`) и записью
(контроль на `F055`: `0x06 → 0x01 → 0x06`). Служебный сеанс и мост для этого не нужны:

```
mdw 0xCF03C154 1              # прочитать XDATA 0xF055
wmem 0xCF03C154 0x00000001    # записать его же
```

Исключение — блок `F1D0…F1D8` (кодовое окно 8051): со стороны Leon2 он читается нулями
и не пишется, хотя служебный канал видит там осмысленный дескриптор
(`docs/nt68503-hardware.md`, `docs/stbc-launch.md`).

**Осторожно с разбором вывода `mdw`.** Он печатает следом строку со **следующим**
адресом и пустым значением (`9F0A0110 :`), поэтому «взять последнее восьмизначное
число» даёт заголовок этой пустой строки, а не значение: ящик выглядит вечно занятым.
Разбирать надо свою строку по адресу.

**Дополнено 2026-08-30: регистровое окно скалера `0xCF03Cxxx` тоже пишется.** Проверено
на `DIR` банка 8 GPIO — это защёлка, у которой read-back однозначен, в отличие от `DATA`,
возвращающего уровень на выводе: `wmem 0xCF03C454 0x57` прочиталось как `0x57`, возврат
`0x55` — как `0x55`. Дальше через это окно дёргались выходы банка 8, и каждая запись
читалась обратно (`docs/uart-console.md`). То есть консоль даёт **прямое управление
периферией скалера**, а не только правку переменных в DRAM. Красные линии при этом те же,
что и раньше (`docs/sw4101-button.md`): банк 4 — шина к `U4003`, банк 12 — шина
панели, банк 14 — вторая I²C-шина с неизвестным адресатом, банк 2 бит 1 — не
подтверждённый на плате слот функциональной кнопки. Сводная карта — `docs/gpio.md`.
Доказанная writable DRAM меняет работающую систему: поля ABL, циклов компенсации и
таймингов панели живут именно там (`docs/oled-panel-abl.md`,
`docs/panel-protect.md`). После любой записи обязателен отдельный `mem`; писать можно
только по адресу с доказанным владельцем и сохранённым исходным значением.

## Консоль Tensilica работает. Терминатор — только `\r`

**2026-08-15, первый успешный сеанс** (`captures/tensilica-help.log`). Терминал `screen`,
настроенный слать `\r` без `\n`:

```
TDBG >>help


mem [addr] [count] : display memory data ( 8 bits format)
wmem [addr] [data]: write data to memory
mdw [addr] [count] : display memory data (32 bits format)
proc [p1] [p2] [p3]: function test
gpio [port]: GPIO test
help OK.
```

Что этим установлено:

- **Дело было в терминаторе.** `\n` не принимается, `\r` принимается. Всё остальное —
  свободный текст, никаких префиксов и фиксированных длин у этого ядра нет.
- **Приглашение `TDBG >>` получено** — вторая половина критерия шага 12, которой не
  хватало.
- **Разбор таблиц из образа верен.** Живой `help` напечатал ровно те строки подсказки,
  что лежат в `0x03B3B8`–`0x03B480`, слово в слово.
- **Успешная команда отвечает `<имя> OK.`** — это строка ` OK.` с `0x03B4E4`, которая
  до сих пор лежала рядом с `Command Not Found!` без объяснения.
- **`help` печатает не таблицу, а отдельный текст подсказки.** Поэтому в выводе есть
  `proc`, которого в таблице нет, и нет `rsa`, `msg0`, `msg1`, которые в таблице есть.
  Проверять их придётся вводом.

## Консоль Leon2 Main тоже работает, и `help` там короче таблицы

`captures/leon2main-help.log`, контакты 7/5, тот же `\r`:

```
MDBG >>help


mem [addr] : display memory data
wmem [addr] [data]: write data to memory
help OK.
```

Два вывода:

- **Ввод у Leon2 Main такой же текстовый, как у Tensilica.** Никакого префикса не нужно.
- **`help` показывает две команды из одиннадцати.** В таблицах `0x00151E64` (FW.034)
  и `0x001521EC` (FW.037) их одиннадцать — `mdw`, `mww`, `ReadStackApi`, `dump`, `ldc`,
  `AT`, `DDRStress` и `ATTIMING` в подсказке просто не описаны. Значит **таблица, а не
  `help`, — источник истины**, и неописанные команды имеет смысл пробовать вводом. То же
  самое было у Tensilica с `rsa`, `msg0`, `msg1`.

Синтаксис у ядер разный: у Tensilica `mem [addr] [count]`, у Leon2 Main `mem [addr]`
без счётчика.

## Кадр с префиксом `'5'` — это не консоль

Разбор ниже сделан, пока консоли молчали, и сначала этот вход ошибочно приняли за
консольный. Живой USB-захват и прошивка `U7005` установили его назначение: это
служебный канал **ПК → USB HID → U7005 UART1 → STBC channel4 → Mailbox → Leon2 Main**. Текстовая консоль
Leon2 Main на отладочном разъёме — другой, независимый вход.

**Уточнение 2026-09-17:** старый разбор ниже описывает родственные парсеры
channel2/3. Доказанный канал U7005 — channel4, приёмник `6D8E4→59B08(4)`,
буфер `A802BBC0`; у него есть дополнительные длины служебных кадров.
Физические адресаты channel2/3 пока не установлены.
Сопоставление с Mailbox (не опубликовано).

**Два родственных приёмника channel2/3:** `0x0005A168` и `0x0005AB10`.
Каждая обслуживает свой буфер на `0x30` байт (`0xA802BB30` и `0xA802BB88`) со своим
индексом (`0xA8029B8A`, `0xA8029B88`) и флагом состояния (`0xA8029B89`, `0xA8029B87`,
он же `ucCmdStatus`). Сбрасывают их `ResetUart3Rx` (`0x0005A9AC`) и
`Uart3SetCmdProcess` (`0x0005AAC8`, `0x0005B27C`) — те самые имена из
`docs/uart-console.md`.

Логика приёма в обеих одинаковая:

```c
// первый байт буфера решает всё
if (buf[0] != '5' && buf[0] != '\0') {
    ucCmdStatus = 1;              // взводится таймер 0x32, потом сброс
}
if (buf[0] == '5' && idx > 5) {
    if (buf[1] == '8') len = 7;   // ждём терминатор на позиции 7
    else if (buf[1] == 'b') len = 10;
    if (idx > len && buf[len] == '\r') { ... }   // ← принимается только по '\r'
}
```

Отсюда три свойства этого входа:

1. **Терминатор — `'\r'` (CR).** Совпадение с консолью случайное, но именно оно и увело
   разбор не туда.
2. **Первый байт кадра должен быть `'5'`** (0x35). Любой другой (кроме нуля) не
   накапливается, а взводит таймер сброса буфера.
3. **Длина фиксированная:** второй байт `'8'` задаёт кадр в 8 байт (терминатор на
   позиции 7), `'b'` — в 11 байт (терминатор на позиции 10). Промежуточных длин нет.

### Формат служебного протокола

```text
GET:      5 8 ID[4] index \r
response: 5 b ID[4] index data... \r
SET:      5 b ID[4] index data[3] \r
ACK:      5 6 0 0 (+|-) \r
```

Символы после `'9'` — `':'`, `';'`, `'<'`, `'='`, `'>'`, `'?'`, `'@'`, `'A'` и
дальше — не разделители: числовые разряды кодируются как `0x30 + n`. Поэтому в
`580040:\r` двоеточие является индексом `10`.

Сопоставление GET выполняет `FUN_000F04C8`; таблица лежит по связанному адресу
`0x161040` (файловые смещения `0x268CA0` в FW.034 и `0x269040` в FW.037). В ней
**131 строка по 8 байт, 130 уникальных кадров**: `5800271\r` продублирован. Таблица
SET находится по `0x161458` (смещения `0x2690B8` / `0x269458`): **141 строка по
11 байт, 134 уникальных сочетания ID+index**; байты `0xFF` в шаблоне означают
произвольные данные. Обе таблицы побайтно одинаковы в FW.034 и FW.037.

Полный статический whitelist GET сгруппирован ниже. В левой колонке указан ID, справа —
допустимые символы индекса; `0` у одиночных команд уже включён в запись.

```text

0090 0091 0092 0093 0094 0095 0096 0097
00;0 00;3 00;9 0[00

несколько индексов:
0040 → :,0,4       0041 → 0,4,5,6     0043 → 0,1,2,3,4,5
```

SET-таблица в основном содержит те же ID/index с тремя произвольными байтами данных.
Дополнительно в ней есть следующие заголовки, которых нет в GET-таблице; здесь пять
символов — это `ID[4]+index`, а угловыми скобками отмечены сырые не-ASCII байты:

```text
00102 00155 002=0 00440
00604 00605 00613 00614 00619 00625 00626 00627 00628 00629
00650 00660 00670 006>0 00840 00<00 00<10
00Z<A5>U 00Z<A7>? 00Z<A8><AA> 00j00 @1;80
```

В большом SET-диспетчере есть настройки OSD и заводские ветви, а часть case — пустые
заглушки. Отправлять неизвестные записи на живой монитор небезопасно.

Примеры опознанных кадров: `5800110\r` — статус, `5800130\r` — серийный номер,
`58001<0\r` — версия прошивки, `5800400\r` — яркость, `5800410\r` — контраст.
Whitelist означает только, что строка распознаётся: часть ветвей диспетчера пустая, а
семантика и допустимые значения зависят от модели.

**Внешний проект `msigd` дал словарь верхнего уровня.** Его исходники формируют ровно
те же кадры `58...\r`/`5b...\r` в HID Report ID 1. С живым захватом MPG 341CQPX точно
совпадает 41 ID, а `00140`/`00150` оказались парой идентификации модели. Вместе с уже
известным `001<0` назначение теперь установлено у 44 из 68 запросов `58...`: в том числе
Gaming Mode, HDCR, Adaptive Sync, Night Vision, PIP/PBP, вход, KVM, OSD и назначения
Navi Key. Полный словарь, кодирование значений, OLED-идентификаторы и оставшиеся
неизвестные команды вынесены в `docs/msi-uart-settings-protocol.md`.

В частности, `5800110\r` — не просто безымянный статус, а read-only `macro_key`, который
`msigd` также описывает как часто опрашиваемый OSD-приложением. Это подтверждает связь
ежесекундного запроса с `MonitorMicroKeyDetector.exe`.

**`'8'` нельзя считать безопасным чтением.** `580040:\r` — строка GET-таблицы с
индексом `':'`, но её обработчик `FUN_0005E768` печатает `--->UartSetI2CEnable` и
переводит сервисный интерфейс скалера из UART в I2C/ISP. После этого U7005 отдельной
локальной командой `e0 01` закрывает UART1 и мультиплексирует те же PE.12/PE.13 в
I2C0; возврат выполняется `e0 00`. Подробная последовательность — в
`docs/usb-isp-protocol.md` и `docs/mcu-u7005.md`.

**Полезно для отладки:** при накоплении более десяти байт приёмник печатает каждый
принятый байт форматом `0x%X : %d` (строка `0x00151A10`), то есть **показывает, что до
него реально дошло**. Ещё есть `timeout` (`0x00151A48`), `Reset:` (`0x00151A28`),
`Set timer:` (`0x00151A38`) и `__ucCmdStatus %d` (`0x001519D0`) — по ним видно, что
происходит с буфером.

### Что осталось неизвестным

После сопоставления с `msigd` неизвестны 24 из 68 запросов `58...` в живом захвате и
отдельный heartbeat `6800;30`; это главным образом новые группы `002A*`, `002B0`,
`002D0`, `0061*`, `006=0`, `008@0`/`008A0`/`008B0` и `00;*`. Вероятная связь с OLED
Care/Panel Protect пока остаётся гипотезой. Кроме того, U7005 перехватывает часть
кадров Report ID 1 локально
(например, `5b00130...` для своей Data Flash), поэтому статический whitelist Leon2 не
означает, что каждый кадр без изменений достижим через USB.

Функция, печатающая `Command Not Found!`, — по адресу `0x00076AB0`; Ghidra относит её к
большой склейке с началом `0x0007654C`, границы там определены неверно (сотня
недостижимых блоков), поэтому декомпиляция этого места нечитаема. Разбирать её надо по
листингу.

## Что из команд проверено на железе

| Команда | Ядро | Результат |
|---|---|---|
| `help` | Tensilica | работает, печатает подсказку |
| `help` | Leon2 Main | работает, печатает две строки из одиннадцати команд |
| `help` | Leon2 Sub | `Command Not Found!` — её там и нет, ожидаемо |
| `msg1` | Tensilica | **включает периодический дамп ABL** |
| `msg0` | Tensilica | **выключает его** |
| `mdw` | Tensilica | отвечает `mdw OK.`, но ничего не печатает — с любыми аргументами и без них |

Не пробовались: `mem`, `wmem`, `mww`, `gpio`, `proc`, `rsa` у Tensilica; всё, кроме
`help`, у Leon2 Main; все семь команд у Leon2 Sub.

Прочее открытое: формат числовых аргументов консоли неизвестен; `RX` 8051 не найден,
и принимать там, судя по образу, нечему.

## `msg1` — включает периодический дамп модуля ABL

Самая ценная из найденных команд, и её нет во встроенной подсказке. `msg1` включает
**периодический вывод всего блока LDC/ABL** (`captures/tensilica-msg1-ldc-dump.log`):

```
Input Duty:
  00.   0000  0000  ... (16 значений)
  01.   0000  0000  ... (16 значений)
Merged Segment:
        40000824  3FFEEFD0  60330  C000A307 ...
LED ADIM:
        0200  0200  ... (16 значений)
LED PDIM:
        0FFF  0FFF  ... (16 значений)
Pure Pattern: 0
ApplyGlobalGain: 0x0400
```

Печатаются ровно те строки, что лежат в образе на `0x03B01C`–`0x03B070`, и значения
совпали с разобранными из образа — сверка в `docs/oled-panel-abl.md`. **Это прямой доступ
к контуру ABL на работающем мониторе**, то есть инструмент для основной цели проекта.

**`msg0` дамп выключает — проверено.** Пара `msg1`/`msg0` (`0x40005B94` / `0x40005BA4`)
работает как переключатель вывода, и без неё экспериментировать неудобно: поток заливает
консоль и мешает вводить команды.

## Первая попытка чтения памяти: команда принята, данных нет

```
TDBG >>mdw 3FFE2390 16


mdw OK.
```

Команда **найдена и выполнена** (`mdw OK.`), но ни одного слова не напечатано и ошибки
`Address Fail` (`0x03B4D0`) тоже нет. Значит дело не в адресе, а в **разборе
аргументов**: скорее всего они не распознались, и обработчик отработал вхолостую —
например, со счётчиком, равным нулю.

**Уточнение:** `mdw` без аргументов даёт тот же самый ответ, значит дело не в разборе
аргументов — обработчик молчит всегда. Заработал ли он после `msg1`, не проверялось;
это первое, что стоит попробовать, раз канал вывода дампов оказался переключаемым.

Формат чисел, который ждёт консоль, пока неизвестен. Перебирается за минуту:

| Что попробовать | Что проверяет |
|---|---|
| `mdw 0x3FFE2390 16` | нужен ли префикс `0x` |
| `mdw 3ffe2390 16` | чувствительность к регистру |
| `mdw 3FFE2390 4` | не слишком ли велик счётчик |
| `mem 3FFE2390 16` | тот же вопрос для 8-битного варианта |
| `mdw` без аргументов | что печатается при нуле аргументов |

Из листинга обработчика (`0x40004A10`) видно: печать идёт через отладочный `printf`
`0x400099BC` — тот самый, что записан в `docs/oled-panel-abl.md`, — а формат-строки
берутся из DRAM по `0x3FFE1D44`, `0x3FFE1D48`, `0x3FFE1D4C`. Вывод устроен блоками
по четыре слова.

**Ловушка Ghidra на Xtensa.** Адреса обработчиков из таблицы (`0x40004A10`,
`0x40004894`) не совпадают с началами функций: Ghidra не создаёт там функций, а
`DecompAt.java` без функции не работает. Дизассемблированный поток к тому же может быть
сдвинут — у Xtensa инструкции переменной длины, и разбор, начатый не с той границы,
выглядит правдоподобно, но врёт. Листингу этого места без перепроверки доверять нельзя.

## Работа с консолями приостановлена 2026-08-15. С чего продолжать

Всё, что нужно для возврата к теме, — здесь; в новой сессии этого документа достаточно.

**Как подключиться:** `CN4008`, Tensilica — TX 14 / RX 12, Leon2 Main — TX 7 / RX 5,
Leon2 Sub — TX 8 / RX 6, все 115200 8N1. Терминал должен слать **только `\r`**, иначе
любая команда получает `Command Not Found!`. Земля — контакт 9 или 10; в линию, куда
подаёте, полезен последовательный 1 кОм.

**Первое действие при возврате:** `msg1` на Tensilica — дамп контура ABL, `msg0`
выключает.

Дальше по убыванию отдачи:

1. **Снять дамп с картинкой на экране.** Сейчас `Input Duty` нулевой только потому, что
   нет сигнала. Подать изображение, менять APL (чёрное поле, белое, градации, окно 10 %)
   и для каждого случая записать `Input Duty`, `LED ADIM`, `LED PDIM`,
   `ApplyGlobalGain`. Это и есть передаточная функция APL → яркость, то есть шаг 15 и
   основная цель проекта, и делается она **только чтением**.
2. **Повторить `mdw` при включённом `msg1`** — вдруг он молчал именно потому, что канал
   вывода дампов был выключен. Если заговорит, дальше подбирать формат аргументов по
   таблице выше.
3. **Опробовать команды, которых нет в подсказке.** Самая интересная — `ldc` у Leon2
   Main: по имени это модуль локального затемнения, то есть тот же контур, но со стороны
   прикладного ядра. Рядом `dump` и `ReadStackApi`.
4. **Разобрать `Merged Segment`** — что за структура печатается под этой подписью
   (`docs/oled-panel-abl.md`).

**Чего не делать без нужды:** `wmem`/`mww` пишут в память работающей системы, где живут
параметры ABL, циклов компенсации и таймингов панели. Вся работа выше — на чтение, и
этого достаточно.

## Уточнение синтаксиса Main mdw, 2026-09-19

Hex-адрес передавать с явным `0x` и проверять адрес в ответе, а не только `mdw OK`.
Read-only ошибочная попытка (не опубликовано)
показывает: `mdw A802B464 2` вывел данные с `0A9CA6C0`, а `mdw A8027A1C 1` —
с `0A9C80B8`. Это другой разбор числа; его общая формула здесь не выводится.
Повтор с префиксом (не опубликовано)
прочитал именно A802B464 и A8027A1C. При невыровненном на16 адресе mdw оставляет
пустые колонки; первое напечатанное слово не обязательно лежит по адресу заголовка
строки. Старые таблицы UART-команд Tens/profile исправлены по реальному TX:
в исходных captures префикс присутствовал, ошибка была только в записи команд
в документации. Сырые захваты не менялись.
