# Драйвер SPI-флеша в STBC Main

Кто и как физически пишет во флеш. Разбор закрывает открытый вопрос №9: код записи
найден, он в разделе id=0x01, и **это не ROM-код**.

Все адреса — образ `stbc-main` (раздел id=0x01, файл `0x010000`–`0x01F026`, 8051,
база `0x0000`); файловое смещение = адрес + `0x010000`. Воспроизвести:

```bash
./tools/ghidra_import.sh stbc-main-8051
~/ghidra_12.0.2_PUBLIC/support/analyzeHeadless "$PWD/ghidra" nt68503 \
    -process "region_010000_01f100.bin" -noanalysis \
    -scriptPath "$PWD/tools/ghidra_scripts" \
    -postScript DisasmAt.java "0x2400-0x2800,0x7d00-0x8000,0x8300-0x8a00,0x9a00-0x9c00,\
0xb000-0xb200,0xc200-0xc400,0xda00-0xe000,0xe100-0xe520" \
    -postScript DumpAsm.java "$PWD/out/main8051.txt" 0x0 0xf100
```

## Откуда берётся опкод чтения

Драйвер не выбирает ширину шины сам: перед каждой читающей транзакцией он копирует
опкод из `XDATA 0xA7CC` в `F0EA`. Саму ячейку `id=0x01` заполняет **один раз**, сразу
после своего баннера и перед процедурой переносов (`CODE:4ECC…4EEC`), читая защёлку
режима `F050`, которую выставил загрузчик:

| `F050` | `A7CC` | Режим |
|---|---|---|
| бит 2 | `0x6B` | Quad Output Fast Read |
| бит 5 | `0x3B` | Dual Output Fast Read |
| ни одного | `0x0B` | Fast Read |

Мест, копирующих `A7CC → F0EA`, в образе четыре: `CODE:812B` (путь движка
`F600…F60E`), `CODE:88E7`, `CODE:9CFA`, `CODE:C582`. Подробности и доводы —
`docs/nt68503-hardware.md` §6.8, «Режим шины хранится в `F050`»;
кто выставляет защёлку — `docs/bootloader.md`, `FUN_0C83`.

## Аппаратный SPI-контроллер

Регистры видны в XDATA 8051 двумя блоками — `0xF0Exx`/`0xF0Fx` (движок) и `0xF1Cx`
(секвенсор и FIFO):

| Регистр | Назначение |
|---|---|
| `0xF0E5` | пуск и занятость: запись `1` — запустить команду записи, `2` — команду чтения; опрос того же бита до нуля |
| `0xF0E6` | режим, всегда `(старое & 0x0C) \| 0x41` для команд и `\| 0x01` для page program |
| `0xF0EA` | опкод для **читающей** транзакции |
| `0xF0EB`/`0xF0EC`/`0xF0ED` | длина данных (в page program — `длина − 1`) |
| `0xF0EE` | опкод для **пишущей** транзакции |
| `0xF0EF` | принятый байт читающей транзакции |
| `0xF0F0`/`0xF0F1`/`0xF0F2` | 24-битный адрес для page program (биты 0–23) |
| `0xF0F4` | `3` для команд, `7` для чтения регистра статуса |
| `0xF1C0` | секвенсор: `0x80` — сброс FIFO, `0x82` — фаза команды, `0x84`/`0x04` — исполнить, `0` — завершить |
| `0xF1C3` | FIFO данных: адрес стирания и полезные данные page program уходят сюда |

Байт JEDEC (тип флеша) лежит в XDATA `0x3066` и используется для выбора формата
регистра статуса.

## Примитивы

| Адрес | Что делает |
|---|---|
| `FUN_E6D9(op)` | однобайтная команда без адреса. **Все 10 вызовов — с `op = 6`, то есть WREN** |
| `FUN_DFF6(op)` | читающая команда, возвращает байт в `R7`. Вызывается с `5` (RDSR), `0x15`, `0x35` |
| `FUN_8314(ptr)` | **снять защиту** блоков через регистр статуса |
| `FUN_C2C2(ptr)` | **вернуть защиту** |
| `FUN_7D8F` | **page program** |
| `FUN_9A7F(R5=op, R6:R7=блок)` | **стирание** |
| `FUN_8868` | чтение |
| `FUN_E8DF(b)` | **задать расширенный адрес** — `WREN`, команда `0xC5` с байтом `b`, ожидание `WIP` |

**Адрес во флеше 32-битный, и старший байт передаётся микросхеме, а не контроллеру.**
Регистры `0xF0F0..0xF0F2` дают только биты 0–23; биты 24–31 уходят в регистр
расширенного адреса командой `0xC5`. `FUN_E8DF` — тот же код, что `FUN_CODE_180D` в
загрузчике (`docs/bootloader.md`); вызывается с `0x8122` и `0x9CF1`, и параметр там
получается сдвигом 32-битного адреса вправо на 24 (`MOV R0,#0x18` + `?C?ULSHR`).
Поэтому 8051 адресует **все 32 МБ**, а не первые 16 МиБ, и в верхнем банке лежит
второй слот прошивки (`docs/flash-u4002.md`).

Опрос статуса устроен канонически: после WREN ждут `JNB ACC.1` (бит **WEL**), после
запуска — `JB ACC.0` (бит **WIP**). Ошибок в этом месте нет, это учебниковая
реализация SPI NOR.

**Уточнение 2026-09-02: эти два ожидания — без счётчика.** В листинге `id=0x01` это
`CODE:E8EC` (`JNB ACC.1, 0xE8E6`) и `CODE:E8FE` (`JB ACC.0, 0xE8F8`) — самоблокирующие
петли, из которых нет выхода, если контроллер не отвечает. Стиль в драйвере не единый:
`FUN_D1D8` ниже ждёт с ограничением в 20000 итераций и по тайм-ауту сдаётся. То есть
устойчивость к неотвечающему контроллеру в одних местах есть, в других нет.

### Расширенный адрес: команда `0xC5` (WREAR)

Всё, что ниже, сверено с даташитом в репозитории —
`datasheets/gd25q256e_rev1_1_20211122-3081729.pdf`, разделы 6.2 и 7.6.

**Задача.** У обычных команд SPI NOR — чтения `03h`, записи страницы `02h`, стирания
сектора `20h` — адрес трёхбайтный, то есть 24 бита, то есть **16 МиБ потолка**.
Микросхема здесь на 32 МБ, и одного бита не хватает. Производители дают на выбор два
способа его добрать, и они несовместимы по смыслу.

| Способ | Как | Что требуется от ведущего |
|---|---|---|
| **4-байтная адресация** | команда `B7h` (EN4B) или отдельные опкоды `13h`/`12h`/`21h`/`DCh` | уметь выдавать **четвёртый** байт адреса |
| **Регистр расширенного адреса** | `C5h` записать, `C8h` прочитать | ничего — адрес остаётся 24-битным |

Скалеру доступен только второй: у его контроллера ровно три регистра адреса
(`0xF0F0`/`0xF0F1`/`0xF0F2`), четвёртого нет физически. Поэтому прошивка и режет
адрес по биту 24 (`docs/bootloader.md`).

**Что это за регистр.** Таблица 9 даташита: восемь бит, из которых значащий ровно один
— **`EA0 = A24`**, остальные зарезервированы (рекомендуется писать нули). Он не входит
в адрес, а **достраивает** его сверху, поэтому микросхема как бы переключается между
двумя половинами:

| `A24` | Что видно по 24-битным адресам |
|---|---|
| `0` | `0x00000000–0x00FFFFFF` — нижние 16 МиБ |
| `1` | `0x01000000–0x01FFFFFF` — верхние 16 МиБ |

Это ровно те два банка, в которых лежат два слота прошивки. **Скалер о них не знает
вообще** — он всегда называет один и тот же 24-битный адрес, а какой из банков ответит,
решает содержимое `EA0`.

Три свойства регистра, каждое из которых имеет здесь последствия:

- **Он изменяемый только на лету.** Даташит, 7.6: «Upon power up or the execution of a
  Software/Hardware Reset, the Extended Address Register bit values will be cleared to 0».
  Отсюда следует, что после подачи питания микросхема всегда отдаёт нижний банк — и
  поэтому загрузчик обязан лежать со смещения 0, а маркер слота `0x7FFF` читается
  всегда из нижнего банка.
- **Он требует `WREN`.** «A Write Enable (WREN) instruction must be executed previously
  to set the Write Enable Latch (WEL) bit before it can be accepted» — что прошивка и
  делает: `06h`, ожидание `WEL`, затем `C5h`.
- **Он действует на 3-байтном режиме и только на нём.** Если микросхема поднялась с
  битом `ADP = 1` или получила `B7h`, она ждёт четырёхбайтный адрес во всех адресных
  командах, а расширенный адрес **игнорируется**.

**Как прошивка её посылает.** `FUN_CODE_180D` в загрузчике и `FUN_E8DF` в `stbc-main` —
побайтово один и тот же код:

```
FUN_17AF(0x06);            // WREN, транзакция без данных (длина 0)
while (!(RDSR & WEL));     // FUN_172D(0x05)
FUN_16DB(0xC5, банк);      // пишущая транзакция, один байт данных
while (RDSR & WIP);
print("SetExtendedAddr=%02bX", банк);
```

Сама транзакция `FUN_16DB` разложена на регистры контроллера так:

```
F1C0 = 0x80                       // сброс FIFO
F0E6 = (F0E6 & 0x0C) | 0x41
F0F4 = 3
F0EB:F0EC:F0ED = 1                // длина данных — один байт
F0EE = 0xC5                       // опкод пишущей транзакции
F1C0 = 0x82                       // фаза команды
F1C3 = банк                       // байт данных в FIFO
F1C0 = 0x84                       // исполнить
F0E5 = 1;  while (F0E5 & 1) ;
```

Обратная команда `C8h` (RDEAR) идёт по читающему пути `FUN_172D`: опкод в `F0EA`,
`F0F4 = 7`, пуск `F0E5 = 2`, ответ забирается из `F0EF`. В загрузчике её посылает
`FUN_18E2` — та самая проверка «а не остался ли флеш в верхнем банке».

### Чем `0xC5` опасна

**Регистр глобальный.** Он достраивает адрес **всем** командам, а не только чтению:
`02h` записи страницы и `20h`/`D8h` стирания тоже. Оставленная единица означает, что
следующее стирание уйдёт в другой слот — то есть сотрёт не ту прошивку. В драйвере
защиты от этого нет: `FUN_E8DF` вызывается из двух мест перед транзакцией, а обратно в
ноль его никто не возвращает. Всякий код, который пишет во флеш по 32-битному адресу,
обязан задавать старший байт **сам, каждый раз**.

**А вот `ADP` — необратимая ловушка.** Бит `S20` регистра статуса 3 («Power Up Address
Mode») **энергонезависимый** (таблица 7 даташита). Если его выставить, микросхема
навсегда начнёт просыпаться в 4-байтном режиме, расширенный адрес перестанет работать,
и 24-битный контроллер скалера потеряет с ней связь на первом же чтении — монитор
не поднимется вообще. Восстановить это можно только программатором, вернув `ADP = 0`.
Ни прошивка, ни утилита MSI этот бит не трогают; опасность возникает только от наших
собственных экспериментов с чипом. **Не выставлять `ADP` и не посылать `B7h`.**

Соседнее наблюдение из той же таблицы: бит `QE` (`S9`, Quad Enable) — тоже
**энергонезависимый**. Это тот самый бит, который выставляет `FUN_0C83` перед печатью
`Set Flash to Quad mode!!`. Его состояние переживает выключение, поэтому проверка
чтением в `FUN_0C83` обычно проходит с первого раза.

**Для работы программатором.** Если читать или писать `U4002` в 3-байтном режиме,
верхние 16 МиБ без `C5h` недостижимы — их просто не видно, и дамп получится вдвое
короче, чем чип. Снятый дамп 32 МБ означает, что чтение шло либо 4-байтными командами,
либо с переключением `EA0`. При записи важно обратное: `EA0` сбрасывается сбросом и
питанием, поэтому оставить микросхему «не в том банке» после программатора нельзя —
это состояние не переживает выключения.

### Стирание `FUN_9A7F`

Печатает `DoBlockErase start %04x`, снимает защиту, шлёт WREN, ждёт WEL, затем по
**опкоду** выбирает, на сколько сдвинуть номер блока, чтобы получить байтовый адрес:

| Опкод в `R5` | Сдвиг | Размер |
|---|---|---|
| `0x20` | `<< 12` | 4 КБ (sector erase) |
| `0x52` | `<< 15` | 32 КБ |
| иначе (`0xD8`) | `<< 16` | 64 КБ |

Три старших байта адреса уходят в FIFO `0xF1C3`, опкод — в `0xF0EE`, `0xF1C0 = 0x84`,
опрос `0xF0E5 & 1`, затем ожидание WIP. В конце печатает `sector erase` и адрес и
возвращает защиту.

**Важно: параметр — номер блока, а не байтовый адрес.** Ошибка на этом месте сотрёт
не то, что задумано.

### Запись `FUN_7D8F`

Классический цикл page program страницами по `0x100` байт:

```c
FUN_8314(&buf);                       // снять защиту
while (len) {
    n = (len >= 0x100) ? 0x100 : len;
    F1C0 = 0x82;                      // фаза команды
    for (i = 0; i < n; i++) F1C3 = src[i];   // данные в FIFO
    F1C0 = 0x82;  WREN();  wait_WEL();
    F0F0:F0F1:F0F2 = addr;            // 24-битный адрес
    F0E6 = (F0E6 & 0x0C) | 1;
    F0F4 = 3;  F0EA = 2;
    F0EC:F0ED = n - 1;
    F1C0 = 0x02; ... F1C1 = 1; F1C0 = 0x04;   // исполнить
    F0E5 = 1;  while (F0E5 & 1);
    F1C0 = 0;
    addr += 0x100;  len -= n;
    wait_WIP();
}
FUN_C2C2(&buf);                       // вернуть защиту
```

Рабочие переменные: `0xA4BA`/`0xA4BB` — 16-битный указатель на источник в XDATA,
`0xA4BC`…`0xA4BF` — 32-битный адрес во флеше, `0xA4C0`/`0xA4C1` — длина.

### Защита от записи и `CMD_SPI_PP_EN`

`FUN_8314` и `FUN_C2C2` **первым делом проверяют бит `0x0D`** побитово адресуемой
памяти и при сброшенном бите не делают ничего (`JNB 0x0D` → выход).

Этот бит ставит команда почтового ящика **`0x2E`** (`0x2A1A`), та самая, что печатает
`CMD_SPI_PP_EN : %d, %d`: бит 0 параметра → флаг `0x0D`, бит 1 → флаг `0x0E`
(последний проверяется отдельно, в `0xCC6E`).

То есть снятие аппаратной защиты флеша — **отдельно взводимое разрешение**, а не
часть операции записи. Сами page program и erase этим битом не закрыты: если
защитные биты в регистре статуса и так сняты, писать можно без `CMD_SPI_PP_EN`.

Неизвестный тип флеша `FUN_8314` не прощает: печатает `error flash!!!` и виснет на
`SJMP` на себя (`0x8386`).

## Кто это вызывает: почтовый ящик из Leon2 Main

Точек вызова у записи и стирания мало, и все ведут в один диспетчер.

Диспетчер почтового ящика — таблица переходов на **`0x24EA`**, 49 записей по 3 байта
(`LJMP`), индекс = `команда − 1`, проверка `CJNE A,#0x31` + `JC`; всё за пределами —
на общий выход `0x2A52`. Параметры команды лежат в `0xA4AE`, `0xA4AF`, `0xA4B0`.

| Команда | Обработчик | Что делает |
|---|---|---|
| `0x11` | `0x2643` | ждёт готовности (`FUN_D1D8`), затем **запись во флеш** (`FUN_E4A3` → `FUN_7D8F`) |
| `0x12` | `0x264E` | то же → **чтение** (`FUN_E471` → `FUN_8868`) |
| `0x13` | `0x2660` | то же → **стирание** (`FUN_EB73` → `FUN_9A7F`) |
| `0x14` | `0x2620` | **задать адрес** — печатает `Update FE2P Addr %08lx` (`FUN_E3D5`) |
| `0x15` | `0x266C` | то же → `FUN_B034` — **FE2P ProgramRange** (a1 — длина) |
| `0x16` | `0x2708` | `CMD_SYS_POWERSAVING` |
| `0x17` | `0x274A` | `CMD_SYS_POWEROFF` |
| `0x1C` | `0x27DB` | `setWakeupTimer %04x` |
| `0x1D`/`0x1E` | `0x2801`/`0x2828` | `CMD_SET_P14` / `CMD_SET_P15` |
| `0x21` | `0x2775` | `CMD_WRITE_DPTXHDCP` |
| `0x26` | `0x268C` | `CMD_FE2P_SETEXTEND : %02X%02X%02X` |
| `0x2E` | `0x2A1A` | **`CMD_SPI_PP_EN`** — разрешение снимать защиту |

Команды `0x1D`/`0x1E` сначала пишут `F0CC=30`, `F1F0=FF`, `SFR:A5=FF`, затем по
нулевому/ненулевому аргументу выполняют `CLR`/`SETB` bit-address `0x94` и `0x95`, то
есть `P1.4` и `P1.5` 8051. Это реальные дискретные выходы, но их назначение на плате
не установлено. Обёртки отправки присутствуют в Main FW.037 (`D03A0`/`D0360`);
их фактическое выполнение и сообщения `CMD_SET_P14/P15` в живых UART-захватах
этим не подтверждены. В полном исправленном листинге STBC Main это единственные
обращения к битам `0x94`/`0x95`, а записей всего `SFR P1` нет, поэтому штатным
механизмом LED в FW.037 они не являются. Короткий ISP-опыт может проверить только их
физическую разводку — [`led-indicator.md`](led-indicator.md).

`FUN_E4A3` (обёртка записи) берёт параметры из глобальных переменных XDATA, а не из
полей команды:

```c
src  = 0xA800;                 // фиксированное окно XDATA, куда Leon2 кладёт данные
addr = [0xA768..0xA76B];       // 32-битный адрес во флеше
len  = [0xA76C..0xA76D];       // 16-битная длина
FUN_7D8F();
```

Рядом лежит `FUN_E14F` — **цикл стирания**: номер блока в `0xA7B6`/`0xA7B7`, счётчик
блоков в `0xA7B8`, опкод в `0xA7B9`; вызывает `FUN_9A7F` нужное число раз, увеличивая
номер блока.

`FUN_D1D8` — не проверка прав, а **ожидание готовности**: до 20000 (`0x4E20`) итераций
опроса; возвращает 0 по таймауту, и тогда обработчик операцию пропускает.

## Транспорт почтового ящика

Диспетчер `FUN_245E` принимает **одно 32-битное слово**: младший байт — код команды,
три старших — аргументы (раскладываются в `0xA4AE`, `0xA4AF`, `0xA4B0` и в 16-битное
поле `0xA4B1`/`0xA4B2`). Точек входа две, и обе читают одну и ту же общую память:

- `0x237C` — из packet type06 COMMAND_BATCH (указатель `0xA48E`, счётчик `0xA496`);
- `0xA37F` (`FUN_A35D`) — четыре байта, прочитанные `FUN_B548`.

`FUN_B548` ходит через `FUN_CD27` — это **мост PBus→AHB**: 32-битный адрес пишется в
`0xCD80`…`0xCD83`, пуск `0xCD8C = 0x40`, опрос бита 0, результат из `0xCD88`…`0xCD8B`
(ошибка моста печатает `PBus to AHB bridge Error!!`). То есть 8051 читает почтовый
ящик прямо из общей памяти Leon2. **Внешней шины здесь нет.**

Со стороны Leon2 Main отправка — вызов функции service runtime из раздела `id=0x0D`
с сигнатурой `(команда, арг1, арг2, арг3, флаг)`. В FW.037 это **`0xA002F770`**, а в
FW.034 — **`0xA002F3EC`**. Функция не является ПЗУ: она лежит соответственно по
файловым смещениям `0x0D7770` и `0x0D73EC`, пишет слово в `0x9F0A0100` и ждёт его
очистки. Вызывается обычным `call` и через вычисленный `sethi`/`jmpl` — второй вариант
легко пропустить при поиске. Полный разбор — `docs/scaler-service-runtime.md`.

Расшифровку дал `MailBox_LoadFE2P` (`FUN_000D0638`, строка `0x0015EDC0`): он шлёт
`0x14` (задать адрес), затем `0x12`. Отсюда и уточнение таблицы выше: **`0x12` — это
чтение, а не стирание**, как предполагала первая редакция.

## Отправители flash-команд: исправление отрицательного результата, 2026-09-17

Прежний вывод «в Main нет отправителей 11/13/15» **опровергнут повторным разбором
Ghidra**. Его нельзя использовать для вывода о роли ROM или неиспользуемом SDK API.

| Main FW.037 | Доказанный вызов A002F770 |
|---|---|
| `D06CC`, call `D06FC` | command11 после command14: программирование |
| `D0708`, call `D0738` | command13 после command14: стирание |
| `D0794`, call `D07D0` | command15 после command14: диапазон буфера (ранее ошибочно WriteByte) |
| `D0438`, call `D04EC` | command18: адрес индикации, также пропущенный старой картой |

Обёртки присутствуют в машинном коде и подтверждены Ghidra xrefs к A002F770.
Это ещё не доказательство выполнения каждой из них при обычном использовании
монитора. Кроме прямого command word существует **packet type06 COMMAND_BATCH**:
STBC `233E..2385` передаёт до четырёх слов в тот же 245E. Поэтому отсутствие
прямого вызова конкретной команды не доказывает её недоступность.

В ходе уточнения восстановлены имена 49 commands и 15 packet types, включая
SPI register read/write 2C/2D, policy2E и FE2P buffer write packet07.
Аргументы, handshake, границы, реальные и неизвестные эффекты —
stbc-mailbox.md (не опубликовано). Старый счётчик 45 точек и полученный из него
«полный» набор команд больше не используются как доказательство полноты.

## Что из этого следует

Примитивы erase/program действительно принимают произвольный flash address и
длину из FE2P globals. Однако **буфер имеет только 2048 bytes (A800…AFFF)**;
16-битное поле длины не означает наличия 64-КиБ буфера. Размер a1*256 задаётся
command14, а packet07 пишет фрагменты до16 bytes в это окно. Реализация должна
согласовывать доступ к нему и не читать чужую XDATA за концом буфера.

D9EC вычисляет `address=base+extend+offset`, DE12 возвращает relative offset,
E3D5 публикует его в portal+B4. C797 обходит 2048 bytes, но вследствие фактического
алгоритма сдвига нулевого аккумулятора возвращает ноль; ECF9 публикует это слово
в portal+B0. Это подтверждено запуском оригинальных инструкций в s51;
описание и воспроизведение (не опубликовано).

Наличие этих примитивов не устанавливает, что штатный USB updater использует
именно их. USB ISP имеет отдельное [исследование протокола](usb-isp-protocol.md);
связь с ROM нельзя выводить из старого ошибочного отсутствия отправителей.

## Границы применения

Драйвер STBC не проверяет запись по таблице разделов; отдельные helpers имеют
ограничения буфера, а не защиту boot region. Уникальные данные экземпляра находятся
в **I2C EEPROM U4003**, их не защищает и не изменяет этот SPI-драйвер. Сохранность
boot/recovery U4002 всё равно зависит от выбранного адреса/сектора.

Erase helper 9A7F принимает **номер блока**, а command13 — текущее байтовое
FE2P-положение и сам переводит его в номер 4-КиБ сектора. Эти уровни нельзя путать.
Флаг0E `CMD_SPI_PP_EN` уже разобран: выбирает две вместо трёх TX bytes у command2D.
Полная карта Mailbox вынесена в отдельный справочник (не опубликовано).
План дальнейшей проверки — только шаг 52 (не опубликовано).

SPI FE2P и SYSAPI EEPROM — разные механизмы, каждый со своей парой read/write.
Сравнение MailBox_LoadFE2P с SYSAPI_WriteEEPROM раньше создавало ложную асимметрию;
она исправлена в [fe2p.md](fe2p.md). Наличие в Main SPI wrappers не означает запись
уникальных данных в U4002: данные экземпляра остаются в U4003.

## Проверка flash handshake при реализации STBC (2026-09-18)

Полный штатный command27 подтверждён в s51 без изменения vendor instructions:
ожидание lowbyte portal+B8==1, F00A/F0E0=AA, свежий read B8, write lowbyte2 с
сохранением upper24, readback, F00A/F0E0=55 и обычный command ACK.
Readback может уже содержать lowbyte0: штатный код его не сравнивает с2.
Отдельный owner в собственной реализации запрещает повтор после сбоя; при
неудавшемся release watchdog controls всё равно восстанавливаются.
Этот handshake сам по себе не защищает локальный FIFO, DMA/F600 и EAR.
Контракт, отличие при timeout и воспроизведение —
спецификация §33 (не опубликовано).

## FE2P FIFO read и EAR (2026-09-18)

`8868..89B0` не посылает EAR-команд. Старший byte32-битного source не попадает
в регистры; используется текущий EAR. Это проверено исполнением неизменённого
command12 с тремя разными старшими byte source и одним low24 адресом.
Сведения о явной записиC5 в DMA helpers выше не распространяются на этот путь.
`tools/stbc_spi_read_probe.py` проверяет45 сценариев до command ACK.
Собственный FIFO driver сохраняет текущий банк и ограничивает destination A800..AFFF;
контракт и частичный результат при ошибке (не опубликовано).

## Сохранение защиты и исправление command15 (2026-09-18)

Проверка75 запусков dispatcher266C→B034→7D8F опровергла название WriteByte:
`a1` задаёт число bytes, source=A800+offset, flash address=FE2P address+offset,
offset=a2:a3. Значениеa1 не копируется в RAM и не является данными для flash.
Актуальное имя — FE2P_PROGRAM_RANGE; источник уже заполнен packet07 или другим
производителем общего буфера.

Примитивы8314/C2C2 подтверждены64 симуляциями с настоящими инструкциями.
Они интерпретируют high nibble **индекса таблицы** XDATA3066, а не JEDEC vendor ID.
Для индекса87 временная защита снимается WRSR01 payload[00,SR2&02], затем
восстанавливаются сохранённыеSR1/SR2. Бypass bit0 пропускает обе процедуры;
register-format bit1 не управляет их длиной. Группа50 пишет толькоSR1.
Собственные bounded helpers переиспользуют boot ABI и SPI register driver;
полная таблица и поведение при сбое (не опубликовано).

## Page-program FIFO и граница страницы (2026-09-18)

7D8F и9A7F проверены36 исполнениями исходных инструкций с модельюMMIO.
В page-program F0EA=02; затемF1C0=02, два чтенияF1C0, второй результат пишется
вF0EE, F1C2 читается/перезаписывается, F1C1=01,F1C0=04,start1.
Нельзя переносить register-write recipe82→84 на этот путь без этих шагов.
И program, и erase используют текущий EAR; низшие24 бита адреса идут в операцию.

Stock7D8F не ограничивает chunk остатком физической страницы: two-byte запись
с...FF идёт одним packet. GD25Q256E Rev1.1 (не опубликовано),
§7.15, стр.31, определяет wrap внутрь той же256-byte страницы. Поэтому собственный
primitive делит запись именно по физическим границам страниц. Это сознательное
исправление ошибки для невыровненных диапазонов; stock trace на обычных выровненных
записях сохранён. Доказательства и границы проверки (не опубликовано).
