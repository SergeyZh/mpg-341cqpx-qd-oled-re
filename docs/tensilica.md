# Ядро Tensilica: база загрузки и карта памяти

Раздел id=0x03, файл `0x030000–0x03D8DC`, 55 516 байт (0xD8DC) — четвёртое ядро,
**Tensilica Xtensa LE**. На нём живёт контур LDC/ABL (на OLED — ограничитель яркости)
и собственная отладочная консоль `TDBG >>`.

Воспроизвести: `./tools/ghidra_import.sh tensilica`

## База — 0x40000000

**Адрес `0x40000000` соответствует файловому смещению `0x030000`**, образ занимает
`0x40000000–0x4000D8DC`. Установлено тремя независимыми способами.

### 1. Таблица секций на 0x3AC38

В конце кодовой части лежит таблица троек `(dst_start, dst_end, src)` — то, что
GCC для Xtensa называет `_memmap_table`. Пятнадцать записей, из них три непустые:

| dst | размер | src | файл |
|---|---|---|---|
| `0x3FFE0000–0x3FFE1A70` | 6 768 | `0x4000ACF8` | 0x3ACF8 |
| `0x3FFE1A70–0x3FFE238C` | 2 332 | `0x4000C768` | 0x3C768 |
| `0x3FFE2390–0x3FFE2BE4` | 2 132 | `0x4000D088` | 0x3D088 |

Таблица сходится сама с собой: `src + размер` каждой секции равен `src` следующей,
а последняя оканчивается ровно на `0x4000D8DC` — то есть на размере раздела id=0x03
(`0xD8DC`) от `0x40000000`. Промахнуться базой и получить такое совпадение нельзя.

Адрес самой таблицы (`0x4000AC38`) лежит литералом на `0x4000041C`, в стартовом коде.

### 2. VECBASE в стартовом коде

Образ начинается не с кода, а с **таблицы оконных векторов Xtensa**: по `0x40000000`
идут четыре `s32e` со смещениями −16/−12/−8/−4 и `rfwo` (`00 34 00`) — канонический
`_WindowOverflow4`. Стартовый код это подтверждает явно:

```
40000454  l32r a2, 0x40000408      ; литерал = 0x40000000
40000457  wsr  a2, VECBASE
```

Ядро само выставляет базу векторов в `0x40000000` — значит по этому адресу лежит
начало образа и память там исполняемая.

### 3. Строки и декомпиляция

При отображении `0x3FFE0000 = файл 0x3ACF8` указатель на себя находят **140 строк
из 142**. Декомпиляция при этих условиях даёт связный код — вот `LDC_LoadPanel`:

```c
if (0x20 < LEDrow * LEDcol) {
    printf("Configured seg size is over than tensilica seg buf size!!");
    printf("Leon2M conf LED_col = %d, LED_row = %d", ...);
    printf("Tensilica LED_CH_NUM = %d", 0x20);
    printf("LDC_LoadPanel Error!!"); }
printf("PanelInfo");
printf("Resolution: %d x %d", ...);
printf("DriverDuty: Max %04x Min %04x", ...);
```

## Карта памяти

| Область | Что | Откуда известно |
|---|---|---|
| `0x40000000–0x4000ACF8` | векторы + код (`.text` с литеральными пулами) | VECBASE, дизассемблер |
| `0x4000ACF8–0x4000D8DC` | образы секций данных для копирования | таблица секций |
| `0x3FFE0000–0x3FFE1A70` | строки (`.rodata`) | секция 1 |
| `0x3FFE1A70–0x3FFE238C` | таблица указателей на строки и прочие литералы | секция 2 |
| `0x3FFE2390–0x3FFE2BE4` | `.data` — изменяемые параметры, в том числе LDC | секция 3 |
| `0x3FFC0000` | очищается циклом в старте — похоже на `.bss` | дизассемблер |
| `0x3FFE2BF0`, `0x3FFE3E00`+ | структуры и массивы за концом `.data`, заполняются на старте | ссылки в коде |
| `0xE009xxxx` | окно регистров ядра (`0xE009104C`, `0xE0091080`, `0xE0091084`) | обращения под `memw()` |
| `0x3FFEF000`, `0x60000000` | адресуются пустыми записями таблицы; назначение **не установлено** | — |

Что лежит в `.data` по адресам — параметры LDC/ABL и таблицы усиления — разобрано в
`docs/oled-panel-abl.md`.

**Почему прежние поиски «литерал → строка» давали ноль.** Код обращается к строкам не
по их адресу во флеше, а по адресу **после копирования в DRAM**. Скан по образу искал
`0x4000xxxx`, а в литералах лежит `0x3FFExxxx`. Это тот же класс ошибки, что описан в
`CLAUDE.md` для четырёх механизмов адресации строк, только пятый его вариант.

Литеральный пул тоже уехал в DRAM (секция 2), и это работает: от кода на `0x40000000`
до пула на `0x3FFE1A70` ровно 124 КБ, а `l32r` дотягивается назад на 256 КБ.

## Стартовый код

Точка, с которой ядро получает управление, в образе **не найдена** — `VECBASE`
выставляется уже исполняющимся кодом, то есть стартовый адрес задан снаружи (ROM ядра
или загрузчик другого процессора). Что делает сам старт (`0x40000444` и далее):

1. `wsr VECBASE, 0x40000000`, `wsr ATOMCTL, 0x15`, `rsil 1`;
2. настраивает TLB циклом `witlb`/`isync` — то есть у ядра есть MMU;
3. чистит область `0x3FFC0000` и копирует секции по таблице `0x4000AC38`;
4. инициализирует окна регистров (`WindowStart`, `WindowBase`), заполняет
   `EXCSAVE2..EXCSAVE5`;
5. `call0 0x40000800` — вход в основную программу.

## Ghidra

Импорт делает `tools/ghidra_import.sh tensilica`. Две вещи обязательны, иначе результат
бесполезен:

- база выставляется **до** анализа (`-preScript SetImageBase.java`), а не после, как у
  остальных образов: DRAM-блоки создаются по абсолютным адресам, а `setImageBase` с
  коммитом сдвигает вместе с образом все блоки, включая их;
- `AddTensDram.java` создаёт блоки DRAM по той же таблице секций. Без них `l32r`
  указывает в пустоту.

Цена вопроса, замерено на одном и том же образе:

| | функций | инструкций | строк |
|---|---|---|---|
| без DRAM-блоков | 283 | 13 744 | 125 |
| с DRAM-блоками | 284 | 16 116 | 268 |

## Что осталось неизвестным

- Исполняется ли `.text` прямо из окна флеша по `0x40000000` или туда отображён ОЗУ-теневой
  образ. Для анализа безразлично, но для записи по `mem`/`wmem` — нет.
- Что такое `0x3FFEF000` и `0x60000000`. Второй похож на окно регистров по аналогии с
  `0xCF000000` у Leon2, но это догадка.
- Кто и когда стартует ядро и грузит ли кто-то образ во внутреннюю память.

## Отдельный эталон FW.034 для собственной Main

При работе с FW.034 нельзя применять таблицу секций FW.037 по умолчанию.
В034 размер id03 равен `D7DC`, SHA-256 точного image:
`00830664e56520111d9a941f7f8a56cd2ab35ae039fd44eb6027dcd7c87d1425`.
Literal по file3041C содержит4000AB38, поэтому таблица находится в file3AB38.
База исполнения остаётся40000000, но источники DRAM другие:

| DRAM | Источник034 CPU | Источник034 file |
|---|---|---|
| 3FFE0000…3FFE1A70 | 4000ABF8 | 3ABF8 |
| 3FFE1A70…3FFE2384 | 4000C668 | 3C668 |
| 3FFE2390…3FFE2BE4 | 4000CF88 | 3CF88 |

`AddTensDram.java` принимает необязательный второй аргумент `0x3AB38`;
без него сохраняется прежний default FW.037. Для034 сначала применять
`SetImageBase.java 0x40000000`, затем `AddTensDram.java /abs/FW034.bin 0x3AB38`,
оба как preScript перед анализом. Проверено импортом отдельного проекта
`tens-034`, без изменения проекта FW.037 и без аппаратного доступа.
`DecompAt.java` получает **начала** функций; передача interior address создаёт
искусственную функцию и может обрезать decompilation. В исследовании это
исправлено повторным импортом; выводы о порядке MMIO сверены с raw listing.
