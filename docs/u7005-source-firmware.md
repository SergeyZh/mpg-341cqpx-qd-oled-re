# Собственная прошивка U7005: совместимость и доказательства

2026-09-14. Реализация: [firmware/u7005](../firmware/u7005/README.md).
Эталон — APROM MSI приложения 54, `flash/u7005_aprom.bin`, SHA-256
`1b89385ed35d472d7f840325c7e6dee952510c53d364c854b383c3e4296d55cb`.
Готовый образ не содержит машинного кода MSI. Сборка опирается на открытые
CMSIS/StdDriver Nuvoton; интерфейс штатного LDROM сохраняется.

## Восстановленный контракт MSI

Источники: Ghidra `u7005_aprom.bin`, полный листинг `0000…7000`, релокация
`CB00…DC00 → 20002600…20003700`, и захват
`captures/update-034/usb-04-update-034.pcapng`. Адреса ниже относятся к этому APROM,
а не к образу NT68503. Общая аппаратная база — [mcu-u7005.md](mcu-u7005.md).

| Группа | Контракт и доказательство |
|---|---|
| USB | Дескрипторы по `6BF8`, `6C57`, `6C7B`, `6CA4`, `6CE8`, `6CF0`, `6D1C`; проверка извлекает соответствующие символы нового ELF и сравнивает байты |
| Report 1 | Диспетчер `1D38`; ASCII 5/8 уходит в выбранный service UART; локальные настройки, события и A0/B0/B2/B4/B6/C0/D0/D2/E0 разобраны по веткам |
| Report 2/4 | Таблицы `6D98` (UART TX), `6DBC` (I2C TX), `6DE0` (I2C RX), по 36 элементов A0…C3 |
| Сборка посылок | A5/A6/A7, B6/B7/B8, BF/C0/C1: начало/продолжение/конец; B9/BA/BB — отдельные записи |
| Report 3 | Четыре операции регистрового I2C; восстановлены по обработчику и примитивам чтения/записи, см. формат ниже |
| UART0 | `55CC`: обработка `5b0040`, `5b00;3`, `580074`, `5800;4`; ответы остаются на UART0 |
| Macro | Вектор IRQ4 указывает на `200028A0`; PB3 INTSRC.bit3 устанавливает байт `2000001B`, который возвращают C0/5800110 и очищают |
| Aux heartbeat | Report 1 `6800;30` возвращает/очищает `2000001A`, ставит `20000019=1`, сбрасывает TIMER0 CNT; IRQ `20002EF4` обнуляет оба флага |
| MSC | Диспетчер `2E4C`; INQUIRY — данные `DB14`; MODE SENSE(10) — `2D10`, страницы `DB38/DB44/DB64/DB0C`; capacity — `3228/3264/32A8`; запись — `342C → 12A8` |

Для TIMER0 `20002F0C` задаёт prescaler=9, CMP=`A8BF38`; источник 7 выбран в
инициализации. При HIRC 22,1184 МГц период ≈5 с. Новая реализация считает этот
таймаут через SysTick. Это перенос поведения из кода, не замер импульсов на плате.

Оба UART исходного приложения настраиваются через `CLK_SetModuleClock`
(`6AC`) с `0x03000000` и нулевым делителем (`5854`, `5A50`), а BAUD получает
`300000BE`. По определениям NUC1261 это HIRC / 192, то есть 115200 бод; новое
приложение задаёт HIRC и 115200 явно. Ранее выведенные из 48 МГц 250000 бод к
этому режиму не относятся. Независимый контроль со стороны скалера уже описан
в [mcu-u7005.md](mcu-u7005.md).

Формат Report 3 (полные HID-отчёты по 64 байта):

| Код | Запрос | Ответ |
|---|---|---|
| A0 | `03 A0 addr7 reg x value` | Первые 4 байта запроса, status в [4] |
| A1 | `03 A1 addr7 reg n x data[n]` | Первые 5 байтов, status в [5] |
| B0 | `03 B0 addr7 reg` | Первые 4 байта, status [4], значение [5] |
| B1 | `03 B1 addr7 reg n` | Первые 5 байтов, status [5], данные с [6] |

Успех = 1, ошибка = 0; остальные байты нового ответа нулевые. Чтение использует
адрес регистра и repeated START. Для исследованной revision=1 это I2C1. Новая
реализация ограничивает n диапазоном 1…58. Обработчики MSI не следует считать
безопасным эталоном поведения на некорректных длинах.

Report 4 сохраняет особенность A0/A1: NACK на SLA приводит к новому START для
следующего байта, последний NACK заканчивает сеанс успешно. Для обычных команд
NACK означает ошибку. Обычный обмен write/read включает STOP, задержку и новый
START. Задержка 10 мс для A7/AB/B5/B8, 2 мс для остальных читающих команд.

## Новая команда 4A

В разборе ASUS (не опубликовано) восстановлен запрос скалеру
`6E 04 4A addr24 XOR`. Новая прошивка выбирает банк командой 0F, ждёт 20 мс,
проверяет ответ `02 F0 bank XOR`, затем посылает 4A, ждёт 20 мс и принимает
515 байтов одной I2C-транзакцией: двухбайтовый заголовок, данные 512 байт, XOR.
SLA+R `6F` добавляется только к вычислению XOR. Последний физически принятый
байт завершается NACK. Дополнительного чтения handshake из I2C нет: в ASUS
это статус USB-моста, а не байт скалера.

Проверенная страница сохраняется в SRAM и выдаётся через 10 HID-ответов по
52 байта максимум. Discovery E2 нужен, чтобы не отправлять неизвестный индекс
в штатную таблицу MSI. Формат, token, ошибки и инвалидирование буфера описаны
в [спецификации v1](../firmware/protocols/u7005-flash-v1.md).

Вход в ISP остаётся в хостовой утилите и использует прежний `isp_read.Bridge`.
Наличие 4A в 8051 и использование ASUS сами по себе не доказывают ответ NT68503.
Первое аппаратное подтверждение на этом мониторе получено 2026-09-14:
[страница 512 байт совпала с обычным SPI-чтением](#аппаратная-проверка-исправленной-сборки).

## Что проверено программно

`make -C firmware/u7005 verify` собирает ARM-приложение, исполняет host-тесты
того же `bridge.c`/`msc.c`, затем проверяет бинарник:

- Все 36 подкоманд обоих транспортов, три семейства потоков, 4098-байтная передача,
  переполнение, восстановление после ошибочной последовательности.
- Локальные команды, настройки, вспомогательный UART, события; четыре операции
  Report 3; сохранение layout B0 и динамическая сумма приложения.
- В захвате обновления 52 710 исходящих Report 4. Повторное исполнение команд с
  записанными ответами I2C на границе HAL даёт **10 653 побайтово совпадающих
  HID-ответа**. Финальный A1 с `04 34 06 3C` в захвате не имеет входящего завершения
  из-за сброса — тест проверяет его отдельно как оставшийся запрос.
- Хостовая утилита работает с настоящим C-диспетчером через тестовый HID-адаптер:
  discovery, page/fetch, некратные адреса/длины, ошибки и границы 32 МиБ.
- Ошибки XOR и B5 отдельно, неправильный token, сброс буфера; I2C-ошибки не
  возвращают прежнюю страницу. Эти ответы скалера синтетические.
- MSC: SCSI-команды, чтение/запись последнего сектора, выход за границу, sense,
  residue, некорректный CBW, phase error/reset. BOT реализован с опорой на
  [USB-IF Bulk-Only Transport 1.0](https://www.usb.org/sites/default/files/usbmassbulk_10.pdf).
- 50 000 детерминированных случайных последовательностей под AddressSanitizer
  и UndefinedBehaviorSanitizer; проверка затрагивает протокол и MSC на хосте.
- ELF: векторы Cortex-M0, код ниже 64 КиБ, FMC leaf-функция и её литералы в SRAM,
  запас стека ≥2 КиБ. HEX: сумма байтов modulo 65536, длина, адреса сегментов,
  отсутствие данных в сохранённых областях.
- USB-установщик: сверка читающей последовательности с физической трассой LDROM,
  2304 пакета A0/00 на модели записи, границы стирания и сохранение DataFlash,
  проверка конечной 16-битной суммы, остановка без retry/AF при потере ACK,
  неверном sequence/checksum/CONFIG. Повреждённый комплект отвергается до USB.
- Нормализация метаданных исполняет тот же `boot_metadata.c` на хосте: проверка
  полной суммы, однократное обновление, отсутствие записи при обычном старте,
  ошибки FMC/метаданных, исключение mode/диска из суммы при сохранении проверки кода.
  Полный сеанс на модели доходит до нормализации C и проверки прикладного USB.

После исправления SysTick проходят **177 тестов**, сборка и проверки ELF/HEX.
Добавлен native-тест настоящего `usb.c` с моделью MMIO/StdDriver: ответ должен
уйти после одиночного запроса, без следующего USB-прерывания, при первом запуске
и после смены режима. Старый код без восстановления SysTick этот тест не проходит.
Отдельно проверено, что хостовый обход не принимает кеш GET_REPORT за новый ответ,
не повторяет команды и не применяется после записи нового приложения.
Новый код занимает 14 192 байта, сумма `8118`; USB BIN — 129 016 байт,
сумма `C62B`, SHA-256
`578c552682981790700017bd219a2ce683d5cb674c4fb6bff6291044e928beae`.
Использован сохранённый APROM экземпляра от 2026-08-16, USB mode=0.

Тесты не обращаются к USB-устройству. Они не исполняют аппаратный `board.c` и ISR
USBD на процессоре U7005; native-модель не проверяет электрические тайминги USB.
Частота, пины и порядок регистров взяты из BSP/разбора,
но тайминги и электрический обмен новой сборки не измерены.

## Отличия и граница результата

Реализован весь найденный набор прикладных HID-команд MSI v54. Это не утверждение
о побайтовом совпадении для любого входа или всех аппаратных побочных эффектов.
Новая реализация отбрасывает выход за таблицы и буферы, ограничивает ожидание I2C,
не переносит автовыбор альтернативного UART2 и ветку глубокого сна MCU из MSI
(условия и граница доказательства — ниже).
Поддержка неизвестных применений PWM/внутренних состояний за пределами описанного
контракта не доказана. USB suspend/resume через USBD предусмотрен, но не испытан.

MSC-диск создан заново как FAT12, его данные находятся в `10000…157FF`, отдельно
от контрольной суммы кода в создаваемом HEX. При установке через USB LDROM
заменяет эту сумму суммой всей передачи. Перед включением USB приложение проверяет
её и нормализует метаданные до длины/суммы кода, сохраняя страницу метаданных.
[Проверка установки и восстановления](u7005-ldrom.md#первая-установка-собственного-приложения-через-usb)
отделяет проверенные свойства кода от границ аппаратного опыта ниже.
Диск содержит новый короткий ярлык MSI, а не заводской
набор файлов. Сохранены SCSI-команды и INQUIRY; MODE SENSE(6) объявляет write-protect,
хотя сырой WRITE реализован, как и у MSI. Некорректные BOT-фазы проходят reset
recovery; полное соответствие сертификационному набору USB-IF не проверялось.

Обновление ID/настроек сохраняет остальные байты DataFlash. Оригинальное приложение
стирает страницу и восстанавливает только часть полей — это намеренное отличие.
При обесточивании посреди erase/program атомарности нет. В первом опыте пользователь
записал APROM через LDROM. Диагностика после ошибки использовала только читающие
команды приложения. LDROM/CONFIG, U4002 и U4003 в этом опыте не записывались.

Перед аппаратным признанием совместимости нужно сравнить запуск и USB enumeration,
HID GET/SET_REPORT и очереди, UART/I2C на известных коротких запросах, поведение
Report 3, mode/настройки, MSC, переход A0 в LDROM, suspend/resume и страницу 4A
с независимым чтением U4002. Это критерии шага 37 в основном плане, а не
полностью завершённые опыты. Текущие размеры и SHA-256 каждой сборки записывает manifest.

## Первый USB-запуск и ошибка SysTick

2026-09-14, исходники до исправления: `f7a649f2a6e3cd54a1b1a78bc658afb0a687fee4`.
Пользователь записал USB BIN с SHA-256
`e6ab8f5ba46dae16252dac44f875f7b08883e0fb9280468e92c7aee80e727a10`,
код 14 128 байт, сумма `624D`. Первичные данные:

- Сеанс установки (не опубликовано),
  исходные USB-пакеты (не опубликовано) и
  точный записанный образ (не опубликовано).
- Диагностика без обхода (не опубликовано).
- Диагностика с GET_REPORT (не опубликовано).
- Проверка новой командой verify (не опубликовано)
  и её пакеты (не опубликовано).

**Проверено на устройстве.** LDROM принял все 2304 пакета, конечная сумма совпала,
AF запустил приложение. B0 ответил `54`, LDROM `15/D926`, сумма приложения `624D`:
это согласуется с нормализацией метаданных после первого запуска. Установщик
остановился на B2, `stage=verifying_app`, `transfer_verified=true`, `complete=false`.
Полного независимого read-back APROM после записи не делали.

Повторный B2 не дал ответа за 6 секунд. Следующий B0 немедленно получил ответ B2
(`01205206`), B4 получил ответ B0, E2 — ответ B4, D2 — ответ E2. Это отставание
ответов на одну команду, а не отказ конкретного обработчика B2. Дополнительный
читающий GET_REPORT после пустого чтения устраняет задержку: последовательно
подтверждены B0/B2/B4/E2/D2, ID `1C33D802`, `U7EX v1`, USB mode=0.
GET_REPORT возвращает кеш последнего отчёта; его содержимое не принималось за
ответ команды, проверялся последующий interrupt IN.

**Причина по исходникам.** `board_init()` включает SysTick, но затем `usb_init()`
вызывает `USBD_Start()`. В закреплённом BSP Nuvoton `Library/StdDriver/src/usbd.c:109`
эта функция вызывает `CLK_SysTickDelay(100000)`. Реализация в `inc/clk.h:430–440`
перенастраивает SysTick и заканчивает `SysTick->CTRL=0`, не восстанавливая таймер.
В `usb_poll()` очередь TX обслуживается перед RX; обработчик команды кладёт новый
ответ в TX уже после этой проверки. Без следующего SysTick главный цикл засыпает
на WFI; следующее внешнее прерывание позволяет выгрузить ответ. Такой же дефект
останавливает миллисекундные таймауты и `board_delay()`, поэтому обход HID не
делает старую сборку пригодной для UART/I2C и чтения 4A.

**Исправление и граница проверки.** После каждого `USBD_Start()` добавлен
`SysTick_Config(SystemCoreClock/1000)`, в том числе при смене USB mode.
Новый комплект создан в `out/u7005-usb-tick-fix/`; старый не перезаписан.
Сборка и регрессионные тесты прошли; последующая запись и аппаратная проверка
описаны ниже. Полная совместимость UART/I2C/MSC/4A этим исправлением не доказана.
Хостовый `--wake-stalled-app` предназначен для чтения сведений и подготовки входа
в LDROM; после записи новая сборка проверяется без обхода.

## Что именно не перенесено из энергосбережения MSI

Уточнение 2026-09-14 по Ghidra-листингам APROM и его RAM-кода. Речь о локальном
Power-down микроконтроллера U7005. В основном цикле MSI `200031F0…2000322C`
проверяются два байта: `2000001C != 0` и `2000001D != 0`. При обоих установленных
флагах код выключает автоматическую подстройку HIRC48 (`SYS.IRCTCTL1=0`), очищает
статусы подстройки, возвращает исходное значение trim и вызывает `00000640`.
Эта функция устанавливает `SCB.SCR.SLEEPDEEP`, `CLK.PWRCTL.PDEN` и исполняет WFI.
Последовательность совпадает с `CLK_PowerDown` в используемом NUC1261BSP.

Второй флаг устанавливает TIMER1 IRQ (`20002F34`, адрес подтверждён вектором IRQ9);
он же ставится при USB detach. Обработчик USB `00005E08` очищает его и счётчик
TIMER1 при attach, reset, suspend, resume и SOF. Поэтому одного факта USB suspend
недостаточно для утверждения о немедленном глубоком сне: нужны таймер и первый флаг.

**Флаг разрешения `2000001C` исходно равен нулю.** Startup-таблица `6F5C…6F68`
копирует `C800…CAFF` в `20000000…200002FF`; байт файла `C81C` равен `00`.
Факт последующего включения этой ветки на физическом мониторе не подтверждён.
Здесь не утверждается отсутствие всех путей изменения флага. Прежняя формулировка
«алгоритм энергосбережения MSI не перенесён» не означала доказанную потерю активного
режима штатной конфигурации.

Собственное приложение использует обычный WFI между обработками событий,
SysTick продолжает будить ядро раз в миллисекунду. При USB suspend выключается PHY,
при resume USB включается обратно; установки SLEEPDEEP/PDEN и подготовки глубокого
сна нет. Если ветка MSI реально включается, возможное отличие — потребление самого
моста при сохранённом питании и поведение его пробуждения; ток и это поведение
не измерены. Поддержка USB suspend/resume новой реализации ещё требует опыта.

Сон всего монитора — отдельный механизм. В измеренном состоянии сна напряжение
на CN7003.1 пропадает: [питание U7005](mcu-u7005.md#питание-u7005-он-засыпает-вместе-с-монитором).
В этом случае мост обесточен независимо от его локальной Power-down-ветки.
Изменение прошивки моста само по себе не переносит управление сном панели/скалера
в U7005. Во время уточнения код и готовые установочные артефакты не изменялись.

## 4A в общих ISP-утилитах и таймаут длинной записи (2026-09-15)

`Bridge.read_flash()` из `tools/isp_read.py` теперь сначала проверяет E2/U7EX.
При поддерживаемой версии используется существующий `FlashReader` с READ/FETCH,
проверкой token, offset, статуса и длины страницы. Без ответа E2 либо при
неподдерживаемой версии сохраняется прежнее чтение через `A700`, максимум 249 байт
за SPI-транзакцию. Discovery кешируется на соединение, после USB reconnect
повторяется. Ошибка самой страницы, XOR или транспорта прерывает чтение, а не
скрывается fallback. Старому мосту Report 4/4A не отправляется.

Оба CLI принимают `--flash-read-method auto|legacy|4a` (по умолчанию `auto`).
`legacy` вообще не посылает E2; `4a` требует подтверждённое расширение. В
`isp_write.py` это относится к `--readback` и проверке `--force-dirty`; при
необходимости чтения discovery выполняется до стирания/записи.

Сохранён адресный контракт: `Bridge.read_flash()` и `isp_read.py --read` принимают
**смещение в текущем банке EAR**, а `isp_write.py --readback` — в выбранном банке
записи. Перед быстрым чтением EAR считывается заново и добавляется к адресу 4A;
не допускается молчаливое чтение банка 0 вместо банка 1. Диапазон внутри одного
банка проверяется до USB, пустое чтение не делает обмена. Для сквозного адреса
32-МиБ флеша и перехода через границу банков остаётся `u7005_flash_read.py`.

```sh
.venv/bin/python tools/isp_read.py --read 0 0x8000 --reuse -o out/head.bin
.venv/bin/python tools/isp_read.py --read 0 0x200 --reuse --flash-read-method legacy -o out/head-legacy.bin
```

**Аппаратно проверено:** по 512 байт с offset 0 обоих банков совпали с независимым
legacy-чтением; EAR остался выбранным после чтения и был возвращён в 0 после опыта.
Вызов общего API занял 0,422/0,424 с против 3,429/3,555 с для legacy — около 8 раз
быстрее на странице, включая чтение EAR. Отдельный поток 32 КиБ через `FlashReader`
до обновления моста занял 7,04 с. Полные 32 МиБ не читались.

Установка загрузчика выявила отдельный дефект моста: `wait_si()` отсчитывал 250 мс
от начала **всей** I²C-транзакции. Поток 4098 байт требует минимум
`4098 × 9 / 100000 = 0,369 с`, без software overhead и clock stretching.
Передача оборвалась на C1 с ACK `00`; последующая попытка 4A дала ошибку I²C.
Штатное закрытие блока `BC FF F2` вернуло доступ, а 32-КиБ read-back совпал с
резервной копией: первая попытка flash не изменила. Прямой трассы момента таймаута
нет; связь с ним подтверждается недостаточным лимитом в коде и успешной той же
передачей после единственного изменения 250 → 1000 мс.

С согласия владельца исправление установлено через USB LDROM. Код 14200 байт,
SHA-256 `6df3509e1bb884bf4a46bdce5e7855c573f822162ca89eba159fa36042774723`,
сумма `82DD`; USB BIN `58d25e918620ec7b4cfb0146f8e794d3398541075a923b189eed50e8b809c65e`.
Подтверждены сумма передачи, запуск приложения, U7EX, board ID и новая сумма кода;
полного независимого read-back APROM не было. DataFlash/CONFIG/LDROM/SPROM не
перезаписывались; код, виртуальный диск и хвост APROM сформированы обычным
установщиком из сборки и сохранённого дампа от 2026-08-16.

После обновления оба 4-КиБ сектора `bootloader-libre` записались, суммы сошлись,
read-back через 4A подтвердил новый образ и сохранность соседних 24 КиБ.
Это аппаратное подтверждение длинной записи на данном мосте; полная совместимость
остальных команд, MSC и suspend/resume по-прежнему не доказана.

`tools/test_isp_flash_read.py` и `tools/test_isp_recover.py` (34 суммарно).

исходные USB-пакеты обновления моста (не опубликовано).
