# Карта прошивки MSI MPG 341CQPX QD-OLED

Файл: `MSI_MPG_341CQPX_QD-OLED_FW.037_0225.bin`, 2 531 840 байт (0x26A200).
Образ **не сжат и не зашифрован** целиком — весь объём это открытый код и данные.
Сборка **Nov 10 2025 09:47:58**, внутреннее имя проекта `NVT_Formal_RG20189`.

Воспроизвести: `.venv/bin/python tools/fwmap.py MSI_MPG_341CQPX_QD-OLED_FW.037_0225.bin -o out/`

## Платформа

- Скалер: **Novatek NT68503** (семейство NT68500) — из конфиг-блока `55AA6699 "SCALER"` @0x203C28.
- Панель: **SDC QMC340CA01_D01** (Samsung QD-OLED) — из `55AA6699 "PANEL"` @0x203C40.
- Строка версии в коде: `NT68500 FW Version: %d.%d.%d (customer id = %d)`.

## Ядра

| Ядро | ISA | Роль | Где |
|---|---|---|---|
| STBC | 8051 | Загрузчик, SPI-флеш, standby, ADC-кнопки, MailBox | 0x000000–0x02E600 |
| Tensilica | Xtensa LE | Контур LDC/ABL (на OLED — ограничитель яркости) | 0x030000–0x03D900 |
| Leon2 Sub | SPARC v8 BE | HDMI/DP RX PHY, EQ, ModeDetect, link training | 0x050000–0x0A5600 |
| Leon2 Main | SPARC v8 BE | OSD, APP-задачи, управление панелью по I2C | 0x108000–0x26A100 |
| — | SPARC v8 BE | Раздел id=0x0B: тракт HDR/EOTF, база 0x9F1B0000 | 0x0B0000–0x0CF500 |
| — | SPARC v8 BE | Раздел id=0x0D: traps/HAL Leon2 Main, база 0xA0028000 | 0x0D0000–0x0D8100 |

«Leon2» — это не кодовое имя, а настоящий SPARC v8: подтверждено таблицами ловушек на
0x50000 и 0xD0000, долей валидных опкодов 73–88 % и текстами обработчиков
(`FP instruction while FPU disabled`, `CP instruction while Co-processor disabled`,
`Register file EDAC error(LEON-FT only)`).

### Адреса загрузки

**Leon2 Sub = 0xA0060000.** Установлено достоверно, четырьмя независимыми способами:

1. Таблица ловушек лежит ровно в начале региона, её первый обработчик — `sethi %hi(0xA0060000), %l4;
   jmp %l4+0x2C0`, то есть 0xA00602C0.
2. 68 % целей `sethi`+`jmp` попадают на начала функций; следующий кандидат даёт 4 %
   (`tools/findbase.py`).
3. Таблица указателей на 0x0A6000 содержит адреса вида 0xA00AD578, которые отображаются
   ровно на область строк Leon2S (файл 0x9D578).
4. Дизассемблирование с этой базой даёт связный код: `sethi 0x2802bc, %o0; or %o0, 0x30, %o0;
   call 0xA00682A0` — построение указателя на строку и вызов отладочного printf.

**Leon2 Main = база 0x00000000, адрес 0 соответствует файловому смещению 0x108000.**
То есть `address = file_offset − 0x108000`. Установлено и подтверждено:

1. Гистограмма разности («начало функции» − «цель `sethi`+`jmp`») даёт единственный пик:
   61 % целей попадают на начала функций, следующий кандидат — 1 %. Контрольный прогон
   той же методики на Sub даёт 68 % против 5 %, то есть метод откалиброван.
2. Прямая проверка дизассемблером: `sethi 0x577, %o2; or %o2, 0, %o0; call 0x7bd68` строит
   адрес 0x15DC00 — ровно адрес строки `OLED set lum mode` при этом отображении, и передаёт
   его в отладочный printf.
3. Автоименование по строкам даёт 51 осмысленный идентификатор прикладного уровня:
   `App_Initialize`, `APPSetPowerOff`, `APPSTATE_PWR_ON`, `DDCCi_SetVCP_Feature`, `ShowLogo`,
   `UartSetCmdProcess`, `APPGetFRCMode`. При неверной базе такого совпадения быть не может.
4. Размер раздела id=0x10 (1 450 060 = 0x16204C) от 0x108000 даёт конец 0x26A04C при длине
   файла 0x26A200 — раздел занимает весь хвост флеша.

Почему предыдущие попытки проваливались: регион для поиска брался как «плотный код»
(0x128100–0x200000), а строки лежат за 0x200000, вне этого окна. Кроме того, образ Main
начинается не с кода — на 0x128140 идёт конфигурационный блок, и SPARC-код стартует
только с ~0x1281C0.

Важное следствие: таблицы EDID (файл 0x118000) попадают внутрь раздела Main по
адресу **0x010000**, то есть это не отдельный «регион», а данные образа Main.

**Service runtime Leon2 Main = 0xA0028000**, файл `id=0x0D` с `0x0D0000`.
Это вторая часть той же программы Main: её reset vector переходит на `0xA0029000`,
runtime вызывает функции Main с базы 0, а Main FW.037 делает 1064 вызова к 37 его
экспортам. Внутри — trap table, IRQ, GPIO-I2C, timer/crash HAL, shared mailbox и часть
display/ISP HAL. Живой дамп FW.034 по `0xA002F770` полностью совпал с файлом
`0x0D7770` после перестановки байтов в словах. Разбор —
`docs/scaler-service-runtime.md`.

**Сегментация Main.** По плотности валидных опкодов SPARC (окна по 32 КБ) регион чётко делится:

- `0x128000–0x200000` — **код** (80–98 %);
- `0x200000–0x26A200` — **данные и ресурсы** (27–54 %): строки OSD, языковые таблицы,
  конфиг-блоки `SCALER`/`PANEL`/`UART`.

Прочие окна: регистры — **0xCF000000**; в Main доминируют ссылки на **0xA8000000** —
это область данных в DRAM, а не база кода.

**Tensilica = 0x40000000**, адрес 0x40000000 соответствует файлу 0x030000. Установлено
таблицей секций на 0x3AC38 (её последняя секция кончается ровно на размере раздела),
инструкцией `wsr VECBASE` с литералом 0x40000000 в стартовом коде и разрешением 140 строк
из 142. Данные ядро копирует в DRAM `0x3FFE0000–0x3FFE2BE4` и адресует уже там — разбор
и карта памяти в `docs/tensilica.md`.

**Почему адреса данных именно такие — видно по железу.** На плате четыре корпуса
`NANYA NT5CB128M16JR-FL` (DDR3, 2 Гбит каждый) = **1 ГиБ при 64-битной шине**
(`docs/hardware-boards.md`). 1 ГиБ — это `0x00000000–0x3FFFFFFF`, то есть
`0x3FFE0000` = вершина памяти минус ровно 128 КиБ, и рабочие данные Tensilica вместе с
параметрами ABL (`0x3FFE2390`) лежат в самом верху физической DRAM.

Переименовано по отладочным строкам (`tools/name_by_strings.py` → CSV → `ApplyNames.java`):

В Main имена дополнительно обёрнуты ANSI-escape и хвостами формата, поэтому извлечение
идентификатора устроено с их отбрасыванием.

Две особенности headless-импорта, на которые ушло время:

- `-loader-baseAddr` для сырого бинарника **молча игнорируется**; база выставляется

- у сырого образа нет точки входа, поэтому 8051 дизассемблировался в ноль функций, пока

## Таблица разделов @0x6000

Формат записи — 8 байт: `u8 bank, u8 id, u16 lo, u32 size` (всё big-endian), и
**адрес раздела во флеше = `(bank << 24) | (id << 16) | lo`**. Формула установлена по
дампу `U4002`, проверена на четырёх независимых таблицах и подтверждена загрузчиком:
`id` и `lo` он отдаёт железу как `F1D5:F1D4:F1D3`, а `bank` — самой микросхеме командой
`0xC5` (Write Extended Address Register). `bank` = номер 16-мегабайтного слота прошивки;
в файле MSI он нулевой, в чипе бывает и `0x01` — `docs/flash-u4002.md`.

| id | lo | смещение | size (037) | Что это |
|---|---|---|---|---|
| 0x01 | 0x0000 | 0x010000 | 61 478 | 8051, основной код |
| 0x02 | 0x0000 | 0x020000 | 58 706 | 8051 AUX, агент USB/ISP |
| 0x03 | 0x0000 | 0x030000 | 55 516 | Tensilica Xtensa LE |
| 0x05 | 0x0000 | 0x050000 | 349 504 | Leon2 Sub |
| 0x0A | 0x6000 | 0x0A6000 | 10 216 | инициализированные данные Leon2 Sub → `0xA8076000` |
| 0x0B | 0x0000 | 0x0B0000 | 128 192 | тракт HDR/EOTF |
| 0x0D | 0x0000 | 0x0D0000 | 32 968 | service runtime Leon2 Main @`0xA0028000` |
| 0x0E | 0xC000 | 0x0EC000 | 23 200 | инициализированные данные Leon2 Main → `0xA8024000` |
| 0x10 | 0x8000 | 0x108000 | 1 450 060 | Leon2 Main |

Во всех девяти случаях `смещение + size` попадает ровно в последний не-`0xFF` байт
соответствующей области данных — и в FW.034, и в FW.037, и в заводской FW.023.

Раньше здесь стояло, что id=0x0D — это EDID, id=0x0E — ресурсы OSD, а размер id=0x10
«не сходится». Всё три неверно: EDID отдельным разделом не являются (они внутри id=0x10
по адресу 0x010000), а `0x108000 + 0x16204C = 0x26A04C` — конец данных образа.

Загрузчик выбирает адрес этой таблицы динамически: если `CODE[0x7FFF] == 0xAA`, таблица
берётся с **0x7000** (альтернативный слот), иначе с **0x6000**. В этом образе байт равен 0,
сигнатура `DUALFW` на 0x6FF0 отсутствует, значит режим двух прошивок выключен —
подробности в `docs/bootloader.md`.

Прежний счёт «сумма размеров = 102 % от данных» был артефактом неверной привязки:
разделы не покрывают образ подряд, а id=0x0D лежит на 0x0D0000, а не поверх EDID.
При правильных смещениях перекрытий нет.

**Что в таблице осталось непонятым:** где хранится контрольная сумма. Зацепка —
конфиг-блок `CHKS` из заводской FW.023, см. `docs/flash-u4002.md`.

## Конфиг-блоки `55 AA 66 99`

| Смещение | Тег | Содержимое |
|---|---|---|
| 0x0EC020 | `VERSION` | `u16 0x0025` = 37 (FW.037) |
| 0x203C28 | `SCALER` | `NT68503` |
| 0x203C40 | `PANEL` | `SDC QMC340CA01_D01` |
| 0x259988 | `UART` | `A5` — флаг включения отладочной консоли |
| 0x259998 | `PANEL` | `SDC QMC340CA01_D01` (дубль) |

Запись на `0x0EC020` имеет вид
`55 AA 66 99 "VERSION" 02 00 25`: `02` — длина значения, а `00 25` —
сама версия. Это тот же формат, что у `SCALER 07 "NT68503"` и
`PANEL 12 "SDC QMC340CA01_D01"`. Поэтому байты после `00 25` не являются
таблицей, связанной с тегом `VERSION`.

Раздел id=0x0E целиком — блок инициализированных глобальных данных Leon2 Main,
который копируется из файла `0x0EC000` в RAM `0xA8024000`. В нём лежат структуры,
флаги, callback-адреса и дескрипторы OSD с указателями на ресурсы в id=0x10,
а не самоописывающийся список прошивочных модулей. Например, указатели
`0x000FC258`, `0x000FCE38`, `0x000FD8B8`, `0x00107940` и `0x00108548`
адресуют палитры и RLE-банки загрузочной заставки; файловое смещение ресурса
равно адресу Main + `0x108000`. Форматы и назначения этих полей подтверждены
в `docs/logo.md`.

## EDID и кадровая частота

Воспроизвести: `.venv/bin/python tools/edid.py MSI_MPG_341CQPX_QD-OLED_FW.037_0225.bin --dump out/edid`

60 базовых блоков EDID, все — MSI 0x4DD0 `MPG341CX OLED`, каждый с расширениями
CTA-861 и DisplayID **1.2** (не 2.0; тип I Detailed Timing, тег 0x03).

Высокочастотные режимы лежат **только в DisplayID**, в базовых блоках их нет:

| Режим | Pclk | Htotal | Vtotal |
|---|---|---|---|
| 3440×1440 @ 240.00 Гц | 1324.64 МГц | 3584 | 1540 |
| 3440×1440 @ 164.99 Гц | 926.00 МГц | 3600 | 1559 |
| 3440×1440 @ 119.99 Гц | 658.75 МГц | 3600 | 1525 |
| 3440×1440 @ 99.98 Гц | 582.75 МГц | 3600 | 1619 |

Дескрипторы пределов: `V 48–240 Гц, max pclk 1500 МГц` (32 + 8 блоков), а также наборы
на 120 Гц/600 МГц и 165 Гц/950 МГц — это профили для разных входов и режимов DSC.

**Вывод по цели «увеличить кадровую частоту».** Выше 240 Гц в EDID нет ничего — ни режима,
ни предела. То есть простой «разлочки» правкой EDID не существует. Единственная зацепка:
объявленный предел 1500 МГц против фактических 1324.64 МГц на 240 Гц, то есть ~13 % запаса
*в поле EDID* (при том же бланкинге это дало бы ~271 Гц). Но это лишь декларация для источника;
реальный потолок определяют T-CON панели и таблицы таймингов скалера. Проверять — в фазе 5.

Позже это подтвердилось ещё дважды: таблицы EDID **побайтово идентичны** между FW.034
и FW.037 (`docs/version-diff.md`), а по внешним источникам панель здесь — Samsung QD-OLED
gen 2 (2024) с паспортными 240 Гц; 34-дюймовая панель на 360 Гц у Samsung есть, но это
другая панель 2025 года (`docs/external-research.md`). Потолок задаёт панель,
а не программный замок.

## Что прошивка держит в DRAM

Сводный указатель переменных, найденных в разных разборах. Это раскладка **прошивки
MSI**, а не свойство кристалла: аппаратная карта адресных пространств — в
`docs/nt68503-hardware.md`. Таблица нужна, чтобы при работе с живой памятью было видно,
какие окна заняты; промежутки между ними свободными считать нельзя.

### Кадровые буферы в физической DDR

Кроме окна globals `0xA8xxxxxx`, у CPU Main есть прямой доступ к физической DDR по
низким адресам `0x00000000–0x3FFFFFFF` (аппаратная сторона — `docs/nt68503-hardware.md`
§3.1). Кадровые буферы MSI размещает в её верхней половине. Снято живьём с консоли Main
2026-08-19 (`captures/leon2main-fw034-ddr-framebuffer-2026-08-19.log`):

| Адрес | Что | Как установлено |
|---:|---|---|
| `~0x2A000000` (полосы `0x29000000–0x2C000000`) | **активный кадровый буфер** — отслеживает экран | change-tracking: смена картинки изменила `0x2A800000` (цветное → `0x19191919`), стоячие области не тронулись |
| `0x20000000` | стоячий буфер с пиксельными данными (~20 МиБ) | при смене картинки **не** изменился |
| `0x26/0x28/0x2E/0x30/0x36/0x38/0x3E…` | белёсые `FF`-буферы (другие кадры/слои) | не менялись при смене картинки |

Формат — 32 бита на пиксель (в серых зонах все 4 байта равны). Активная область
`~0x29000000–0x2C000000` ≈ 48 МиБ при кадре `3440×1440×4 = 18,9 МиБ` — вероятно
двойная/тройная буферизация. Точная база буфера и число копий не добиты; кадр
пишется DMA сканера, CPU Main его только читает. Нижняя половина DDR
(`~0x01000000–0x1FFFFFFF`, ~496 МиБ) свободна, но записать в неё с CPU Main нельзя —
`store` туда игнорируется (2026-08-21, `docs/leon2-main-ram-development.md`).

### `id=0x0A` — это `.data` ядра Sub, а не отдельная «таблица указателей»

Раньше раздел значился в этой таблице как «таблица указателей `0xA00xxxxx`» — по первым
словам, которые действительно указатели. Разбор 2026-09-06 показал, что он **ровно то
же самое для Sub, чем `id=0x0E` является для Main**: секция инициализированных данных.

Довод — размах абсолютных ссылок. Все **2 079** адресов вида `0xA8xxxxxx`, собранных из
пар `sethi`+`or` по всему образу Sub, лежат в `0xA8076000…0xA807FF94` и **ни один** вне
этого окна. Окно ровно `0xA000` = 40 КиБ, и столько же занимают раздел плюс заливка
нулями сразу за ним: движок `F600` кладёт 10 216 байт по физ. `0x9F196000`, а хвост
`0x9F1987E8…0x9F1A0000` обнуляет (`docs/nt68503-hardware.md` §4.3). Из этих ссылок
**404 попадают в инициализированную часть, 1 675 — в обнулённый хвост**, то есть
`.data` и `.bss` соответственно. У Main картина та же с точностью до адресов: 8 370 из
8 372 ссылок лежат в `0xA8024000…0xA803E400`, а туда кладётся `id=0x0E` с заливкой до
`0x9F07C000`.

Отсюда база: `0xA8076000` ↔ физ. `0x9F196000`, то есть смещение `0x08EE0000` — **не то
же самое**, что у данных Main (`0x08FC4000`), и это ожидаемо: карты `0xA8xxxxxx` у двух
ядер разные (§4.3 аппаратного документа). База выведена из совпадения размаха, а не
прочитана на живом мониторе; проверяется чтением `0xA8076000` с консоли Sub.

**Что внутри.** 1 555 ненулевых слов из 2 554, шестью участками. Начало — таблица
ловушек SPARC/LEON: 17 пар «указатель на строку + номер ловушки», причём строки лежат в
самом образе Sub около `0xA00AD568`:

```
A00AD568 01  Power-on reset                 A00AD6F0 20  Hardware breakpoint match
A00AD578 02  Error during instruction fetch A00AD710 28  Register file EDAC error(LEON-FT only)
A00AD598 03  UNIMP or other un-implemented… A00AD738 24  Co-processor exception
A00AD5C8 04  Execution of privileged instr… A00AD750 2A  CP instruction while Co-processor disabled
A00AD600 05  FP instruction while FPU disa… A00AD780 2B  Divide by zero
A00AD628 06  SAVE into invalid window       A00AD790 00  Write buffer error
A00AD648 07  RESTORE into invalid window
A00AD668 08  Memory access to un-aligned address
A00AD690 09  FPU exception
A00AD6A0 0A  Access error during load or store instruction
A00AD6D0 0B  Tagged arithmetic overflow
```

Тексты дословно совпадают с примерами Gaisler для LEON — то есть это не MSI-код, а
стандартный обработчик ловушек, попавший в сборку вместе с рантаймом. Дальше идут
таблицы указателей на функции Sub (`A0079F90`, `A009A3D4`, `A006D2C0`…), таблицы
значений регистров скалера (`CF005400`, ряды `0x0400xxxx`) и мелкие массивы.

**Кто читает.** Только Sub, и не по абсолютному адресу: сплошной поиск пар `sethi`+`or`,
попадающих внутрь раздела, по образам Main, Sub и `id=0x0B` даёт **ноль** — секция
адресуется как данные, через базу. Из флеша раздел читается **дважды за сеанс**: при
загрузке и при пробуждении по кнопке, по 0,85 мс каждый раз (`docs/spi-boot-trace.md`);
дальше он живёт в SRAM.

Между версиями раздел заметно вырос — 5 288 байт в заводской FW.023 против 10 216 в
FW.034 (`docs/flash-u4002.md`), что для `.data` естественно.
