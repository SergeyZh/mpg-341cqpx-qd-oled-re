# Вендорские команды DDC/CI

Обработчик DDC/CI — `0x00027868` (`DDCCi_SetVCP_Feature`), вендорские опкоды разбирает
`0x0006E9C0`. Опкод VCP лежит в `param[4]`, полезная нагрузка — в `param[5..7]`;
для опкода `0xE1` в `param[5]` идёт подкоманда, дальше — её аргументы.

Все адреса — Leon2 Main, база 0; файловое смещение = адрес + `0x108000`.

Ни один из этих кодов не объявлен в строке возможностей MCCS и ни один не защищён
проверкой заводского режима. На DisplayPort канал DDC/CI — это I2C поверх AUX, то есть
всё перечисленное доступно хосту и всему, что стоит между хостом и монитором.

## Что разобрано

| Команда | Что делает | Где |
|---|---|---|
| `0xE1`, `0xA1` | при взведённом бите 14 слова `0xA802BD74` — вечный цикл (заводская проверка сторожевого таймера) | `docs/burn-in-mode.md` |
| `0xE1`, `0xA2`, `param[6]=0` | `0xA802BD6C = param[7]` — включение заводского прогона, запись FE2P немедленно | `docs/burn-in-mode.md` |
| `0xE1`, `0xA3`, `param[6]=0`, `param[7]=0` | **обнуляет общую наработку панели** (`SysParam 0x06…0x09`, U4003 `0x478…0x47E` в RAM), ставит бит 3 `A8029AE7`; путь до записи в U4003 не пройден. Разобрано на FW.034 (`0x0006E984` → `0x0006F3EC`), кадр не проверялся. **Не посылать**: данные экземпляра | panel-protect-fw034.md (не опубликовано) |
| `0xE1`, `0xA7`, `param[6]=3` | контур ACE (динамическая яркость) вкл/выкл | ниже |
| `0xE1`, `0xA7`, `param[6]=6` | заставка при включении вкл/выкл | `docs/logo.md` |
| `0xE1`, `0xA7`, `param[6]=0x13` | подмена середины кривой яркости — похоже на калибровку | ниже |
| `0xE7` | `FUN_000E202C(0, param[5], param[6], param[7])` — залить экран произвольным цветом | `docs/burn-in-mode.md` |
| `0x14`, `param[7]=0` | текущие RGB-усиления (`0x16` и соседние) заносятся в пресет по `param[5]` (5/6/8 = Warm50/Normal65/Cool93) и **сразу пишутся в `U4003:0x0440`** — заводская калибровка белой точки. Разобрано на FW.034 (обработчик `0x0006E6C8`, запись `0x0006EE98`); раскладка кадра не проверена | [eeprom-u4003.md](eeprom-u4003.md#когда-штатная-прошивка-пишет-0x0440-в-eeprom) |
| **`0xFB`** | **вход в ISP: `ServicePort_EnableIsp`, дальше вечный цикл. Только в FW.037** | ниже |

Разбор подкоманды `0xA7` начинается на `0x0006ECA0`: сначала проверяется `param[6] == 6`,
затем управление уходит на `0x0006F9F8`, где разбираются `param[6] == 3` и
`param[6] == 0x13`. Прочие значения `param[6]` не обрабатываются.

Три поля, которые правит `0xA7`, лежат в одном блоке пользовательских настроек длиной
`0x1F8` байт, начинающемся с `0xA802BD74`; блок целиком сбрасывается в FE2P по смещению 0.

## `0xFB` — вход в ISP одной командой DDC/CI. Разобрано 2026-08-28

Самая тяжёлая по последствиям команда из всех здесь описанных, и она **появилась только
в FW.037**.

### Условие срабатывания

`A002FD00` (`ServicePort_EnableIsp`, `docs/scaler-service-runtime.md`) вызывается из
Leon2 Main **ровно из одного места** — `CODE:00028DE0`, внутри `DDCCi_SetVCP_Feature`.
Цепочка условий целиком:

1. пакет DDC/CI, принятый аппаратным I²C-слейвом (тип 4 диспетчера `FUN_000D0C1C`) и
   прошедший гейт контрольной суммы — XOR по `(buf[1]&0x7f)+3` байтам обязан дать `0x6E`
   (`docs/usb-isp.md`);
2. **команда DDC/CI = `0x03`** (Set VCP Feature) — проверка на `0x00027904`–`0x00027924`;
   `0x01`, `0x07` и всё, что больше `0x07`, уходят другими ветками;
3. **код VCP = `0xFB`** — таблица переходов Main `0x000297D8`, индекс равен опкоду,
   вход `[0xFB]` ведёт на `0x00028D9C`;
4. **значение не проверяется вообще** — тело case не читает `param[5..7]`;
5. проверки заводского режима нет, как и у остальных команд здесь.

То есть достаточно `51 84 03 FB xx xx <cs>` на адрес `0x6E`.

### Что делает

`v = FUN_000E0274(0)` — идентификатор текущего источника окна 0. Дальше два подпути,
оба заканчиваются вызовом и безусловным вечным циклом `call A002CCDC` / `ba,a`; возврата
нет, выход только передёргиванием питания.

- **`v ≤ 0x0A` либо `v > 0x0F`** — канал берётся по активному входу
  (`FUN_000E7104(v)`: код порта `0x61`/`0x71`/`0x81` → номер канала из структуры порта в
  DRAM) и вызывается `ServicePort_EnableIsp(канал)`.
- **`0x0B ≤ v ≤ 0x0F`** — смотрится код порта `FUN_000E035C(v)`: `0x71` → 0, `0x81` → 1,
  **любой другой → `0xFF`, и в ISP не идём вовсе**, сразу в цикл. Для `0x71`/`0x81`
  снимается мультиплексор текущего канала (`1 << канал` через портал `0x000D01F4`),
  пауза 5 тиков, `FUN_000A42F8(тип, 3, 1, 0)`, затем **`ServicePort_EnableIsp(3)` —
  канал 3 жёстко зашит** (банк 1, биты 6/7).

Что означают пороги `0x0A` и `0x0F` — не установлено.

### Различие версий: единственное во всей таблице

Таблицы переходов обеих версий сравнены целиком:

| | FW.037 | FW.034 |
|---|---|---|
| база таблицы | Main `0x000297D8` | Main `0x000294E0` |
| default | `0x0002836C` | `0x00028350` |
| опкодов с обработчиком | **35** | **34** |
| `table[0xFB]` | `0x00028D9C` — реальный case | `0x00028350` — **default** |

Остальные 34 опкода совпадают. **Вход в ISP по DDC/CI добавлен в FW.037**, что сходится
с тем, что `A002FD00` — новый экспорт этой версии. На мониторе стоит FW.034, где `0xFB`
не делает ничего.

### Следствия

- **Отрицательный результат `docs/ddc-external-probe.md` привязан к версии.** Опыты
  «сервисной плоскости на видеоразъёме нет» ставились на FW.034, то есть на прошивке,
  в которой этого входа не существует. Для FW.037 они не воспроизводились.
- **Задачу пустого флеша это не решает**: `DDCCi_SetVCP_Feature` исполняет работающая
  прошивка, ограничение то же, что у кадра `580040:` (`docs/factory-programming.md`).
- Но как *вход в ISP* это проще всего известного: одна стандартная команда DDC/CI
  вместо цепочки через мост `U7005`.

**Не проверено живьём.** Нужен монитор с FW.037, то есть обновление, а оно перепишет
слот. Отдельно стоит посмотреть, объявлен ли `0xFB` в строке возможностей MCCS — по
прежнему разбору вендорские коды там не объявлены.

## Чтение: что вообще можно получить обратно

Ответы формируются в двух местах, и это весь набор. Признак «ответ готов» ставит
`FUN_00029C24` (`DAT_A8029AFC = 0x50`); у неё **10 точек вызова**, и других
отправителей нет:

| Где | Сколько | Что это |
|---|---|---|
| `FUN_0006E174` | 5 + через `FUN_0006DFF0` | обработчик **GET**: штатные VCP и вендорские строки |
| `FUN_0006E9C0` | 4 | ответы на вендорские **SET** — эхо и контрольные суммы запроса |

Формат ответа: `6E | 0x80\|len | 02 | …`. Штатный ответ VCP собирает
`FUN_0006DFF0`, и вызывают её только из `FUN_0006E174`.

Читается вот это:

| Запрос | Что возвращает | Откуда берётся |
|---|---|---|
| VCP `0x10` | яркость | `0xA802BD7D` |
| VCP `0x12` | контраст | `0xA802BD7E` |
| VCP `0x16`, `0x1A`, `0x6C`, `0x70`, `0xCC`, `0xE2` | штатные MCCS | поля в RAM |
| VCP `0xE9` | `MPG341CX OLED` | `0x00151AD0`, константа |
| VCP `0xEF`, подкоманда `0x13` | серийный номер | FE2P, смещение `0x2E0` |
| `0xE1`, `0xA7`, `param[6]=7`, `param[7]=0` | `SDC QMC340CA01_D01` | `0x00151AE9`, константа |
| `0xE1`, `0xE6`, `param[6]=6`, `param[7]=0` | `FW.037` | `0x00151AE1`, константа |
| `0xE1`, `0xA5`, `param[6]=3`, `param[7]=0` | фиксированный ответ `FE 02 B0` | константы в коде |

Строки в образе длиной вперёд: `0D "MPG341CX OLED"`, `06 "FW.037"`,
`12 "SDC QMC340CA01_D01"` — лежат подряд с `0x00151AD0`.

### Ни `0xA802BF4C`, ни состояние заставки прочитать нельзя

Проверено по всем трём отправителям ответов:

- **`FUN_0006E174` (единственный GET) не обращается ни к `0xA802BD74`, ни к
  `0xA802BF4C` вообще** — ни одной ссылки, по `RefsTo` в Ghidra. Единственное
  соседнее поле, которое он читает, — `0xA802BD7D`, то есть пользовательская яркость
  под VCP `0x10`.
- В `FUN_0006E9C0` бит 12 слова `0xA802BD74` встречается только в двух записях
  (`0x0006FA88`, `0x0006FC04`), а `0xA802BF4C` — только в подкоманде `0x0E`, и там оно
  читается ради сохранения прежнего значения, а не ради ответа. В буфер ответа ни то,
  ни другое не попадает: все четыре ответа этой функции — эхо `param[6]`/`param[7]` и
  контрольные суммы запроса.
- Обходного пути через FE2P тоже нет: читающая FE2P `FUN_000E6F9C` вызывается всего из
  трёх мест — дважды из `FUN_0006FEE0` (накат умолчаний при старте) и один раз из
  `FUN_0006E174` с **жёстко заданными** аргументами (смещение `0x2E0`, 16 байт —
  серийник). Команды «прочитать произвольный адрес FE2P или RAM» в образе нет.

Практический вывод: **значение `0xA802BF4C` восстановить после перезаписи будет неоткуда,
кроме дампа FE2P** — то есть шага 9 плана. Это ещё один довод снять дамп до любых
экспериментов с подкомандой `0xA7`/`0x13`.

С заставкой проще: прочитать бит нельзя, но он ни на что, кроме заставки, не влияет,
так что его состояние видно на экране при включении.

Не проверялось: канал USB. Штатная утилита MSI требует USB и DisplayPort одновременно
(`docs/isp-update.md`), и не исключено, что часть состояния она читает не по DDC/CI.

## Безопасная запись `0xA802BF4C` — подкоманда `0x0E`

Помимо `0xA7`/`0x13` то же поле правит отдельная подкоманда `0x0E` (разбор на
`0x0006F478`), и устроена она аккуратнее:

```c
new = (param[7] << 8) | param[8];
old = 0xA802BF4C;
0xA802BF4C = new;
...
if (0xA802BF4C > 0x30C) 0xA802BF4C = 0x30C;   // потолок
if (0xA802BF4C < 0x7D)  0xA802BF4C = 0x7E;    // пол
FUN_00075600();                                // применить и показать
if (param[6] == 1) FE2P_write(0xA802BD74, 0, 0x1F8);   // зафиксировать
else               0xA802BF4C = old;                   // откатить
```

То есть `param[6] = 0` — это **предпросмотр**: значение применяется, его видно на экране,
и прежнее возвращается. Фиксирует только `param[6] = 1`. Значение зажимается в
`[0x7E, 0x30C]` — те же границы, что у кривой яркости.

Чего не проследил до конца: под каким именно VCP-опкодом идёт эта подкоманда. На
`0x0006F478` код проверяет только `param[5] == 0x0E`, а ветвление до этого места —
компилированный `switch` с переиспользованием кодов условия, и я его не разбирал.

## `param[6] = 3` — контур ACE

```asm
ldub  [%i0+7], %g1
cmp   %g1, 0
bne   -> param[7] != 0
; param[7] == 0:
ld    [%g1+0x11c], %o7     ; 0xA802BE90
sethi 0x200000, %o2        ; 0x80000000
andn  %o7, %o2, %o5        ; сбросить бит 31
st    %o5, [%g1+0x11c]
; общий хвост:
call  0xd911c              ; FUN_000D911C(0)
cmp   %l6, 0xc
bne   -> выход без применения
call  0x7592c              ; применить
```

| `param[7]` | Действие |
|---|---|
| `1` | установить бит 31 слова `0xA802BE90` (`0x0006FC34`) |
| `0` | сбросить бит 31 (`0x0006FBAC`) |
| иное | не писать ничего, но пройти по хвосту |

Бит 31 — это **включение контура ACE**. Цепочка прослеживается до конца:
`FUN_0007592C` читает бит 31 и передаёт его в `FUN_000E5428`, а та при значении 1
запускает `0x000C65A8` = `ACE_LumGainLoop`, иначе — `FUN_000C6B98`. Сам контур уже
разобран в `docs/panel-protect.md`: он измеряет гистограмму кадра из блока ACE
(Adaptive Contrast Enhancement), считает усиление и гонит его рампой в регистр панели
`0x05E` (`Lum Gain`). Если бит 31 сброшен, `FUN_0007592C` дополнительно вызывает
`FUN_00075600` — то есть возвращает штатную яркость.

Две особенности:

- **Применяется не всегда.** Между записью бита и вызовом `FUN_0007592C` стоит проверка
  `FUN_000D911C(0) == 12`. Эта функция возвращает старшие 4 бита первого слова массива
  дескрипторов видеотракта `0xA802CA10` (шаг `0x78`, четыре элемента). Что означает
  значение 12 — не установлено. Если условие не выполнено, бит записан, а контур не
  переключается до следующего применения из другого места.
- **В FE2P не пишется.** Ветка уходит на общий выход `0x0006FE10` (`ret; restore`) без
  вызова `FUN_000E7050`. Но поле лежит внутри блока `0x1F8`, и блок сбрасывается в FE2P
  в ветке `dc off` (`0x000224EC`), так что настройка всё равно переживает штатное
  выключение.

Этот же бит правят `UserSetGameMode` и `UserSetProMode` — то есть режимы изображения
переключают ACE сами. Какому пункту меню это соответствует — не установлено: обе функции
передают в `FUN_000E5428` двухбитное поле, а не бит 31.

## `param[6] = 0x13` — середина кривой яркости

```asm
ldub  [%i0+7], %o5
cmp   %o5, 1
be    -> 0x6fc44           ; param[7] == 1
; param[7] != 1:
ld    [%l0+0x1d4], %o7     ; 0xA802BF48
sethi 0x10, %o2            ; 0x4000
andn  %o7, %o2, %o3        ; сбросить бит 14
mov   0x46, %g1            ; 70
mov   0x226, %l1           ; 550
st    %o3, [%l0+0x1d4]
stb   %g1, [%l0+9]         ; 0xA802BD7D = 70   — яркость
call  0x75600              ; применить яркость
sth   %l1, [%l0+0x1d8]     ; 0xA802BF4C = 550
```

| `param[7]` | Действие |
|---|---|
| `1` | установить бит 14 в `0xA802BF48`; восстановить яркость `0xA802BD7D` из сохранённого байта `0xA802BF4B` |
| иное | сбросить бит 14; принудительно выставить яркость 70 и записать 550 в `0xA802BF4C` |

Обе ветки затем вызывают `FUN_00075600` (применение яркости), `FUN_00070D1C` и
**пишут блок `0x1F8` в FE2P немедленно** (`0x0006FC7C` и `0x0006F2DC`).

### Что делает бит 14

`FUN_00075600` переводит пользовательскую яркость `0xA802BD7D` (0…100) в код яркости
панели — те же единицы, что и в контуре ACE: от `0x7E` (126) до `0x3FF` (1023), формула
пересчёта совпадает с описанной в `docs/panel-protect.md`. Кривая ломаная, с изломом на
яркости 70:

| Режим | яркость 0 | яркость 70 | яркость 100 |
|---|---|---|---|
| обычный | 126 | 879 | 1023 |
| `0xA802BE1C & 0x400` и `0xA802BEF5 == 7` | 126 | **580** (`0x244`) | 780 (`0x30C`) |
| то же плюс бит 14 `0xA802BF48` | 126 | **`0xA802BF4C`** | 780 |

То есть бит 14 подменяет **только середину** кривой — концы остаются 126 и 780.
Это ровно то, чем выглядит калибровочная ручка, а не пользовательская настройка, и
косвенное подтверждение тому есть: `FUN_00079088`, сбрасывающая настройки к умолчаниям,
специально **сохраняет** `0xA802BF4B` и `0xA802BF4C` и переустанавливает бит 14 по своему
аргументу — единственные поля блока, которые сброс не трогает.

### Чего установить не удалось

- Что за режим включают `0xA802BE1C & 0x400` и `0xA802BEF5 == 7`, без которого подмена
  вообще не работает. `0xA802BEF5` — перечисление 0…7, значения раздаёт `FUN_0006488C`.
- Почему ветка «выключить» пишет в `0xA802BF4C` именно 550, хотя штатная середина 580,
  и почему она же принудительно ставит яркость 70. У `0xA802BF4C` 48 обращений по всему
  образу, то есть значение используется не только в этой кривой.
### Осторожно

`0xA802BF4B` и `0xA802BF4C` — единственные поля блока настроек, которые переживают сброс
к умолчаниям. Похоже, туда пишут на заводе. Команда `0xA7`/`0x13` затирает их и
немедленно фиксирует в FE2P, а сброс настроек прежнее значение **не вернёт**. Прочитать
его по DDC/CI нельзя (см. выше), то есть восстанавливать будет неоткуда, кроме дампа
FE2P. До снятия дампа (шаг 9 плана) эту подкоманду трогать не стоит; если менять
значение всё-таки нужно, есть подкоманда `0x0E` с предпросмотром без фиксации.

Отдельно: соседняя подкоманда `0xA2` с `param[6]=0` включает заводской прогон и тоже
пишет FE2P немедленно (`docs/burn-in-mode.md`). Ошибка в байте попадает в неё.
