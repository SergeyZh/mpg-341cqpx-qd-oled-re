# LED-индикатор монитора

**Управление найдено и проверено на железе 2026-09-13: GPIO 7.2 — белый канал,
GPIO 7.3 — жёлтый, оба активны нулём.** Регистр данных — `XDATA:F012`,
со стороны Leon2 — `0xCF03C048`; направление — `F013` / `0xCF03C04C`.
Это корпусный индикатор MSI MPG 341CQPX, а не подсветка панели.

Назначение следует из путей ON, sleep, Power Off, настройки разрешения LED и мигания
при компенсации. Обёртки проверены в Ghidra в FW.034 и FW.037. Независимая проба
через ISP дала все три цвета; владелец подтвердил совпадение и возврат к белому.

## Как управлять

Меняются только биты `0x0C` регистра `F012`. Единица в `DIR` означает вход;
для этих двух линий `F013 & 0x0C` должен быть нулевым.

| Индикатор | GPIO 7.2 | GPIO 7.3 | `F012 & 0x0C` |
|---|---:|---:|---:|
| белый | 0 | 1 | `08` |
| жёлтый | 1 | 0 | `04` |
| погашен | 1 | 1 | `0C` |
| оба канала, смешанный бело-жёлтый свет | 0 | 0 | `00` |

Комбинация `00` штатным трём состояниям не нужна. По просьбе владельца она
дополнительно выставлена через ISP на три секунды: `F012=C9 → C1 → C9`,
`F013=C2` сохранился. Владелец подтвердил смесь белого и жёлтого:
«Не чисто белый, но и не желтый». Это визуальное наблюдение, без измерения
спектра или цветовой температуры.
Журнал — `isp-both.txt` (не опубликовано).
Сохранять соседние выходы обязательно: в этом банке находятся другие цепи платы.
Штатный GPIO HAL дополнительно поднимает latch входных битов, поскольку чтение
`DATA` показывает уровни на выводах, а не скрытый выходной latch:

```c
uint8_t data = read_reg(0xF012);
uint8_t dir  = read_reg(0xF013);
write_reg(0xF012, ((data | dir) & 0xF3) | led_bits);
```

В `bootloader-libre` уже достаточно существующего GPIO API:

```c
gpio_write(GPIO_PIN(7u, 2u), GPIO_HIGH);
gpio_write(GPIO_PIN(7u, 3u), GPIO_HIGH); /* оба погашены */
gpio_write(GPIO_PIN(7u, 2u), GPIO_LOW);  /* белый */
```

При холодной настройке сначала задать обоим высокий уровень, затем разрешить выходы
через `gpio_configure(..., GPIO_OUTPUT_HIGH)`. Это рецепт для собственной прошивки;
новая LED-логика в загрузчик пока не добавлялась.

### Проверенная проба через ISP

[`tools/led_indicator.py`](../tools/led_indicator.py) работает через уже подготовленный
ISP и по умолчанию только читает. С `--sequence` показывает заданные цвета и после
**каждого** возвращает исходные LED-биты. Проверяет `D511=17`, выходное направление,
read-back и неизменность соседних выходов. При исключении также пытается восстановить
LED. `DIR`, flash и U4003 не пишет; скалер оставляет в ISP.

```sh
# Один раз войти из работающей MSI; ожидается JEDEC c8 40 19:
.venv/bin/python tools/isp_read.py --jedec
# Если уже запущен recovery загрузчика — добавить --bootloader.

.venv/bin/python tools/led_indicator.py
.venv/bin/python tools/led_indicator.py --sequence off white yellow --seconds 3
.venv/bin/python tools/led_indicator.py --sequence both --seconds 3
```

Повторный вход через `--jedec` для каждой пробы не требуется.
Для штатной работы после опытов — аппаратный reset без удержания джойстика вправо.

## Доказательство по прошивке

### Четыре непосредственных обёртки

| Действие | Main FW.037 | Main FW.034 | Вызов GPIO HAL |
|---|---:|---:|---|
| белый включить | `000C0D20` | `000C0A28` | `(7, 04, 00)` |
| белый выключить | `000C0D88` | `000C0A90` | `(7, 04, FF)` |
| жёлтый включить | `000C0DF0` | `000C0AF8` | `(7, 08, 00)` |
| жёлтый выключить | `000C0E58` | `000C0B60` | `(7, 08, FF)` |

HAL находится по `A002C508` в FW.037, `A002C6FC` в FW.034.
Младший бит третьего аргумента: `0` снимает маску, `1` устанавливает.
В FW.037 таблица LOW `A002C814`, элемент 7, ведёт в `A002C618`, затем к `ANDN`
и записи `CF03C048`; таблица HIGH `A002C7CC`, элемент 7, ведёт в `A002C534`,
к `OR` и записи того же регистра. Полярность проверена по листингу и обеим таблицам.

SPARC delay slot `call A002C508; restore` передаёт подготовленные `i0/i1/i2`
как `o0/o1/o2`. Это прямой tail-call GPIO HAL, без mailbox и без STBC-команды.

### Три состояния сходятся на одной паре GPIO

| Путь FW.037 | Сайты вызовов | Итог |
|---|---|---|
| ON, `APPSTATE_PWR_ON`, в том числе case 2 | `21DC0 → C0E58`, `21DC8 → C0D20` | жёлтый выключить, белый включить |
| sleep, `APPSTATE_PWR_ON(3)` | `22280 → C0D88`, `22288 → C0DF0` | белый выключить, жёлтый включить |
| Power Off, `APPSetPowerOff` | `20550 → C0D88`, `20558 → C0E58`; альтернативно `20428/20430` | оба выключить |

Затем sleep доходит до `SYSAPI_PowerSaving` (`E1084`) и mailbox `0x16`,
а Power Off — через runtime до mailbox `0x17`. STBC-обработчики `2708`/`274A`
останавливают Leon2 и сохраняют тип ожидания в `A7CB`. **Цвет уже выставлен Main.**
Остановка CPU не требует менять выходной latch GPIO: для постоянного цвета
постоянно исполняющийся LED-драйвер не нужен. Прежний поиск записи цвета внутри
STBC-обработчиков начинался слишком поздно. ISP-проба независимо показала, что цвет
задаётся и удерживается при остановленном Main.

### Поле `0x12` — разрешение LED, не состояние панели

Все четыре обёртки разрешают запись, если getter `E1A6C(0x12)` возвращает 1
**либо** `C3AA4()` возвращает 1 или 2 — активные OFF/EL Sensing.

Первый getter читает **бит 21 слова `A802CC98`**. Setter `E1C34(0x12, value)`
меняет тот же бит. Смысл независимо раскрывает `77D4C`: временно разрешает управление,
выбирает белый или оба погашены по аргументу и сохраняет выбранное разрешение.
Эту функцию вызывают обработчик пользовательской настройки `37478` и UART setter
`6960C`; они работают с битом 14 `A802BF64`. Точное имя пункта OSD и номер
HID-команды здесь не установлены. Эти высокоуровневые setter могут сохранять настройки
и в ISP-пробе не использовались.

`C3AA4` действительно читает состояние панели (`A802C376`), но оно лишь обходит
пользовательский запрет индикации во время компенсации. При запрете LED Power Off
временно ставит разрешение 1, гасит оба канала и возвращает 0 (`20420…20440`).
Нельзя переносить назначение условия на сами выходы.

### Независимая проверка по миганию

В автомате `C3CE4` при флаге `A802C389=1` OFF Sensing переключает
`C0D20`/`C0D88`, а EL Sensing — `C0DF0`/`C0E58`, через фазовый байт `A802C37E`.
Ветви проверяют интервал более 1000 мс: примерно секунда на фазу, полный период
около двух секунд. Сайты переключения: `C49E4/C4A14` и `C4A04/C4A24`.
Это индикация компенсации, а не включение питания панели каждую секунду.
Штатные постоянные цвета задаются дискретными уровнями; осциллограмма выходного
каскада и переходные процессы отдельно не снимались.

## Живая проверка 2026-09-13

До ISP консоль FW.034 прочитала `CF03C048=C9`, `CF03C04C=C2`: белый канал
в нуле, жёлтый в единице, оба выходы. Из-за нестабильного Main при припаянных к
флешу проводах активную проверку по указанию владельца перенесли в полный ISP.
Вход `isp_read.py --jedec` вернул `c8 40 19`.

Журнал: `isp-sequence.txt` (не опубликовано),
подтверждение наблюдений —
`observations.md` (не опубликовано).

| Команда | Записано F012 | Прочитано F012 | Наблюдение владельца |
|---|---:|---:|---|
| исходное | — | `C9` | белый |
| погасить на 3 с | `CF` | `CD` | погас |
| белый на 3 с | `CB` | `C9` | белый |
| жёлтый на 3 с | `C7` | `C5` | жёлтый |
| окончательное восстановление | `CB` | `C9` | снова белый |

После каждой пробы был возврат исходного цвета на секунду. `F013=C2` сохранился,
соседние выходы не изменились. Разница write/read `02` относится к входу `7.1`:
HAL освобождает его latch, чтение возвращает внешний ноль. Это не ошибка записи.
Обычный boot/recovery повторно после этой пробы не проверялся; загрузчик и flash
опытом не изменялись, скалер оставлен в ISP согласно выбранному способу исследования.

## Электрическая сторона и ошибка прежнего разбора

Мультиметр ранее локализовал LED на `CN4002`:

| Pin | погашен | белый | жёлтый | Интерпретация |
|---:|---:|---:|---:|---|
| 6 | 0 В | 1,5 В | 1,9 В | вероятный жёлтый анод |
| 7 | 0 В | 2,75 В | 0 В | вероятный белый анод |
| 8 | 0 В | 0 В | 0 В | вероятный общий катод, 1,2 Ом до GND |

Первичный замер —
`2026-09-13-multimeter.txt` (не опубликовано),
распиновка — [`hardware-boards.md`](hardware-boards.md#cn4002-джойстик-кнопки-и-двухцветный-led--измерено-2026-09-13).
Активный ноль у скалера и положительное анодное напряжение согласуются с
**инвертирующим внешним каскадом**. Его транзисторы, резисторы, BGA-шары скалера
и причина остаточных 1,5 В ещё не прослежены. Управлению это уже не мешает.

Прежний разбор ошибочно назвал `7.2/7.3` «линиями панели» и исключил их из опыта.
Причина — контекст sensing и неверное толкование поля `0x12`. Затем он отбросил
строку `10min led and offrs start`, потому что рядом меняется якобы «уже установленная
линия панели 7.3». Это круговое обоснование, а не независимая проверка. Теперь видно:
`C0E58` там гасит жёлтый канал перед следующей стадией компенсации. Строка находится
в Leon2 Main, не в STBC Main.

Остальные прежние следы не являются найденным управлением LED:

- `Set Indicator` (`D0438`, mailbox `18/19/1A`) — общий GPIO-механизм STBC;
  прежняя проверка Ghidra не нашла отправителя в этой сборке. Название само по себе
  не устанавливает назначение; корпусный LED управляется другим путём.
- STBC `CMD_SET_P14/P15` (`1D/1E`, обработчики `2801/2828`) меняют SFR P1.4/P1.5,
  а не scaler GPIO 7.2/7.3. Прежний листинг не показал их использования в штатных
  переходах. Проба этих выводов для поиска LED больше не нужна.
- PWM-похожая таблица U7005 `DA20` не получила ссылок в прежнем анализе;
  сам U7005 обесточивается в sleep. Доказанный LED-путь его не использует.

## Воспроизведение статического разбора

Адреса Main переводятся в файл прибавлением `0x108000`. Имена сохранены в
[`leon2main_led_fw037.csv`](../names/leon2main_led_fw037.csv) и
[`leon2main_led_fw034.csv`](../names/leon2main_led_fw034.csv).
Через `DumpAsm.java`/`RefsTo.java` проверены:

- Main FW.037 `C0D20…C0EC0` и ссылки на четыре входа; Main FW.034 `C0A28…C0BC8`;
- runtime FW.037 `A002C508…A002C85C`, обе таблицы для банка 7;
- Main FW.037 `20330…20730`, `21D10…22400`, `77D4C…77DB8`,
  `E1A6C…E1F34`, `C3AA4`, ветви мигания `C49D4…C4A30`.

Листинги `out/led-*.asm` регенерируемы; выводы и имена не оставлены только в `out/`.
