# Эквализация и обучение линка: HDMI 2.0, HDMI 2.1 FRL, DisplayPort

Продолжение `docs/video-input.md` вглубь: что именно происходит между «в разъём воткнули
кабель» и «появились тайминги». Это самая объёмная часть образа Leon2 Sub.

Адреса — образ Leon2 Sub, база `0xA0060000`, файловое смещение = адрес − `0xA0010000`.

## Как адресуются регистры PHY

Числа вида `0x1178`, `0x1EA0`, `0x2578`, которыми прошивка сыплет в отладочных
сообщениях, — **не адреса и не смещения в окне `0xCF000000`**, описанном в
`docs/video-input.md`. У приёмников свой, страничный доступ (`0xA0092390` — чтение,
`0xA009233C` — запись):

```c
страница = (номер >> 8) & 0xFF;      // 0x11, 0x1E, 0x21, 0x31 …
смещение = номер & 0xFF;
*(u32*)(0xCF03D004 + порт*4) = страница;                  // выбор страницы
значение = *(u32*)(0xCE008100 + порт*0x100 + смещение);   // данные
*(u32*)(0xCF03D004 + порт*4) = прежняя_страница;          // восстановление
```

То есть окно данных — `0xCE008100`, по `0x100` байт на порт, а старший байт номера
регистра выбирает страницу через регистр `0xCF03D004 + порт·4`. Страница всегда
восстанавливается после доступа, то есть обращения вложены безопасно. Из этого же
следует смысл нумерации: `0x1178` и `0x2178` — один и тот же регистр `0x78` на разных
страницах, `0x11` для HDMI 2.0 и `0x21` для HDMI 2.1; шаг `0x04` между страницами
соответствует переходу к следующему каналу (`0x11`, `0x15`, `0x19` — CH0, CH1, CH2).

## Три независимых механизма

| Тракт | Автомат | Состояний | Что подбирает |
|---|---|---|---|
| HDMI 2.0 / TMDS | `DRV_HDMI_EQScan_FSM_*` | 17 | аналоговую эквализацию приёмника |
| HDMI 2.1 / FRL | `DRV_HDMI21_RXDetect_FSM_LTS_*` | 10 | скорость линка и коррекцию передатчика |
| DisplayPort | `0xA0073E1C` и соседи | — | скорость и число линий |

Разница принципиальная. В HDMI 2.0 **обратной связи с источником нет вообще**: приёмник
молча крутит свои аналоговые настройки, пока не перестанут сыпаться ошибки. В HDMI 2.1 и
в DP есть протокол обучения, и приёмник может попросить источник сменить скорость или
предыскажение.

## Как автоматы вызываются

Оба HDMI-автомата висят на таймерах, а не в главном цикле. Записи таймера — структура из
трёх слов `{остаток, период, обработчик}`, регистрация — `0xA0067BBC`:

| Структура | Обработчик | Что гоняет |
|---|---|---|
| `0xA8078BF4` | `DRV_HDMI_EQDetect_Timer` (`0xA0089F2C`) | → `0xA0080078`, диспетчер EQ-скана |
| `0xA80793B0` | `0xA009E65C` | диспетчер FRL-обучения (`DRV_HDMI_Init_Timer(0x14)`) |
| `0xA80793A4` | `0xA00A0B44` | второй обработчик того же семейства (`тип 1`) |

Период у всех берётся из байта `0xA80792E8`, значение которого статически не видно — оно
выставляется при инициализации.

Оба диспетчера устроены одинаково: берут номер состояния из своей переменной, вызывают
обработчик по таблице указателей и **повторяют вызов, пока обработчик возвращает
не ноль**. То есть за один тик автомат может пройти несколько состояний подряд; ноль
означает «на сегодня всё, ждём следующего тика».

```c
// EQ-скан, 0xA0080078
state = *(int*)(0xA807BF3C + port*0xC);
do { ret = table_0xA00AE040[state](port); } while (ret != 0);
if (state == 16) { /* FSM_EQSCAN_DONE */ }

// FRL, 0xA009E65C — для обоих портов
for (port = 0; port < 2; port++) {
    state = *(int*)(0xA807C790 + port*4);
    do { ret = table_0xA00B1E20[state](port); } while (ret != 0);
}
```

Таблицы состояний лежат в образе и дают полный список состояний в правильном порядке:
`0xA00AE040` (17 записей, файл `0x09E040`) и `0xA00B1E20` (10 записей, файл `0x0A1E20`).

## HDMI 2.0: EQ-скан

### Что вообще подбирается

У приёмника HDMI три канала данных (CH0…CH2), и у каждого своя аналоговая цепь. В ней
три настройки, и все три прошивка называет своими именами в отладочных строках:

- **RVGA** — усиление входного каскада. Значений всего три: таблица `HDMI_RVGA_TABLE`
  по адресу `0xA00AE0E8` = `{0x03, 0x09, 0x0F}`.
- **RCT** — сопротивление в цепи эквалайзера, 4 бита.
- **CCT** (в части сообщений `CFT`) — ёмкость там же, 13 бит.

RCT и CCT живут в одном регистре: для HDMI 2.0 это `0x1178` (CH0), `0x1578` (CH1),
`0x1978` (CH2) — биты `[23:8]` это CCT, биты `[3:0]` — RCT. Для HDMI 2.1 те же роли у
`0x2178`, `0x2578`, `0x2978`, `0x3178` (четыре канала). RVGA пишется в `0x1128`/`0x1528`/
`0x1928`, биты `[23:20]`.

### Таблица пар R/C

Перебор идёт не по всем комбинациям, а по готовому списку из **24 записей** по адресу
`0xA00AE084` (файл `0x09E084`), запись 4 байта: `{u8 RCT, u8 —, u16 CCT}`, признак конца —
нулевая запись:

| # | RCT | CCT | | # | RCT | CCT |
|---|---|---|---|---|---|---|
| 0 | `0x0B` | `0x1FFF` | | 12 | `0x02` | `0x00FF` |
| 1 | `0x06` | `0x1FFF` | | 13 | `0x03` | `0x00FF` |
| 2 | `0x02` | `0x1FFF` | | 14 | `0x01` | `0x00FF` |
| 3 | `0x03` | `0x1FFF` | | 15 | `0x08` | `0x00FF` |
| 4 | `0x07` | `0x0001` | | 16 | `0x04` | `0x00FF` |
| 5 | `0x06` | `0x0001` | | 17 | `0x0E` | `0x00FF` |
| 6 | `0x01` | `0x1FFF` | | 18 | `0x05` | `0x0001` |
| 7 | `0x08` | `0x1FFF` | | 19 | `0x03` | `0x0001` |
| 8 | `0x04` | `0x1FFF` | | 20 | `0x0B` | `0x000F` |
| 9 | `0x0E` | `0x1FFF` | | 21 | `0x08` | `0x000F` |
| 10 | `0x0B` | `0x00FF` | | 22 | `0x06` | `0x000F` |
| 11 | `0x06` | `0x00FF` | | 23 | `0x03` | `0x000F` |

Порядок не монотонный: сначала идут все варианты с `CCT = 0x1FFF` (все ёмкости включены,
максимальный подъём АЧХ), потом `0x00FF`, потом `0x000F` — то есть **список отсортирован
от «длинного кабеля» к «короткому»**, и первое же попадание обычно и есть ответ.
Число 24 зашито в коде отдельной константой (`< 0x18`), поэтому таблицу нельзя удлинить,
не правя код.

### Метрика: счётчик ошибок SCDC

Качество настройки прошивка меряет **счётчиком ошибок символов (CED)**, который HDMI
определяет в SCDC. Читается он в состоянии `PHY_ChkError` из регистров `0x1EA0`/`0x1EA4`,
статус — из `0x1E94`/`0x1E98`:

```c
если (статус & 0x20) == 0 и значение == 0x8000 -> канал чистый
иначе                                              ошибок = значение & 0x7FFF
```

`0x8000` — бит достоверности счётчика; «достоверно и ноль» и означает «ошибок нет».
Перед измерением автомат выжидает **шесть тиков** (счётчик в контексте порта), чтобы
счётчик успел набраться.

### Семнадцать состояний

| № | Имя | Что делает |
|---|---|---|
| 0 | `PHY_Init` | сброс, определение скремблирования и bit-ratio, → 1 |
| 1 | `PHY_PLL` | выбор диапазона PLL по частоте; вне диапазона → 0 |
| 2 | `PHY_DPHY` | настройка цифровой части; **пиксельная частота выше 600 МГц отвергается** как `out clk range`, → 3 |
| 3 | `PHY_PICDR` | восстановление тактовой (`Set ICDR Clock`), → 4 |
| 4 | `PHY_EQ` | развилка: ручная эквализация (MEQ) или автоматическая (AEQ), → 10 |
| 5 | `BA_Turning` | подбор R/C по «лучшему значению» для каждого канала |
| 6 | `PreRVGA` | перебор RVGA: для каждого из трёх значений считается длина непрерывного участка настроек с ошибкой < `0x10` |
| 7 | `PreAEQ` | перебор кандидатов R/C поверх выбранного RVGA, → 6 или 12 |
| 8 | `RunAEQ` | применение найденной пары, → 11 (AEQ) или 15 (MEQ) |
| 9 | `R_Turning` | доводка R, → 11 |
| 10 | `PreChkError` | предварительная проверка, → 0 |
| 11 | `PHY_ChkError` | измерение SCDC по трём каналам; → 16 (успех), 13, 4 или 0 |
| 12 | `R_ChkError` | то же для фазы подбора R, → 7 |
| 13 | `Search_Process` | выбор лучшего RVGA по минимуму ошибок, → 11, 14 или 16 |
| 14 | `Search_EQTable` | шаг по таблице из 24 пар R/C; таблица кончилась → 0 |
| 15 | `Check_MEQ_Done` | завершение ручного режима, → 0 или 16 |
| 16 | `Done` | `finish FSM_EQSCAN_DONE`, печать итоговых RVGA по каналам |

Общая логика: **сначала грубо (RVGA), потом точно (R/C), потом проверка, и при неудаче —
следующая запись таблицы**. Если таблица кончилась, всё начинается с `PHY_Init`; если
подряд не вышло больше десяти раз, срабатывает отдельная ветка сброса (счётчик
`0xA8078BB0`).

Отдельная ветка — «TMDS Skew Fail»: даже при чистом SCDC проверяется перекос между
каналами, и при неудаче автомат уходит в `PHY_Init`, увеличив счётчик повторов.

### MEQ и AEQ

Флаг в байте `0xA807BF44 + порт·0xC` переключает две стратегии, и он же меняет границы
всех переборов: в AEQ-режиме перебираются 13 значений, в MEQ — 9; RVGA-индекс в AEQ
считается от 0, в MEQ — от 3. В строках это `------- Force MEQ -------` и
`------- AEQ -------`, есть и функция с комментарием `This function is MEQ only`.
Чем режим выбирается — по коду не прослежено.

### Где состояние

| Адрес | Что |
|---|---|
| `0xA807BF3C + порт·0xC` | номер состояния (u32) |
| `0xA807BF43 + порт·0xC` | счётчик кругов проверки ошибок |
| `0xA807BF44 + порт·0xC` | флаг MEQ/AEQ |
| `0xA8079C68 + порт·0x898` | контекст EQ, 2200 байт на порт |

Внутри контекста: `+0x00` — индекс в таблице R/C по каналам (3 байта), `+0x09` — лучший
индекс RVGA по каналам, `+0x30` — счётчик кругов, `+0x31` — «канал уже чистый» по каналам,
`+0x38` — таблица набранных ошибок `score[RVGA][канал]`, `+0x80` — сетка измерений для
`PreRVGA`, `+0x884` — текущая пара R/C по каналам.

## HDMI 2.1: обучение FRL

Здесь работает протокол из спецификации HDMI 2.1, и имена состояний прошивки совпадают с
ним буквально: LTS:1 … LTS:P, LTS:L.

| № | Состояние | Смысл |
|---|---|---|
| 0 | `FSM_Init` | инициализация, → 1 |
| 1 | `LTS_1` | источник обнаружен, → 2 |
| 2 | `LTS_2` | чтение возможностей, → 3 или 7 |
| 3 | `LTS_3` | собственно обучение: запросы шаблонов и коррекции, → 4 или 7 |
| 4 | `LTS_Chk_Err` | разбор ошибок и смена скорости, → 0, 3, 6, 7 |
| 5 | `LTS_4` | → 7 |
| 6 | `LTS_P` | линк обучен, идёт видео; → 3, 8, 9 |
| 7 | `LTS_L` | Legacy: откат на TMDS, → 3 |
| 8 | `LTS_Chk_SCDC_Err` | проверка ошибок в рабочем режиме, → 3 |
| 9 | `LTS_Chk_Stable` | проверка стабильности, → 3 |

**Скорость.** Ставка хранится в поле `[27:24]` регистра `+0x90` блока порта и принимает
значения 1…6, которым в строках соответствуют `3G/3L`, `6G/3L`, `6G/4L`, `8G/4L`,
`10G/4L`, `12G/4L` — то есть от 3 до 12 Гбит/с на линию при трёх или четырёх линиях.
Значение 0 — ошибка (`FRL_Rate = 0 Error`), больше 6 — запрос понижения
(`FRL_Rate > 12G, request for lower FRL rate`). Блок порта адресуется через массив
указателей `0xA807CC60 + порт·0x34`.

**Диалог с источником** идёт через `FLT_update` (флаг `+0x80`) и `LTP_req` — по нибблу на
линию в регистрах `+0xA0` и `+0xA4`. Приёмник просит источник сменить предыскажение
(`TxFFE`), источник отвечает сменой шаблона. Таймаут на LTS_3 — 200 мс
(`LTS3 MAX timeout for 200ms go to LTS_L`), общий счётчик ожидания снятия `FLT_update` —
300 тиков, после чего либо `HPD Toggle`, либо возврат в `FSM_Init`.

**Проверки качества** здесь богаче, чем в HDMI 2.0: кроме SCDC используются CED по каждой
линии (`Jex: ch%d CED error > 4 in 1s`), счётчик ошибок Рида — Соломона RSED
(`RSED err>4 in 1s`) и отдельный скан фазы `DRV_HDMI21_IQ_Scan_byCED`. Порог в обоих
случаях — больше четырёх ошибок за секунду.

**Отладочный костыль:** `DRV_HDMI_DbgMenu(10, …, 1)` ставит флаг `0xA8079302` —
`LTP force pass`, «считать обучение успешным не проверяя». Полезно знать при
экспериментах, но в штатной работе флаг не взводится.

## DisplayPort: обучение линка

Автомат как таковой не выделен — обучение выполняет `0xA0073E1C` с помощниками
(`0xA0073708` — clock recovery, `0xA0073A34` — channel equalization). Стартовые параметры
зашиты константой `0x1E040000`, то есть **8,1 Гбит/с (HBR3) на четырёх линиях**, и при
неудаче идёт стандартная лестница отката:

```
0x1E (8,1 Гбит/с)  ->  0x14 (5,4)  ->  0x0A (2,7)  ->  0x06 (1,62)
число линий при этом делится пополам: 4 -> 2 -> 1
```

Результат печатается по каналам: `Channel[%02x] is Training done!!`,
`Channel[%02x] is Training fail`, `Channel[%02x] is skipped`; отдельно ловятся
`Lost CDR`, `CDR fail`, `TRAINING_NORESPONSE`, `TRAINING_FAIL`. В рабочем режиме
слежение ведёт автомат линка (`docs/video-input.md`): `Lost Training`, `Lost SCDT`,
`FIFO Mode Changed` возвращают его в `PHY_POWERON` или `LINK_STANDBY`.

DSC для DP включается отдельно: строки `DP DSC en= %d` и
`Model Enable 500 Cut5 L%d DSC 3440 4 slices = %d` — четыре среза на 3440 пикселей.

## Отладочные сообщения

Всё описанное выше прошивка умеет печатать сама — нужен только UART (открытый вопрос №5
в `README.md`). Маска категорий — слово `0xA80785FC`, имена бит лежат таблицей указателей
по `0xA00B1CC0`:

| Бит | Имя | Что даёт |
|---|---|---|
| 0 | `EN_HDMI_MSG_INIT_INFO` | инициализация PHY, калибровка Z50, загрузка trim |
| 1 | `EN_HDMI_MSG_EQ_FLOW` | **весь EQ-скан по шагам, с RVGA, R/C и счётчиками SCDC** |
| 2 | `EN_HDMI_MSG_MODEDET_FLOW` | определение режима, тайминги, смены режима |
| 3 | `EN_HDMI_MSG_INT` | прерывания |
| 4 | `EN_HDMI_MSG_INFOFRAME` | InfoFrame: AVI, SPD, HDR, аудио |
| 5 | `EN_HDMI_MSG_AUD` | звук |
| 6 | `EN_HDMI_MSG_HDCP22` | HDCP 2.2 |
| 7 | `EN_HDMI_MSG_IF` | интерфейсный слой |
| 11 | — (имени в таблице нет) | сообщения `[HDMI21]`, то есть обучение FRL |

Управление — `DRV_HDMI_DbgMenu(6, номер_бита, 0/1)`; значение `0x0F` в номере выключает
все категории сразу. Биты 8…14 в таблице имён пустые, хотя бит 11 в коде используется.

## Что не разобрано

- **Чем выбирается MEQ или AEQ.** Флаг найден, писателя не искали.
- **Физический смысл сеток в `PreRVGA`.** Понятно, что считается длина непрерывного
  участка «хороших» настроек — это оценка раскрыва глаза, — но точная формула индексов
  (деление на 7, умножение на `0xCCCCCCCD`) не расписана.
- **Состояния 5 (`BA_Turning`) и 9 (`R_Turning`)** прочитаны бегло: понятно, что это
  доводка R/C, но их место в общем потоке (кто в них входит) по коду не прослежено —
  прямых присваиваний номера состояния в них нет, значит, вход возможен только из
  ветвей, где номер приходит из переменной.
- **Инициализация PHY** (`DRV_HDMI_InitialSettings`, 18 КБ декомпилированного текста):
  видно, что грузятся trim-значения из EFUSE или вручную и калибруется Z50, но подробно
  не читалась.
- **HDCP** не смотрели вовсе.

## Что здесь вывод, а не факт

- Названия RVGA/RCT/CCT взяты из отладочных строк прошивки; их физическая трактовка
  («усиление входного каскада», «сопротивление и ёмкость эквалайзера») — общепринятая
  для адаптивных приёмников, но из образа не следует.
- «Таблица R/C отсортирована от длинного кабеля к короткому» — вывод из того, что CCT
  убывает `0x1FFF → 0x00FF → 0x000F`, то есть подъём АЧХ ослабевает.
- Порог 600 МГц назван пределом HDMI 2.0 по совпадению с спецификацией; в коде это
  просто константа сравнения.
- Соответствие значений 1…6 конкретным ставкам FRL взято из порядка строк
  `FRL Rate = 3G/3L … 12G/4L`, а не из таблицы в коде.
